### Погоджена модель підетапу 4.1

Електронний облік починається 01.01.2027; кадровик вносить підтверджені початкові залишки після врахування операцій до 31.12.2026 включно. Робочі роки основної щорічної відпустки рахуються від дати прийняття, соціальні періоди — календарними роками, періоди за стаж служби в ОМС задаються вручну. Обчислення повертаються як пропозиції й не створюють рядків та днів. Підтверджений нуль зберігається явним записом, відсутність запису лишається невідомим станом. Немає нормативного автозарахування, пропорційного накопичення чи історії використань. Див. технічні інваріанти й фактичні межі в ARCHITECTURE.md.

Нижче збережено хронологію рішень. Положення з номером етапу описують його стан на той момент; уточнення 3.4.2.2/3.4.3.8 та поточний HANDOFF визначають чинні модель/резервування. Старі заборони переходу чи merge не скасовують погодженої фіналізації.

## Поточний кадровий облік (3.5)

HromadaHR веде актуальні кадрові дані та автоматизує подальші операції. Історичну модель посад і призначень та категорію посади вилучено. Дата прийняття зберігається окремо від актуальних посади й підрозділу. Міграція v5 після захисної копії разово очищує дозволені тестові кадрові записи. Це рішення поширюється також на відновлення старих копій через v5.

- Повний облік стажу й попередніх періодів служби скасовано.
- Для надбавок у майбутньому зберігатимуться чинний відсоток, документально підтверджена дата та контроль наступного перегляду.
- Для рангів у майбутньому зберігатимуться актуальний ранг, необхідні підтверджені дати й контроль наступного можливого присвоєння. Повернення категорії посади потребує окремого рішення.
- Для додаткової відпустки за вислугу передбачено початковий показник належної тривалості та контрольну дату наступного перегляду.
- Підетап 4.1 створив початкові залишки й облікові періоди без історії використання; для нових періодів від 01.01.2027 дні зберігаються тільки після кадрового підтвердження. Повноцінний UI (4.2) та реєстрація використання потребують окремих підетапів.

Ці майбутні функції потребують окремих завдань. Підвищення надбавок і присвоєння рангів потребуватимуть кадрового підтвердження.

## Вибір SQLite на етапі 2.2

Обрано **better-sqlite3 13.0.3** із фіксованою версією, без ORM. API prepared statements та синхронних transaction wrappers достатній для малої локальної службової схеми; rollback при винятку реалізує драйвер. На 2.4 штатний online backup використано для всіх знімків активної SQLite. Див. [API драйвера](https://github.com/WiseLibs/better-sqlite3/blob/v13.0.3/docs/api.md).

| Критерій | better-sqlite3 13.0.3 | node:sqlite у поточному Electron |
| --- | --- | --- |
| API | Усталені prepared statements/transaction API; версія драйвера фіксується незалежно | У Node 24.21.0 статус 1.2 Release candidate; API прив'язаний до Node у складі Electron |
| Транзакції | transaction().immediate(), автоматичний rollback винятків | BEGIN/COMMIT/ROLLBACK через SQL, більше ручної обв'язки |
| Майбутнє резервування | Асинхронний online backup API | backup API також доступний; відсутність копій не є причиною відмови |
| Windows | У пакеті є win32-x64 та win32-arm64 Node-API prebuilds; фактично перевірено x64 | Вбудований модуль фактично завантажився в Electron 44.7.1, Node 24.21.0 |
| pnpm/ABI | Node >=22; Node.js 24.22.1 та pnpm 11.25.0 сумісні. Для перевіреного prebuild окремий rebuild не потрібен | Немає окремої залежності та rebuild, але версія SQLite постачається з Electron |
| Пакування | Потрібно включити runtime-пакет і native prebuild відповідної архітектури поза ASAR | Окремих native-файлів застосунку немає |

Перевага better-sqlite3 тут — зрілий транзакційний API та незалежне фіксування драйвера; node:sqlite залишається можливою альтернативою, а не несумісним рішенням. Статус і API Node звірено з [документацією Node 24.21.0](https://github.com/nodejs/node/blob/v24.21.0/doc/api/sqlite.md).

Важлива відмінність від старих better-sqlite3: [версія 13 перейшла на Node-API](https://github.com/WiseLibs/better-sqlite3/releases/tag/v13.0.0) і постачає prebuilds разом із пакетом. Тому стандартну вимогу rebuild для старих ABI-модулів не застосовано механічно. `pnpm-workspace.yaml` явно забороняє install-компіляцію цього пакета; перевірка справжнього Electron Main підтвердила завантаження на Windows x64 без @electron/rebuild. При зміні Electron/драйвера/архітектури тест потрібно повторити. Якщо потрібна власна збірка без сумісного prebuild, слід окремо налаштувати Windows toolchain та rebuild під цільовий Electron відповідно до [правил native modules Electron](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules).

Майбутній пакувальник повинен зберегти better-sqlite3 як runtime-залежність, правильно зібрати залежності pnpm та розпакувати потрібні `prebuilds/*.node` з ASAR. Пакування, ARM64, інсталятор і реліз у 2.2 не створювалися й не перевірялися.

Шлях даних — `%LOCALAPPDATA%\HromadaHR[-dev]\data\hromadahr.db`; чинні Electron-профілі `%APPDATA%` залишено. Dev визначається чинним `!app.isPackaged && --dev`. Обрано WAL, foreign_keys=ON, busy_timeout=5000 та synchronous=FULL з пріоритетом збереження даних. Одна міграція — одна IMMEDIATE-транзакція разом із ledger/checksum/user_version; новішу чи невідому схему відхиляємо, автоматичного downgrade немає. На 2.4 критичним міграціям передує перевірений online snapshot; помилка його створення блокує SQL. Пошкоджену або недоступну базу не замінюємо порожньою.

## Остаточна модель доступу (2.4)

Етап 2.3 скасований остаточно, а не відкладений. Усі функції доступні після запуску без входу. Не буде local_account, логінів/паролів, реєстрації, акаунтів, сеансів, ролей/RBAC, розмежування функцій або скидання/відновлення пароля. SQLite та копії не шифруємо; спеціальні NTFS ACL не налаштовуємо, стандартні дозволи Windows програмно не змінюємо. Ці механізми не плануються в наступних етапах. Це не скасовує технічну межу Main/renderer: sandbox, contextIsolation, nodeIntegration=false, sender/mainFrame/URL, Zod, allowlist та контрольовані помилки залишаються обов'язковими.

## Політика резервування і відновлення (2.4)

- Дві існуючі теки обираються системним діалогом Main. Зберігаються атомарно у службових backup_config/backup_state (міграція 2); довільні шляхи через renderer не приймаються. Канонічні Windows-шляхи перевіряються на однаковість/вкладеність, перетин із каталогом активних даних і запис. Один том — попередження, не заборона.
- Один успішний автоматичний результат на теку за локальну календарну добу; повний цикл вимагає успіху обох тек. Перевірка при запуску/збереженні конфігурації та кожні 15 хвилин під час роботи. Не більше чотирьох автоматичних спроб на теку/добу; повтори через щонайменше 15 хвилин, невдала тека не спричиняє дублювання успішної. Ручні копії не змінюють добові маркери/ліміти. Після повного закриття застосунку завдань немає.
- Знімок створюється online backup API у тимчасовому файлі, переводиться в standalone DELETE journal mode, перевіряється integrity_check/FK/ledger і синхронізується на диск. На 2.4.1 готове ім'я публікується одним MoveFileExW у тій самій теці, без REPLACE_EXISTING/COPY_ALLOWED, із WRITE_THROUGH. Hardlinks більше не потрібні; помилка не залишає готового неповного файла. Перевірено NTFS; фізичний exFAT потребує ручного приймання. Стиснення та шифрування відсутні.
- Імена містять namespace-UUID цієї БД, тип auto/manual і UTC-час. Починаючи з 3.4.3.8 суфікс — SHA-256 спільного образу; старі випадкові UUID підтримуються. Ротація після нової справної auto-копії залишає 14 останніх справних auto-копій цього namespace, звіряє також instance_id усередині БД. Ручні/захисні/чужі/пошкоджені файли не видаляються. При аварії між публікацією та записом результату можливий зайвий безпечний знімок під час повтору.
- Вибір файла для відновлення створює окремий перевірений staged snapshot та одноразовий токен на 5 хвилин. Окреме підтвердження IPC потребує цього токена та системного діалогу Main з безпечним default/cancel. Прапорця confirmed або шляху в аргументах немає. Навігація/знищення вікна скасовують невикористані вибори.
- Перед заміною зберігається перевірений protect-restore snapshot у власному data/protection. Після checkpoint TRUNCATE/close і перевірки відсутності WAL/SHM журнал наміру передує перейменуванню старої БД. Нову БД відкриваємо, мігруємо й перевіряємо; тільки потім видаляємо журнал. Помилка повертає стару БД; незавершений журнал при наступному старті також повертає попередню. Якщо безпечне повернення не вдалося — RECOVERY_REQUIRED, без удаваної готовності. Джерело та захисні копії не видаляються.
- Штатне відновлення зберігає поточні теки/namespace інсталяції, скидає результати backup_state/добові маркери, але не окремий backup-history.json та потребує справної активної БД для online-захисту. Інтерфейс перезавантажується після успіху. Захисні копії не входять до ротації; їх автоматичне очищення не реалізовано. На 2.4.1 додано окремий аварійний сценарій; автоматичного ремонту немає.

## Надійність резервування та аварійне відновлення (2.4.1)

Node fs.rename на Windows може замінити наявний файл; exists+rename не дає no-replace. Обрано вузький Main-only Win32 адаптер через фіксований koffi 3.3.6. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) без прапорця заміни відхиляє колізію; fallback між томами через copy/delete заборонено. Публікується лише перевірений і fsync-нутий online snapshot. Одне перейменування не показує проміжних скопійованих байтів під готовою назвою; фізичні збої ФС/носія цим не усуваються. Koffi має Node-API prebuild; Windows x64 перевірено в Node й Electron, ARM64/пакування — ні. Майбутній пакувальник має включити native optional-пакет поза ASAR. Скрипт компіляції вимкнено в pnpm-workspace.yaml; інших залежностей не додано.

Аварійне відновлення дозволене для CORRUPT, UNSUPPORTED_SCHEMA (окремо від пошкодження) та MISSING_DATABASE. FILESYSTEM/BUSY/помилка міграції не дозволяють заміну. До ready основний інтерфейс закритий екраном відновлення; retry — явна дія під тим самим mutex. Перший успішний запуск створює окремий маркер: втрата вже відомої БД не спричиняє її створення. До першого маркера відсутню стару БД неможливо відрізнити від нової інсталяції.

Той самий двоетапний restore створює staging/incoming і вимагає native confirmation. Для пошкодженого оригіналу [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) із share=0 утримує всі наявні DB/WAL/SHM/journal файли без стороннього читання/запису/видалення. Якщо handles не отримані або побайтове збереження в protection/raw-UUID та SHA-256 не вдалося, заміни немає. Перейменування виконується через ті самі handles: [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) із ReplaceIfExists=false. Це короткочасний захист відновлення локальних файлів, не зміна моделі розташування бази.

Розширено існуючий restore-journal (v2/raw, старий формат підтримується). Перевірений raw-набір залишається незмінним джерелом повторюваного rollback, включно з перериванням файлових операцій. Commit — видалення журналу після відкриття/міграцій/цілісності кандидата. Невдале повернення — RECOVERY_REQUIRED. Raw/previous/rejected не ротуються. За аварійного відновлення конфігурація резервування повертається з копії; її слід перевірити. Міграції 1/2 та checksum не змінено. Авторизація, ACL, шифрування й мережева модель не додаються.

## 4.3 — Погоджений облік використаних днів

Три поточні види мають спільну модель реєстрації. Кадровик підтверджує надання, явну тривалість і розподіл. Календарна арифметика пропонує тривалість, FIFO пропонує розподіл за найстарішими підтвердженими періодами. Ручне зменшення календарної тривалості потребує пояснення. Підтверджені величини періодів не переписуються при списанні. Залишок обчислюється з чинних розподілів.

Початок звичайної реєстрації — від 01.01.2027. Відпустки, що почалися у 2026 році, потребують окремої перевірки початкових залишків. Два active інтервали одного працівника не перекриваються незалежно від виду. Повноцінна корекція й скасування реєстрацій належать 4.4.

## 4.4 — Редагування та скасування

Корекція активної відпустки зберігає її ID та первинну дату створення. expectedRevision захищає від застарілого редагування, успішна корекція/перше скасування збільшує ревізію. Перерахунок власних списань атомарний. Чужі реєстрації не перерозподіляються.

Скасована відпустка лишається в журналі з причиною та часом, її розподіли зберігаються для зв’язків, але не беруть участі в поточному використанні. Повторна реєстрація здійснюється новим записом. Скасування в застосунку не скасовує кадровий документ.

FIFO пропонує тільки періоди, які почалися на дату початку відпустки. Ручне списання допускає період із початком усередині інтервалу, але не після завершення. Старі невідповідності зберігаються до ручного виправлення та позначаються в журналі. GUI-приймання відкладене до фінального підетапу.

П’ять видимих груп не змінюють шість внутрішніх типів: «Соціальні та інші» — навігаційна група з обов’язковим фактичним підвидом, а не юридична класифікація чи спільне право. Спеціальні річні обмеження та періодні правила збережені. Візуальні критерії й Windows scaling після перебудови потребують ручного приймання.

## 4.6.4 — Ручне підтвердження поточного права

Погоджено мінімальний незалежний стан на кожен фактичний тип: has_right/no_right або відсутня перевірка, з останнім часом Main. Це не правовий калькулятор і не історія; початкові дані v9 не перетворюються на автоматичні права. Оновлення статусу не змінює днів/історії й не блокує чинних операцій реєстрації. Суперечності показуються кадровику як застереження. Збереження в окремій v10 employee_leave_rights, керування лише у робочому розділі. ОМС-пропозиції обраних календарних років — редаговані чернетки, а не встановлені програмою періоди стажу чи дні права. Видимі тексти використовують середнє тире; користувацькі дані не переформатовуються.

## 4.6.5 — Наступний робочий період

Погоджено показувати один наступний робочий рік основної відпустки як пропозицію з міткою майбутнього. Це не право й не автоматичне нарахування; кадровик може явно підтвердити дні. Старі періоди не мігруються, політика 29 лютого й обмеження використання майбутніх періодів незмінні. Дитячі календарні роки та ручні ОМС-періоди не успадковують цей алгоритм. Права винесено до третьої вкладки; загальна реєстрація завжди починається без автоматичного вибору працівника.

## 4.6.6 – Показ подієвих видів поруч із залишками

Вкладка залишків охоплює шість фактичних видів у двох чітких групах. Для подієвих показуємо річні реєстрації за роком початку й повну підтверджену тривалість активних записів; скасовані лишаються історією. Це не новий баланс і не розбиття через 31 грудня. Ліміт спеціального виду не перетворюємо на гарантовану доступну різницю; для навчальної універсального ліміту немає. Права лишаються незалежним ручним висновком із одним явним збереженням змінених станів. Облікові/правові правила не переглядалися.

## 4.6.8 – Поточне право й облікова історія

Статус «Права немає» описує поточний висновок кадровика. Історичні залишки, списання та записи журналу зберігають свій зміст. Явне підтвердження в редакторі потрібне для додавання періоду з основою `confirmed_entitlement`, якщо цього підтвердження ще немає й поточний статус `no_right`. Початкові залишки та виправлення наявних підтверджень проходять звичайним шляхом. За помилки читання прав редактор просить повторити завантаження перед додаванням нового права. Після успішного збереження прав вкладка залишків перечитує `listRights` для вибраного працівника.

Кількість і найстаріший період із залишком визначаються за підтвердженими періодами з додатним `availableDays`. Дати показують межі облікового періоду. У річному огляді до початку обліку типовим вибором є 2027 рік. Роки фактичних реєстрацій доступні у списку.

## 4.7.4 – Розподіл і наступний робочий період

Чернетка розподілу зберігає значення за ідентифікаторами підтверджених періодів. Після зміни дат, виду або тривалості у підсумку враховуються тільки допустимі періоди з актуальної відповіді Main. Значення за тимчасово недопустимим періодом можна відновити, повернувши допустимий діапазон. Збереження вимагає повного коректного розподілу. FIFO враховує початок відпустки та застосовується лише явно. Ручне списання враховує завершення відпустки. Попередження про нестачу використовує суму всіх допустимих підтверджених днів.

Пропозицію наступного робочого року щорічної основної звіряють із підтвердженими записами. Непідтверджена пропозиція веде до редактора залишків через захист чернетки. Підтверджений період після завершення відпустки відображається інформаційно, а допустимий період із додатними днями має поле списання. Перегляд і переходи не записують днів. Схема, IPC, серверна валідація, ревізії та транзакції обліку залишилися чинними.

## 4.7.5 – Межі ручного списання та FIFO

Рішення 4.7.5 замінює обмеження ручного списання за датою завершення відпустки. Розподіл може посилатися на реальний підтверджений період працівника й виду з достатнім залишком, зокрема на період після завершення відпустки. Це облікова можливість. Кадровик перевіряє юридичну підставу використання, на що вказує контекстне застереження у формі. FIFO залишається явною дією та використовує періоди, що почалися не пізніше дати початку відпустки.

Похідна ознака allocationWarning більше не вважає майбутню дату помилкою. Поле збережено для сумісності IPC. Міграції й історичні записи залишилися чинними. Перевірки ідентифікатора, виду, суми, залишку та ревізії, транзакції й повернення днів після скасування застосовуються до всіх розподілів.

## 4.7.6 – Точка відліку за стаж та вибір дитячого року

Кадровик явно зберігає дату набуття права за стаж. Річні межі використовують чинну календарну арифметику з переходом 29 лютого на 28 лютого в невисокосному році. Пропозиції охоплюють поточний горизонт і наступний період у межах захисного ліміту. Уже внесені межі не зсуваються. Перекриття зі старими періодами прибираються з пропозицій. Дні підтверджуються окремо.

Редактор ручного періоду пропонує дату завершення. Явно змінена дата зберігається до натискання «Перерахувати завершення». Дитячий рік утворює межі 01.01–31.12 і порожню чернетку днів. Поточний статус права не визначає минулих залишків. Річний огляд подієвих типів у залишках вилучено. Журнал і чинні операції для всіх шести видів збережено.

## 4.8.2 – Межі чернетки реєстрації

Чернетка належить поточному екземпляру `LeaveRegistrationForm`. Поки відкритий редактор днів, стан форми залишається змонтованим, а її діалог тимчасово замінено. Явне закриття або навігація залишаються під чинним захистом. Відмова в редакторі днів скасовує тільки його власні незбережені правки. Внесені залишки є самостійним обліковим записом і не відкочуються при відмові від реєстрації.

Повернення перечитує актуальну пропозицію з Main. Раніше введені значення залишаються за ідентифікаторами, недоступні списання потрібно явно прибрати. Ревізія редагування не підміняється під час оновлення залишків. Актуальний запис відкривається лише окремою дією кадровика, а повторне збереження використовує чинні перевірки ревізій та ідемпотентності.

## 4.8.3 – Попередній перегляд і послідовний запис залишків за стаж

Main та редактор використовують один чистий календарний розрахунок із `shared/leave-periods.ts`. Редактор показує пропозиції для чернетки дати без запису в сховище. Чинні межі періодів, політика річниці, фільтр перекриття з підтвердженими періодами й межа 01.01.2027 збережені.

Одна дія користувача координує два незалежні виклики IPC. Зміна дати не повертається автоматично при помилці днів. Відомий успіх дати стає новим базовим станом форми, тому повторний запис без зміни дати надсилає лише дні. Повідомлення про успіх залежить від фактично виконаних записів.

## 4.8.4 – Фактичні надання та тимчасовий контекст журналу

Форма й журнал читають один набір записів `LeaveWorkspace`. Для подієвих видів `annualUsage` відносить усю тривалість активного запису до року початку, а скасування рахує окремо. Поточне право, періодні залишки та надання залишаються незалежними. Відсутність запису про право означає неперевірений стан після успішного читання.

Контекстний вхід відкриває чинну таблицю та панель фільтрів з точним видом і роком початку. Поза контекстом рік у журналі, як і раніше, враховує перетин календарного року, а спеціальні види групуються. Форма тимчасово прибирає діалог і зберігає локальну чернетку. Повернення відновлює діалог, явний вихід із розділу проходить через наявний захист.

## 4.9.2 – Глобальна черговість і поточні назви

Підрозділи й посади мають незалежні порядки. Одна посада може використовуватися в різних підрозділах. Ревізія порядку охоплює створення, видалення та перестановку, а ревізія запису захищає перейменування й підтвердження видалення. У разі відмови reorder Renderer перечитує Main. Підтвердження видалення показує назву, Main повторно перевіряє зв’язки в момент запису.

Кадрові картки та інші представлення, які читають JOIN із довідником, показують поточну назву. Історія назв цим етапом не ведеться. Розділ створює основу для 4.9.3. Таблиця й сортування реєстру працівників залишаються чинними.

## 4.9.5 – Семантика показників у вкладці обліку

Поточне право є незалежним висновком кадровика. Підтверджені дні – внесені до обліку величини за збереженими періодами, зокрема початкові залишки. Використані дні за періодами – списання з цих періодів. Доступні дні залишаються їхнім підтвердженим залишком, а за відсутнього поточного права позначаються як історичні. Підтверджений нуль відображається окремо від невнесених величин.

Для подієвих видів сума й кількість надань відображають активні реєстрації в HromadaHR за роком початку. Скасовані реєстрації залишаються в історії. Облікова межа тривалості походить із чинних обмежень спеціального виду. Індивідуальна належна тривалість залежить від документів і не виводиться автоматично зі статусу права, внесеного початкового залишку або межі реєстрації. Модель сховища й облікові алгоритми залишилися чинними.

## 4.9.6 – Типізований намір переходу до відпусток

LeaveNavigationIntent існує в Renderer і передає ID працівника, верхню вкладку та опційний вид обліку. App виконує один navigationGuard перед переходом і очищає намір на звичайній навігації. LeaveWorkspace використовує його лише як початковий стан нового екземпляра та читає актуальні дані через чинні IPC. Картка не передає підсумки, а контекст відсутнього працівника не підмінюється іншим ID.
