## Вибір SQLite на етапі 2.2

Обрано **better-sqlite3 13.0.3** із фіксованою версією, без ORM. API prepared statements та синхронних transaction wrappers достатній для малої локальної службової схеми; rollback при винятку реалізує драйвер. На 2.4 штатний online backup використано для всіх знімків активної SQLite. Див. [API драйвера](https://github.com/WiseLibs/better-sqlite3/blob/v13.0.3/docs/api.md).

| Критерій | better-sqlite3 13.0.3 | node:sqlite у поточному Electron |
| --- | --- | --- |
| API | Усталені prepared statements/transaction API; версія драйвера фіксується незалежно | У Node 24.21.0 статус 1.2 Release candidate; API прив'язаний до Node у складі Electron |
| Транзакції | transaction().immediate(), автоматичний rollback винятків | BEGIN/COMMIT/ROLLBACK через SQL, більше ручної обв'язки |
| Майбутнє резервування | Асинхронний online backup API | backup API також доступний; відсутність копій не є причиною відмови |
| Windows | У пакеті є win32-x64 та win32-arm64 Node-API prebuilds; фактично перевірено x64 | Вбудований модуль фактично завантажився в Electron 44.7.1, Node 24.21.0 |
| pnpm/ABI | Node >=22; Node.js 24.22.1 та pnpm 11.25.0 сумісні. Для перевіреного prebuild окремий rebuild не потрібен | Немає окремої залежності та rebuild, але версія SQLite постачається з Electron |
| Пакування | Потрібно включити runtime-пакет і native prebuild відповідної архітектури поза ASAR | Окремих native-файлів застосунку немає |

Перевага better-sqlite3 тут — зрілий транзакційний API та незалежне фіксування драйвера; node:sqlite залишається можливою альтернативою, а не несумісним рішенням. Статус і API Node звірено з [документацією Node 24.21.0](https://github.com/nodejs/node/blob/v24.21.0/doc/api/sqlite.md).

Важлива відмінність від старих better-sqlite3: [версія 13 перейшла на Node-API](https://github.com/WiseLibs/better-sqlite3/releases/tag/v13.0.0) і постачає prebuilds разом із пакетом. Тому стандартну вимогу rebuild для старих ABI-модулів не застосовано механічно. `pnpm-workspace.yaml` явно забороняє install-компіляцію цього пакета; перевірка справжнього Electron Main підтвердила завантаження на Windows x64 без @electron/rebuild. При зміні Electron/драйвера/архітектури тест потрібно повторити. Якщо потрібна власна збірка без сумісного prebuild, слід окремо налаштувати Windows toolchain та rebuild під цільовий Electron відповідно до [правил native modules Electron](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules).

Майбутній пакувальник повинен зберегти better-sqlite3 як runtime-залежність, правильно зібрати залежності pnpm та розпакувати потрібні `prebuilds/*.node` з ASAR. Пакування, ARM64, інсталятор і реліз у 2.2 не створювалися й не перевірялися.

Шлях даних — `%LOCALAPPDATA%\HromadaHR[-dev]\data\hromadahr.db`; чинні Electron-профілі `%APPDATA%` залишено. Dev визначається чинним `!app.isPackaged && --dev`. Обрано WAL, foreign_keys=ON, busy_timeout=5000 та synchronous=FULL з пріоритетом збереження даних. Одна міграція — одна IMMEDIATE-транзакція разом із ledger/checksum/user_version; новішу чи невідому схему відхиляємо, автоматичного downgrade немає. На 2.4 критичним міграціям передує перевірений online snapshot; помилка його створення блокує SQL. Пошкоджену або недоступну базу не замінюємо порожньою.

## Остаточна модель доступу (2.4)

Етап 2.3 скасований остаточно, а не відкладений. Усі функції доступні після запуску без входу. Не буде local_account, логінів/паролів, реєстрації, акаунтів, сеансів, ролей/RBAC, розмежування функцій або скидання/відновлення пароля. SQLite та копії не шифруємо; спеціальні NTFS ACL не налаштовуємо, стандартні дозволи Windows програмно не змінюємо. Ці механізми не плануються в наступних етапах. Це не скасовує технічну межу Main/renderer: sandbox, contextIsolation, nodeIntegration=false, sender/mainFrame/URL, Zod, allowlist та контрольовані помилки залишаються обов'язковими.

## Політика резервування і відновлення (2.4)

- Дві існуючі теки обираються системним діалогом Main. Зберігаються атомарно у службових backup_config/backup_state (міграція 2); довільні шляхи через renderer не приймаються. Канонічні Windows-шляхи перевіряються на однаковість/вкладеність, перетин із каталогом активних даних і запис. Один том — попередження, не заборона.
- Один успішний автоматичний результат на теку за локальну календарну добу; повний цикл вимагає успіху обох тек. Перевірка при запуску/збереженні конфігурації та кожні 15 хвилин під час роботи. Не більше чотирьох автоматичних спроб на теку/добу; повтори через щонайменше 15 хвилин, невдала тека не спричиняє дублювання успішної. Ручні копії не змінюють добові маркери/ліміти. Після повного закриття застосунку завдань немає.
- Знімок створюється online backup API у тимчасовому файлі, переводиться в standalone DELETE journal mode, перевіряється integrity_check/FK/ledger і синхронізується на диск. На 2.4.1 готове ім'я публікується одним MoveFileExW у тій самій теці, без REPLACE_EXISTING/COPY_ALLOWED, із WRITE_THROUGH. Hardlinks більше не потрібні; помилка не залишає готового неповного файла. Перевірено NTFS; фізичний exFAT потребує ручного приймання. Стиснення та шифрування відсутні.
- Імена містять namespace-UUID цієї БД, тип auto/manual, UTC-час і випадковий UUID. Ротація після нової справної auto-копії залишає 14 останніх справних auto-копій цього namespace, звіряє також instance_id усередині БД. Ручні/захисні/чужі/пошкоджені файли не видаляються. При аварії між публікацією та записом результату можливий зайвий безпечний знімок під час повтору.
- Вибір файла для відновлення створює окремий перевірений staged snapshot та одноразовий токен на 5 хвилин. Окреме підтвердження IPC потребує цього токена та системного діалогу Main з безпечним default/cancel. Прапорця confirmed або шляху в аргументах немає. Навігація/знищення вікна скасовують невикористані вибори.
- Перед заміною зберігається перевірений protect-restore snapshot у власному data/protection. Після checkpoint TRUNCATE/close і перевірки відсутності WAL/SHM журнал наміру передує перейменуванню старої БД. Нову БД відкриваємо, мігруємо й перевіряємо; тільки потім видаляємо журнал. Помилка повертає стару БД; незавершений журнал при наступному старті також повертає попередню. Якщо безпечне повернення не вдалося — RECOVERY_REQUIRED, без удаваної готовності. Джерело та захисні копії не видаляються.
- Штатне відновлення зберігає поточні теки/namespace інсталяції, скидає історію/добові маркери та потребує справної активної БД для online-захисту. Інтерфейс перезавантажується після успіху. Захисні копії не входять до ротації; їх автоматичне очищення не реалізовано. На 2.4.1 додано окремий аварійний сценарій; автоматичного ремонту немає.

## Надійність резервування та аварійне відновлення (2.4.1)

Node fs.rename на Windows може замінити наявний файл; exists+rename не дає no-replace. Обрано вузький Main-only Win32 адаптер через фіксований koffi 3.3.6. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) без прапорця заміни відхиляє колізію; fallback між томами через copy/delete заборонено. Публікується лише перевірений і fsync-нутий online snapshot. Одне перейменування не показує проміжних скопійованих байтів під готовою назвою; фізичні збої ФС/носія цим не усуваються. Koffi має Node-API prebuild; Windows x64 перевірено в Node й Electron, ARM64/пакування — ні. Майбутній пакувальник має включити native optional-пакет поза ASAR. Скрипт компіляції вимкнено в pnpm-workspace.yaml; інших залежностей не додано.

Аварійне відновлення дозволене для CORRUPT, UNSUPPORTED_SCHEMA (окремо від пошкодження) та MISSING_DATABASE. FILESYSTEM/BUSY/помилка міграції не дозволяють заміну. До ready основний інтерфейс закритий екраном відновлення; retry — явна дія під тим самим mutex. Перший успішний запуск створює окремий маркер: втрата вже відомої БД не спричиняє її створення. До першого маркера відсутню стару БД неможливо відрізнити від нової інсталяції.

Той самий двоетапний restore створює staging/incoming і вимагає native confirmation. Для пошкодженого оригіналу [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) із share=0 утримує всі наявні DB/WAL/SHM/journal файли без стороннього читання/запису/видалення. Якщо handles не отримані або побайтове збереження в protection/raw-UUID та SHA-256 не вдалося, заміни немає. Перейменування виконується через ті самі handles: [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) із ReplaceIfExists=false. Це короткочасний захист відновлення локальних файлів, не зміна моделі розташування бази.

Розширено існуючий restore-journal (v2/raw, старий формат підтримується). Перевірений raw-набір залишається незмінним джерелом повторюваного rollback, включно з перериванням файлових операцій. Commit — видалення журналу після відкриття/міграцій/цілісності кандидата. Невдале повернення — RECOVERY_REQUIRED. Raw/previous/rejected не ротуються. За аварійного відновлення конфігурація резервування повертається з копії; її слід перевірити. Міграції 1/2 та checksum не змінено. Авторизація, ACL, шифрування й мережева модель не додаються.

## Межа наступних рішень

На етапі 2.1 обрано мінімальні спільні контракти без RPC-фреймворку, Zod для runtime-валідації в Main та дискримінований результат без витоку текстів винятків. Sandboxed preload збирається наявним Vite в один CommonJS-файл. На 2.4 реєстратор розширено на асинхронні операції зі збереженням тих самих технічних перевірок; авторизації та її заглушок немає.

На 3.1 реалізовано замовлену предметну основу працівників, міграцію 3 та типізовані кадрові IPC-контракти без React-інтерфейсу. За уточненим завданням employee_type — official або staff, по батькові nullable. Посада/підрозділ і дата прийняття походять лише з employee_positions: поточне призначення — останній запис, прийняття — перший. Категорія nullable належить призначенню. UNIQUE(employee_id,start_date); довідники захищено від дублів Unicode-нормалізованим ключем. Міграція 3 вимагає захисну копію. IPC 3.1 обмежений читанням, створенням працівника/довідників і редагуванням персональних відомостей; видалення працівника та зміни історії — 3.3. Наступні предметні функції, міграції й зміни контрактів потребують окремого завдання. Авторизація й механізми паролів не є майбутнім завданням.

На 3.2 реалізовано замовлений React-реєстр, створення/персональне редагування, швидке створення довідників і особову картку з історією. Використано дев’ять готових IPC-методів без змін схеми/сервісів. Пошук/фільтр/сортування — клієнтські для ~30 записів, без нового grid-фреймворку чи залежностей. Три майбутні вкладки картки planned; видалення та зміни історії не відкриті.

Реалізація 3.3 та наступних предметних функцій, інсталятора, оновлень або релізів потребує окремого завдання. Етап 2.4 завершує поточну локальну інфраструктуру; 2.3 скасований.
