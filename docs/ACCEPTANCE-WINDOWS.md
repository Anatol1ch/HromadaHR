## 2. Безпечне середовище — виконати до запуску

**Built використовує каталог даних поточного Windows-користувача. Не запускати руйнівні сценарії в обліковому записі, де є реальні кадрові дані.** Обрати окрему тестову Windows VM або окремий локальний тестовий обліковий запис; увійти саме до нього. Для іншої еквівалентної ізоляції спочатку довести фактичні шляхи та відсутність production-даних. Звичайне окреме вікно PowerShell у тому самому обліковому записі ізоляції не дає.

| Режим | SQLite | Electron userData / масштаб та службові налаштування |
|---|---|---|
| dev | `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db` | `app.getPath('appData')\HromadaHR-dev`, зазвичай `%APPDATA%\HromadaHR-dev` |
| built | `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db` | `app.getPath('appData')\HromadaHR`, зазвичай `%APPDATA%\HromadaHR` |

Підтверджено electron/storage/index.ts storagePath та electron/main.ts userData. Відмінність Roaming/Local є реальною: не шукати всі файли лише поруч із SQLite. Шляхи перевіряються технічним оператором у Windows, без додавання їх у renderer/API. Жодних підмін LOCALAPPDATA/APPDATA, нових runtime-прапорців чи очистки production-каталогів.

У тестовому Windows-профілі перед першим запуском:

```powershell
whoami
$env:USERPROFILE
$env:LOCALAPPDATA
$env:APPDATA
Test-Path -LiteralPath (Join-Path $env:LOCALAPPDATA 'HromadaHR\data\hromadahr.db')
Test-Path -LiteralPath (Join-Path $env:LOCALAPPDATA 'HromadaHR-dev\data\hromadahr.db')
```

Якщо це не підтверджений тестовий користувач або файли вже існують невідомого походження — **STOP**, з’ясувати власника/вміст поза застосунком; не видаляти й не перезаписувати. Для повтору з чистого стану використовувати новий тестовий профіль/чистий snapshot VM або штатний restore власної синтетичної копії. В інструкції навмисно немає скрипта очищення БД.

Для нового тестового checkout після публікації пакета (у вільному каталозі тестового користувача):

```powershell
git clone --branch codex/8.1-acceptance-baseline https://github.com/Anatol1ch/HromadaHR.git HromadaHR-acceptance
Set-Location HromadaHR-acceptance
```

Звірити фінальний SHA пакета зі звітом 8.1. У наявному checkout спочатку зберегти сторонню роботу; не робити reset/clean заради приймання. У копії репозиторію з потрібним SHA:

```powershell
git status --short
git rev-parse HEAD
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

Завантаження залежностей/Electron потребує інтернету. Node 24.22.1, pnpm 11.25.0. Після збірки зупинити dev/Vite, потім **лише в ізольованому тестовому Windows-профілі**:

```powershell
pnpm start:built
```

Це запуск `electron .` з dist, не інсталятор. Готового Windows-інсталятора й auto-update немає. Dev запускається `pnpm dev`, читає Vite `http://127.0.0.1:5176/`; built має читати dist без Vite. Не запускати два сеанси одного профілю для створення штучних revision-конфліктів; single-instance lock штатний.

Після першого успішного запуску/закриття звірити файл та власника read-only:

```powershell
Get-Item -LiteralPath (Join-Path $env:LOCALAPPDATA 'HromadaHR\data\hromadahr.db') | Select-Object FullName,Length,LastWriteTime
Get-Acl -LiteralPath (Join-Path $env:LOCALAPPDATA 'HromadaHR\data\hromadahr.db') | Select-Object Owner
```

Не відкривати live SQLite довільним редактором для сценаріїв GUI, не копіювати лише main db без WAL як спосіб резервування. Копії — через штатний BackupService. Для offline-перевірки після install/build від’єднати мережу **тестової VM**; локальне UI/SQLite мають працювати, зовнішні контакти й мережеві backup-теки оцінюються окремо. Відновити мережу після перевірки. Жодного GUI-сценарію Codex у 8.1 не виконував.

## 4. Правила виконання й критерії

Виконувати A (ізоляція/запуск) → B і дані S0 → C/D → E/S1 → F → G → H; модифікаційні кейси мають повертатися до зазначеної S0/S1. Значення й точні тестові періоди — [ACCEPTANCE-DATA](ACCEPTANCE-DATA.md). Якщо рядок має кілька перевірок, занотувати результат кожної; невиконана критична частина не дозволяє загальний PASS. Для нової ОС/масштабу копіювати рядки з новими умовами, не стирати попередній результат. Вести один протокол на SHA, Windows build і конфігурацію; для повторного масштабу/ОС робити окрему копію результатів, не стирати минулі.

Статуси: PASS — дії реально виконані й усі очікування підтверджені; FAIL — підтверджена невідповідність; BLOCKED — немає безпечних умов/еталона/тестового harness; NOT_RUN — ще не виконано; NOT_APPLICABLE — обґрунтовано не застосовується, погоджено з відповідальним. Усі рядки починаються NOT_RUN. Колонка P — попередній рівень **лише якщо знайдено дефект**, не твердження про існуючий дефект. Для втрати даних підвищити до P0 незалежно від рядка.

Факт: дата/виконавець, точні результати (дні/номери/статуси), посилання на синтетичний доказ. Якщо FAIL — створити DEF у [журналі](ACCEPTANCE-DEFECTS.md), зв’язати scenario ID; якщо BLOCKED/NOT_APPLICABLE — записати причину й умови повтору. Не вимагати від UI засобів ін’єкції transport errors/stale revisions: якщо немає підготовленого disposable harness, залишити BLOCKED для ручної частини, вказати чинний автотест. Не редагувати live SQLite для отримання PASS.

До практичної експлуатації потрібні завершене релевантне GUI-приймання, відсутність відкритих P0/P1 або явне рішення відповідальних, оцінка RELEASE-GAPS, окреме рішення замовника про персональні дані й перевірене відновлення. 8.1 не є цим дозволом. При P0/P1 зупинити залежні сценарії, зберегти докази/синтетичну БД, не робити імпровізованого ремонту; окреме завдання на виправлення.
