# Поточний стан HromadaHR

**Функціональне тестування HromadaHR завершено успішно 16 листопада 2026 року. Основні робочі сценарії перевірено користувачем. Етапи функціональної розробки та перевірки завершено. Наступна фаза – послідовне вдосконалення інтерфейсу та користувацьких процесів.**

## Статус

- Вихідна гілка codex/8.1-acceptance-baseline, SHA 748e36d8fae752919101aec8084ca8142f0a9a2e. Гілка фіналізації: codex/8.2-functional-finalization.

## Прийнятий функціональний обсяг

Користувач особисто підтвердив створення/редагування працівників, довідники посад/підрозділів, стаж, надбавки, ранги/прогнози, права/залишки відпусток, реєстрацію/FIFO, кадрові документи, ручні/автоматичні номери, document–leave links, кадровий контроль/нагадування. Погоджений спосіб практичної перевірки описано в [підсумку](ACCEPTANCE-WINDOWS.md). Резервування лишається без змін, із чинним автоматизованим покриттям; не додаємо твердження про окреме ручне приймання backup.

Шість глобальних розділів: Головна, Огляд, Працівники, Документи, Довідники, Налаштування. Персональні кадрові операції — у EmployeeProfilePage. Документи мають реєстр і глобальний журнал відпусток; серії — окремий довідник. Номер — текст, ідентифікація за UUID. Зв’язки з відпустками явні й захищають реквізити, нумераційні claims не звільняються після delete.

## Наступна фаза: одне вікно за раз

1. Користувач показує конкретне вікно.
2. Обговорюємо недоліки, складність і бажану поведінку.
3. Погоджуємо остаточну структуру й користувацьку логіку.
4. Окреме завдання визначає обсяг лише цього вікна.
5. Реалізуємо, перевіряємо та комітимо зміну.
6. До наступного вікна переходимо лише після завершення попереднього.

Можна змінювати користувацьку логіку в погодженому обсязі. Немає масового редизайну, наперед визначеного великого UI roadmap або функцій на випередження. HromadaAID лишається read-only джерелом перевірених спільних компонентів, палітра HromadaHR зберігається. У коміті 8.2 редизайн не починається.

## Перевірки після оптимізації

Було 52 файли *.test.mjs / 287 сценаріїв + Electron storage smoke. Стало 42 файли / 234 сценарії + той самий smoke. Реально вилучено 53 надлишкові сценарії (18,5%); просте перейменування чи виключення з запуску не використовувалося. Орієнтир 30–50% не досягався штучно: збережені критичні перевірки даних/розрахунків/інфраструктури. Обґрунтування видалень, вісім груп і карта гарантій — [tests/README.md](../tests/README.md).

- Невелике погоджене UI-вікно: pnpm typecheck, pnpm build, git diff --check; наявні цільові тести, якщо торкнута їхня поведінка.
- Shared UI/Main/SQLite/IPC/розрахунки або значущий інтеграційний коміт: повний pnpm test (усі тести + Electron smoke).
- pnpm test ui / documents / leaves / seniority / personnel / control / infrastructure / backup — цільовий запуск. Без аргументів або all — весь набір. Кожен test-файл обов’язково належить модулю; невідомий/неприв’язаний файл спричиняє помилку запуску.
- Нові тести лише для підтвердженого дефекту/істотного нового ризику. Не створювати 5–10 тестів на підписи, відступи або перестановку кнопок.

Фінальні перевірки 8.2: pnpm typecheck, повний pnpm test **234/234** + **ELECTRON_STORAGE_OK** (Electron 44.7.1, Node 24.21.0 x64), pnpm build та git diff --check — успішні; pnpm test ui — 10/10. Немає skipped/cancelled тестів. Vite bootstrap 535.35 kB має те саме рекомендаційне попередження; build pipeline/ліміт не змінено. Додатково перевірено fail-closed відмову runner на невідомий модуль і неприв’язаний test-файл, повноту manifest та локальних документальних посилань. Це не нові приховані test-сценарії. Число тестів не є критерієм приймання UI.
