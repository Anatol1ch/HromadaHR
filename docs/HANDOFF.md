## Прийнятий функціональний обсяг

Користувач особисто підтвердив створення/редагування працівників, довідники посад/підрозділів, стаж, надбавки, ранги/прогнози, права/залишки відпусток, реєстрацію/FIFO, кадрові документи, ручні/автоматичні номери, document–leave links, кадровий контроль/нагадування. Погоджений спосіб практичної перевірки описано в [підсумку](ACCEPTANCE-WINDOWS.md). Резервування лишається без змін, із чинним автоматизованим покриттям; не додаємо твердження про окреме ручне приймання backup.

Шість глобальних розділів: Головна, Огляд, Працівники, Документи, Довідники, Налаштування. Персональні кадрові операції — у EmployeeProfilePage. Документи мають реєстр і глобальний журнал відпусток; серії — окремий довідник. Номер — текст, ідентифікація за UUID. Зв’язки з відпустками явні й захищають реквізити, нумераційні claims не звільняються після delete.

## Наступна фаза: одне вікно за раз

1. Користувач показує конкретне вікно.
2. Обговорюємо недоліки, складність і бажану поведінку.
3. Погоджуємо остаточну структуру й користувацьку логіку.
4. Окреме завдання визначає обсяг лише цього вікна.
5. Реалізуємо, перевіряємо та комітимо зміну.
6. До наступного вікна переходимо лише після завершення попереднього.

Можна змінювати користувацьку логіку в погодженому обсязі. Немає масового редизайну, наперед визначеного великого UI roadmap або функцій на випередження. HromadaAID лишається read-only джерелом перевірених спільних компонентів, палітра HromadaHR зберігається. У коміті 8.2 редизайн не починається.

## Етап 9.12.9 – Річна доступність УБД та ЧАЕС

Від `codex/9.12.8-children-leave-simplification` (`ff5da41d4e278db428c4d269657dd14a2558fc5d`) створено `codex/9.12.9-special-leave-annual-availability`. Main тепер вимагає поточне кадрове `has_right`, повний суцільний період 14 днів для ветеранської або 16 для ЧАЕС, рік початку не раніше поточного та відсутність іншого активного запису цього типу за рік початку. Чинний унікальний partial index, IMMEDIATE-транзакція, idempotency, revision/overlap guards забезпечують контроль дублювання. Перехід через межу року атрибутується року початку; минулорічне використання не зменшує наступний рік; скасований запис не споживає ключ. Поточний статус права не доводить історичне право й не видаляє старі факти.

SQLite v25 додає лише backup-protected INSERT/UPDATE triggers для точної кількості днів та календарної довжини. Міграція не змінює старих даних; старий активний частковий запис зберігається для читання/скасування, але його дати й кількість не можна переписати. У реєстраційній формі використано чинний `listRights`; без права, завантажених даних або за суперечливого року реєстрація блокується. У «Зведенні» доступність показується лише за підтвердженого поточного права; історичне використання видиме, `unknown` та `no_right` не породжують нормативного залишку. Нових таблиць/API немає.

Документація: [архітектурна специфікація](LEAVE-BALANCE-AUTOMATION-DESIGN.md), [архітектура](ARCHITECTURE.md), [рішення](DECISIONS.md), [UI transfer](UI-TRANSFER.md), [HromadaAID reuse](HROMADAAID_REUSE.md). Додано read-only `leave:getPeriodAttention(throughDate)`: Main в одному deferred snapshot рахує актуальні періоди для всіх наявних працівників і повертає періоди підтвердження, нейтральні перевірки даних та агрегати працівників/періодів. Нагадування не зберігаються. Основна відпустка показує 30 днів лише для поточного `confirmed_entitlement` періоду; початковий `initial_balance` потребує ручного внесення без вигаданого числа. Майбутні періоди пропускаються. Для ОМС потрібне підтверджене право й надійна позитивна рекомендація ServiceProjection; невідоме право/недостатні дані показуються без числа. Початковий залишок спрямовує до ручного внесення, явне `no_right` не створює завдання.

У вкладці «Відпустки» перед незміненою таблицею «Зведення» з’являється компактний список завдань поточного працівника й агрегат по установі. Перехід веде до відповідного типу в «Залишках» і автоматично відкриває редактор із фокусом на потрібному періоді; перевірка права веде до розділу «Права». Після зміни прав/періодів дані перечитуються. Схема SQLite, підтверджені дні, FIFO та реєстрації не змінювалися.

У моделі працівника немає статусу звільнення/дати завершення; усі записи, що існують у `employees`, вважаються активними (видалені працівники вже відсутні). Окремого глобального центра нагадувань і GUI-приймання немає. Дані оновлюються при відкритті вкладки та після змін; постійне опитування й системні сповіщення не використовуються.

## Етап 9.12.8 – Спрощення додаткової відпустки на дітей

Для нового календарного періоду `children_social_additional` використовується річний рядок `leave_period_balances` без окремої таблиці або сімейної анкети. У `BalanceEditor` кадровик вибирає 10 або 17 к. дн. окремо для кожного року; порожній вибір не створює днів, а для нового `confirmed_entitlement` Main вимагає поточне підтверджене право та одне зі значень 10/17. Підтверджені нетипові значення залишаються видимими й редагованими, зміна права їх не видаляє. `initial_balance` лишається фактичним ручним залишком без підстановки 10/17.

Похідний контроль 9.12.7 розширено на дитячу відпустку: лише поточний календарний рік, `no_right` не створює завдання, невідоме право просить перевірку, підтверджене право веде до вибору тривалості для нового entitlement або до ручного початкового залишку до межі електронного обліку. Вибір права за поточний рік не створює задач для минулих років. Збереження/використання й далі спираються на чинні періоди, allocations та FIFO; SQLite, міграції й реєстрація не змінювалися. GUI-приймання не проводилося.
