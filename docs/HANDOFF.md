# Передавання контексту HromadaHR

## Поточний стан

Працюйте лише в `Anatol1ch/HromadaHR`. Етапи 2.1, 2.2 та 2.4 реалізовано; 2.3 остаточно скасовано замовником. База етапу 2.4 — `44255054c12d9d09d6d30255afd4c28b68571d7e`, гілка `main`, перед початком робоче дерево було чистим. Фактичний HEAD/стан завжди перевіряйте Git-командами. Версія застосунку залишається 0.1.0; до кадрової експлуатації ще не готовий.

Авторизація, реєстрація, логіни/паролі, акаунти, сеанси, ролі/RBAC, розмежування функцій, відновлення пароля, шифрування SQLite/копій та спеціальні NTFS ACL не реалізуються й не плануються. Усі функції доступні після запуску без входу; стандартні дозволи Windows програмно не змінюються. Технічні IPC-перевірки залишаються обов'язковими.

## Реалізовано

- Незалежний Electron 44.7.1 / React / TypeScript / Vite / pnpm, сім українських розділів і власна бузково-фіолетова дизайн-система. HromadaAID не змінювався. `reference/` — локальні матеріали, не змінювати й не додавати в Git; ресурс герба — `assets/community-coat.png`.
- Main: `contextIsolation=true`, `nodeIntegration=false`, `sandbox=true`, заборона навігації/redirect/webview/сторонніх вікон та дозволів. Обмежений contextBridge, sender/WebContents/mainFrame/URL, Zod для аргументів/відповідей і контрольовані коди помилок.
- SQLite better-sqlite3 13.0.3 (Node-API prebuild), Zod 4.6.7; нових залежностей на 2.4 не додано. Windows x64 native load та online backup перевірено в справжньому Electron Main. ARM64/пакування не перевірялися.
- БД built: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`; dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`. Корінь — системний LOCALAPPDATA, режим — чинний `!app.isPackaged && --dev`, без NODE_ENV. Незалежні Electron-профілі залишаються в `%APPDATA%`. `start:built` використовує продукційну БД, тому не є командою руйнівних тестів.
- WAL, foreign_keys=ON, busy_timeout=5000, synchronous=FULL. Readonly integrity_check/FK/ledger до змін, перевірка після міграцій. Пошкоджена/невідома/недоступна БД не замінюється порожньою.
- Міграція 1/schema_migrations не змінена. Нова міграція 2 додає тільки backup_config і backup_state. Конфігурація/результати атомарні, namespace UUID відділяє копії цієї БД від інших профілів. Немає local_account, app_settings або кадрових таблиць.
- У налаштуваннях: дві теки через Main/system dialog, показ шляхів/доступності/результатів, ручна копія та двоетапне відновлення. Канонічні Windows-шляхи з junction/case/trailing separators: однакові/вкладені або перетин із data-каталогом заборонені; перевіряється запис. Один том — попередження, не блокування. Довільні каталоги за шляхом із renderer не створюються.
- Автоматичний цикл після обох тек: при запуску/збереженні та кожні 15 хвилин тільки у відкритому застосунку. Успіх фіксується окремо для кожної теки за локальну добу. До чотирьох спроб на теку/добу, повтор не раніше ніж через 15 хвилин; успішна тека не дублюється. Ручна копія не змінює добові маркери/ліміти. Mutex відхиляє паралельні операції; вихід очікує завершення поточної.
- Online snapshot у .partial, нормалізація закритого знімка в standalone DELETE journal mode, integrity/FK/schema/fsync, atomic hardlink publication без перезапису. Файлова система цілі має підтримувати hardlink (перевірено NTFS); інакше контрольована помилка. У копії вся SQLite, без Electron-профілю, без пароля/шифрування.
- Ротація залишає 14 останніх перевірених auto-копій власного namespace з перевіреним instance_id. Ручні/захисні/чужі/пошкоджені файли не видаляються.
- Restore: перевірка формату/версії/цілісності, власний staged snapshot, одноразовий токен 5 хвилин, окремий IPC і native confirmation із cancel за замовчуванням. Шлях джерела/confirmed-прапорець не приймаються. Перед заміною — перевірений protect-restore у data/protection, checkpoint/close, перевірка відсутності WAL/SHM, журнал перед rename. Reopen/міграції/цілісність, потім commit видаленням журналу. Помилка повертає стару БД, startup повертає її після незавершеного журналу; невдача повернення => RECOVERY_REQUIRED. Джерело й protective snapshot збережені. Після успіху поточні теки/namespace залишаються, історія/auto-маркери очищені, renderer перезавантажується.
- `requiresBackup` інтегровано в асинхронний startup-координатор. Перед критичним SQL — перевірений snapshot у data/protection; його невдача блокує міграцію. SQL-помилка не видаляє копію. На звичайному старті без критичних pending-міграцій зайвих копій немає.

## Файли

`electron/main.ts`, `electron/ipc.ts`, `electron/preload.cts`; `electron/storage/{index,migrations,errors,validation}.ts`; `electron/backup/{files,service,recovery,controller}.ts`; `shared/{ipc,backup}.ts`; `src/App.tsx`, `src/components/BackupSettings.tsx`, `src/styles/components.css`; `tests/{ipc,storage,backup}.test.mjs`, `tests/electron-storage-smoke.cjs`, `tests/run-electron-storage.mjs`. Деталі — в ARCHITECTURE та DECISIONS.

Main скомпільовано в `dist-electron/electron/main.js`; preload — один CommonJS `dist-electron/preload.cjs`, shared — `dist-electron/shared/`. Після змін Main/preload перезапускайте dev; start:built не перебудовує dist. Старий відкритий single-instance може показувати старий інтерфейс.

IPC: system.getInfo, storage.getStatus та backup.{getStatus,chooseFolder,saveConfig,runManual,chooseRestore,confirmRestore}. Лише обрані/збережені backup-теки повертаються як шляхи для інтерфейсу; активний шлях SQLite, довільні файлові дії, SQL та generic invoke не відкриті. Вибір тек підтверджується токенами на 10 хвилин; навігація/знищення вікна інвалідує невикористаний вибір.

## Перевірки та обмеження

Етап 2.4: `pnpm typecheck`, `pnpm test` (46/46 + реальний Electron Main online-backup smoke), `pnpm build`, `git diff --check` — успішно. Тести використовують тільки mkdtemp, зокрема для Electron userData/session/logs/crashDumps. Реальні APPDATA/LOCALAPPDATA профілі не відкривалися. GUI-тести не створювалися, GUI-приймання не виконувалося. React-перевірка: окремий компонент, type-only контракти, cleanup таймерів, pending/in-flight guard, disabled controls, семантичні кнопки/Alert, наявні design tokens.

Синхронні integrity/SQL/ротація блокують Main; великим базам знадобиться вимірювання. Таймер не працює після закриття застосунку. Ручні/захисні копії зберігаються без автоматичного ліміту; після жорсткого переривання можливі залишкові власні staging/partial/rejected файли для технічного прибирання. Між публікацією та записом успіху аварія може спричинити зайву безпечну копію при повторі. Журнал захищає від перевірених процесних збоїв, але не гарантує відновлення після фізичної відмови носія чи довільного пошкодження ФС. Для restore потрібна справна поточна БД і можливість захисної копії; автоматичний ремонт пошкодженої активної БД не реалізовано.

Кадрові функції, відпустки, стаж/ранги, документообіг, сервер/хмара, автооновлення, інсталятор і реліз не реалізовані. Не переходьте далі без окремого завдання.

## Ручне приймання (не позначати виконаним без перевірки)

- [ ] Dev і built запускаються/закриваються/повторно відкриваються, мають незалежні профілі й конфігурацію. Не підміняйте справжню built-БД для тестів.
- [ ] Сім розділів, breadcrumbs, герб, бузково-фіолетовий дизайн, Tab/Enter/видимий фокус, вузьке вікно й масштаби Windows збережені.
- [ ] Дві теки: системний picker/cancel, зміна/збереження/перезапуск, шляхи/доступність. Однакові/вкладені/data-теки відхиляються; один том дає попередження.
- [ ] Після налаштування створено auto-копії в обох теках. Від'єднання одного тестового носія дає часткову помилку без блокування; пізніше повторюється лише невдала тека в межах ліміту.
- [ ] Ручне резервування: виконання/блокування повторного кліку, результати окремо для обох тек, auto-день не змінено. Ручні копії не ротуються.
- [ ] Відновлення перевіряти тільки в ізольованому тестовому Windows-профілі: вибір справної/пошкодженої/новішої копії, попередження, cancel за замовчуванням, явний native confirm, protective snapshot, перезавантаження UI без старих даних.
- [ ] Немає екранів входу, паролів, ролей, шифрування або змін ACL. IPC не має generic invoke/SQL/файлового менеджера.
