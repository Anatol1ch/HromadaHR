# Передавання контексту HromadaHR

## Поточний стан

Працюйте лише в `Anatol1ch/HromadaHR`. Етапи 3.1 та 3.2 реалізовано: предметна основа, реєстр, створення/редагування персональних відомостей і особові картки. Етап 3.3 не розпочато. База змін 3.2 — `6b07dbfbbfa3695c82b4ddf397ed44f6f776548c`, `main`, дерево перед роботою чисте. База змін 3.1 — `7bfab57c2d5af2fc0a19f4478055dde2442fe8db`, `main`, до першого запиту дерево було чистим; уточнення 3.1 застосовано поверх власних незакомічених змін цього чату. Етапи 2.1, 2.2, 2.4 та виправлення 2.4.1 реалізовано; 2.3 остаточно скасовано замовником. База змін 2.4.1 — `cfe1f404d11a3b31f0b70f3370a476cc2b7640a5`, гілка `main`, перед початком робоче дерево було чистим. Фактичний HEAD/стан завжди перевіряйте Git-командами. Версія застосунку залишається 0.1.0; до кадрової експлуатації ще не готовий.

Авторизація, реєстрація, логіни/паролі, акаунти, сеанси, ролі/RBAC, розмежування функцій, відновлення пароля, шифрування SQLite/копій та спеціальні NTFS ACL не реалізуються й не плануються. Усі функції доступні після запуску без входу; стандартні дозволи Windows програмно не змінюються. Технічні IPC-перевірки залишаються обов'язковими.

## Реалізовано

- Незалежний Electron 44.7.1 / React / TypeScript / Vite / pnpm, сім українських розділів і власна бузково-фіолетова дизайн-система. HromadaAID не змінювався. `reference/` — локальні матеріали, не змінювати й не додавати в Git; ресурс герба — `assets/community-coat.png`.
- Main: `contextIsolation=true`, `nodeIntegration=false`, `sandbox=true`, заборона навігації/redirect/webview/сторонніх вікон та дозволів. Обмежений contextBridge, sender/WebContents/mainFrame/URL, Zod для аргументів/відповідей і контрольовані коди помилок.
- SQLite better-sqlite3 13.0.3 (Node-API prebuild), Zod 4.6.7; на 2.4.1 додано лише koffi 3.3.6 для фіксованих Win32-викликів (Node-API optional prebuild; build script вимкнено). Windows x64 native load та online backup перевірено в справжньому Electron Main. ARM64/пакування не перевірялися.
- БД built: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`; dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`. Корінь — системний LOCALAPPDATA, режим — чинний `!app.isPackaged && --dev`, без NODE_ENV. Незалежні Electron-профілі залишаються в `%APPDATA%`. `start:built` використовує продукційну БД, тому не є командою руйнівних тестів.
- WAL, foreign_keys=ON, busy_timeout=5000, synchronous=FULL. Readonly integrity_check/FK/ledger до змін, перевірка після міграцій. Пошкоджена/невідома/недоступна БД не замінюється порожньою.
- Міграція 1/schema_migrations не змінена. Нова міграція 2 додає тільки backup_config і backup_state. Конфігурація/результати атомарні, namespace UUID відділяє копії цієї БД від інших профілів. Немає local_account або app_settings; кадрові таблиці додано окремою міграцією 3.
- У налаштуваннях: дві теки через Main/system dialog, показ шляхів/доступності/результатів, ручна копія та двоетапне відновлення. Канонічні Windows-шляхи з junction/case/trailing separators: однакові/вкладені або перетин із data-каталогом заборонені; перевіряється запис. Один том — попередження, не блокування. Довільні каталоги за шляхом із renderer не створюються.
- Автоматичний цикл після обох тек: при запуску/збереженні та кожні 15 хвилин тільки у відкритому застосунку. Успіх фіксується окремо для кожної теки за локальну добу. До чотирьох спроб на теку/добу, повтор не раніше ніж через 15 хвилин; успішна тека не дублюється. Ручна копія не змінює добові маркери/ліміти. Mutex відхиляє паралельні операції; вихід очікує завершення поточної.
- Online snapshot у .partial, нормалізація закритого знімка в standalone DELETE journal mode, integrity/FK/schema/fsync, публікація одним MoveFileExW у тій самій теці, WRITE_THROUGH без REPLACE_EXISTING/COPY_ALLOWED. Hardlinks не використовуються; колізія не перезаписує файл, невдача прибирає власний partial. Перевірено NTFS; фізичного exFAT-носія для приймання немає. У копії вся SQLite, без Electron-профілю, без пароля/шифрування.
- Ротація залишає 14 останніх перевірених auto-копій власного namespace з перевіреним instance_id. Ручні/захисні/чужі/пошкоджені файли не видаляються.
- Restore: перевірка формату/версії/цілісності, власний staged snapshot, одноразовий токен 5 хвилин, окремий IPC і native confirmation із cancel за замовчуванням. Шлях джерела/confirmed-прапорець не приймаються. Перед заміною — перевірений protect-restore у data/protection, checkpoint/close, перевірка відсутності WAL/SHM, журнал перед rename. Reopen/міграції/цілісність, потім commit видаленням журналу. Помилка повертає стару БД, startup повертає її після незавершеного журналу; невдача повернення => RECOVERY_REQUIRED. Джерело й protective snapshot збережені. Після успіху поточні теки/namespace залишаються, історія/auto-маркери очищені, renderer перезавантажується.
- `requiresBackup` інтегровано в асинхронний startup-координатор. Перед критичним SQL — перевірений snapshot у data/protection; його невдача блокує міграцію. SQL-помилка не видаляє копію. На звичайному старті без критичних pending-міграцій зайвих копій немає.

## Етап 3.1 — працівники

- Реалізовано уточнене завдання 3.1: employees (last_name/first_name обов’язкові, middle_name/birth_date/note nullable, employee_type=official|staff), departments, positions, employee_positions. Категорія nullable належить призначенню. Дати YYYY-MM-DD (0001–9999), Zod + SQL CHECK. UUID генерує Main.
- Міграція 3/personnel_foundation має requiresBackup=true: чинний координатор зберігає перевірений pre-v3 snapshot перед SQL. Помилка копії блокує міграцію. Міграції 1–2/назви/SQL/checksum незмінні; тест фіксує оригінальні хеші. Незакомічений попередній варіант 3.1 замінено до публікації; його temp-БД не підтримуються, checksum mismatch автоматично не переписується.
- employee_positions — єдине джерело дати прийняття (перша start_date), поточного призначення (остання start_date) та підрозділу. Немає end_date й дублюючих полів у employees. Поточне призначення — останній запис, включно з майбутньою датою; не відбір за сьогодні. UNIQUE(employee_id,start_date), FK CASCADE для працівника та RESTRICT для довідників; індекси FK. Немає таблиць наступних модулів.
- Довідники мають технічний name_key UNIQUE: Unicode NFC, згортання пробілів, toUpperCase().toLowerCase(), повторний NFC. Нормалізована назва зберігає регістр. Конфлікти українського регістру, пробілів, складених символів та Straße/STRASSE перевірено; це не транслітерація й не пошук схожих літер.
- Main-only PersonnelService і window.hromadaHR.personnel: дев’ять методів listEmployees/getEmployee/createEmployee/updateEmployee/getHistory, listDepartments/createDepartment, listPositions/createPosition. Створення працівника + першого призначення атомарне. updateEmployee змінює лише персональні відомості. ПІБ до 200, примітка до 4000; nullable поля явно null. createEmployee додатково приймає positionId, departmentId, category, startDate. Картка повертає обчислені hireDate/currentAssignment із довідниками.
- Strict Zod аргументів/відповідей, sender/frame/URL, IpcResult та контрольовані NOT_FOUND/CONFLICT/STORAGE_UNAVAILABLE/BUSY. Довільного SQL/FS API немає. Сервіс бере актуальне з’єднання після restore й блокується під час backup/restore.
- Видалення працівника, наступні призначення та виправлення історії не відкриті в IPC й сервісі: це 3.3. Редагування/видалення довідників також не додано. Каскад і можливість додати історію перевірено тільки прямим SQL тестових fixture.
- Нові файли: shared/personnel.ts; electron/personnel/{schemas,service}.ts; electron/storage/personnel-migration.ts; tests/personnel.test.mjs. Розширено чинні Main/preload/IPC та цільові тести. src/env.d.ts успадковує HromadaHRApi без змін. Залежності, storage/backup/recovery runtime й React не змінено.
- Перевірки: pnpm typecheck; цільові personnel+IPC тести 26/26; pnpm test 76/76 + справжній Electron Main smoke; pnpm build; git diff --check. Лише ізольовані mkdtemp-бази/профілі. Продукційні дані не відкривалися; GUI-приймання не виконувалося.
- На 3.2 ці дев’ять методів підключено до UI (див. нижче). Схема, сервіси й IPC залишилися без змін; дії 3.3 не додано.

## Етап 3.2 — реєстр та особові картки

- Замість заглушки «Працівники» реалізовано реєстр: кількість, створення, пошук по всіх частинах ПІБ незалежно від регістру/порядку слів із Unicode NFC, фільтр поточного підрозділу, сортування ПІБ через Intl.Collator('uk'), таблиця та стани loading/error/empty/no-results. Для ~30 записів усе на клієнті після listEmployees, без пагінації/нових залежностей.
- EmployeesWorkspace керує локальними представленнями registry/create/card/edit. Пошук, підрозділ та порядок сортування зберігаються при переході до картки/форми й назад, поки відкритий розділ. Після повернення реєстр перечитується; пізні відповіді покинутого екрана ігноруються. Немає localStorage, незалежного кадрового сховища чи фіктивних даних.
- EmployeeForm: усі поля початкового створення, nullable по батькові/народження/примітка/категорія, два типи official/staff з українськими назвами, календарні дати 0001–9999 і межі 200/4000 відповідно до Main. Редагування надсилає лише шість персональних полів; посада/підрозділ/категорія/прийняття тільки для читання. Створення відкриває картку, успіх показано Alert; дані форми залишаються при помилках, повторні запити блокуються ref-guard + disabled.
- Швидке створення посади/підрозділу в тій самій формі: нормалізація назви як у Main, після успіху запис додається до переліку та вибирається. CONFLICT не створює дубль, оновлює перелік для вибору наявного запису. Є пояснення до дії й повідомлення про те, що довідник зберігається одразу навіть після скасування працівника.
- Картка завантажує getEmployee/getHistory та обидва довідники паралельно. Загальна інформація повна; інші три вкладки — компактний planned-state без розрахунків. Назви історії зіставляються з довідниками за ID; порядок зворотний, завершення попереднього інтервалу обчислюється тільки для показу як день перед наступним початком. Поточне призначення залишається останнім за чинним контрактом 3.1, включно з майбутнім початком.
- Збережено сім розділів, оболонку й палітру. Додано breadcrumbs реєстр/картка/форма, повернення, фокус заголовка та помилкового поля, labels/aria-invalid, семантичну таблицю, клавіатуру вкладок (стрілки/Home/End), видимий focus, адаптивні сітки й горизонтальне прокручування таблиці. App і локальні кнопки перевіряють guard незбереженої форми через confirmation; beforeunload також перевіряє його. Під час запису вихід блокується. Поведінку нативного закриття/масштабування слід прийняти вручну.
- Нові файли: src/components/employees/{EmployeesWorkspace,EmployeeRegistry,EmployeeForm,EmployeeCard}.tsx; src/employees/model.ts; src/styles/employees.css; tests/employees-ui.test.mjs. Змінено App/styles imports і фактичні тексти головної. Міграції 1–3, їхні checksum, electron/shared API та backup/restore, залежності не змінені.
- Перевірки: pnpm typecheck, pnpm test (82/82 та Electron Main smoke), pnpm build, git diff --check. Шість нових цільових тестів: український пошук/сортування, фільтрація, дати історії, відповідність клієнтської валідації Main Zod, персональний update payload та Unicode-назви. React-review за react-best-practices: окремі компоненти, type-only контракти, parallel reads, cleanup/late-response guards, pending refs, доступна семантика й чинні tokens. GUI snapshot/кліки/прокручування не автоматизувалися; GUI вручну не приймався. Продукційна БД не відкривалася.
- Для 3.3: поточні контракти не дозволяють видалення працівника, наступні призначення та виправлення історії. Перед реалізацією погодити UX підтвердження видалення, правила корекції дат/історії та можливих майбутніх зв’язків. Реєстр/картка мають перечитувати авторитетні дані після таких операцій. Наразі цих дій немає; 3.3 не розпочато.

### Ручне приймання 3.2 — ще не виконано

Використовуйте лише тестові дані в ізольованому профілі; start:built відкриває продукційну БД.

- [ ] Порожній реєстр → створення працівника з мінімальними та повними відомостями → картка; перевірити обидва типи, nullable поля та повідомлення про успіх.
- [ ] Пошук українським регістром/частинами ПІБ/переставленими словами, фільтр підрозділу, сортування, відсутність результатів, скидання. Відкрити картку й повернутися: запит/фільтр/порядок збережені.
- [ ] Додати посаду й підрозділ із форми, перевірити автоматичний вибір і збереження всіх полів. Повторити назву зі зміненим регістром/пробілами → CONFLICT. Скасувати працівника: нові довідники залишилися.
- [ ] Перевірити обов’язкові поля, довжини, календарні дати та народження після прийняття. Помилка збереження не очищує форму; повторне натискання під час очікування не дублює запит.
- [ ] Відредагувати персональні відомості → оновлена картка й реєстр; кадрові поля незмінні. Перевірити назви/дати історії та три planned-вкладки без удаваних даних.
- [ ] Змінити форму й натиснути «Скасувати», breadcrumbs, інший розділ або закриття вікна: перевірити підтвердження/відмову. Пройти Tab/Shift+Tab/Enter, стрілки/Home/End вкладок; перевірити focus, вузьке вікно й масштаби Windows 125–200%.

## Аварійне відновлення 2.4.1

- До ready App показує екран із причиною/кодом, вибором копії (лише CORRUPT/UNSUPPORTED_SCHEMA/MISSING_DATABASE), повторною перевіркою й закриттям. BUSY/FILESYSTEM не трактуються як пошкодження; довільних шляхів через IPC немає. Сім розділів залишаються недоступними до готовності SQLite.
- Успішне відкриття записує storage-{hash шляху}.initialized у корені HromadaHR[-dev]; відома зникла БД більше не створюється. Retry ніколи не створює файл. Старі інсталяції до першого запуску 2.4.1 ще не мають маркера: відсутність і БД, і маркера не відрізняється від нової інсталяції.
- Picker → заголовок/integrity/FK/ledger/checksum → власний online staging → токен → native confirm → окремий перевірений incoming. Джерело не змінюється й не мігрується.
- Усі наявні DB/-wal/-shm/-journal ексклюзивно відкриваються через CreateFileW share=0. Інший відкритий файл блокує процедуру. ReadFile зберігає точні байти в data/protection/raw-UUID; manifest містить розмір/SHA-256. Це діагностичний набір, не гарантовано справна SQLite. Якщо збереження неможливе, заміни немає. Handles утримуються до перейменування оригіналів через SetFileInformationByHandle без перезапису.
- Чинний restore-journal розширено v2/raw; sync журналу передує заміні. Кандидат відкривається/мігрується/перевіряється; успіх видаляє журнал і перезавантажує UI. Raw/previous збережені поза ротацією. Конфігурація резервування береться з копії — перевірте її після аварійного restore.
- Помилка або перерваний процес: startup перевіряє raw-хеші, зберігає кандидата/rejected і повертає початковий набір через rollback-файли та ексклюзивні handles. Незмінний raw дозволяє повторити перерване повернення. Пошкоджений оригінал після rollback лишається на recovery-екрані; невдача повернення => RECOVERY_REQUIRED із журналом. Діагностичні файли автоматично не видаляйте.

## Перевірки та обмеження

Етап 2.4.1: `pnpm typecheck`, `pnpm test` (63/63 + реальний Electron Main online-backup/emergency-restore smoke), `pnpm build`, `git diff --check` — успішно. Тести використовують тільки mkdtemp, зокрема для Electron userData/session/logs/crashDumps. Реальні APPDATA/LOCALAPPDATA профілі не відкривалися. GUI-тести не створювалися, GUI-приймання не виконувалося. React-перевірка: окремий компонент, type-only контракти, cleanup таймерів, pending/in-flight guard, disabled controls, семантичні кнопки/Alert, наявні design tokens.

Синхронні integrity/SQL/ротація блокують Main; великим базам знадобиться вимірювання. Таймер не працює після закриття застосунку. Ручні/захисні копії зберігаються без автоматичного ліміту; після жорсткого переривання можливі залишкові власні staging/partial/rejected файли для технічного прибирання. Між публікацією та записом успіху аварія може спричинити зайву безпечну копію при повторі. Журнал захищає від перевірених процесних збоїв, але не гарантує відновлення після фізичної відмови носія чи довільного пошкодження ФС. Штатне відновлення справної БД збережено; аварійний сценарій описано нижче. Автоматичного ремонту немає.

Переведення, зміна історії/видалення працівника, відпустки, стаж/ранги, документообіг, сервер/хмара, автооновлення, інсталятор і реліз не реалізовані. Не переходьте далі без окремого завдання.

## Ручне приймання (не позначати виконаним без перевірки)

- [ ] Dev і built запускаються/закриваються/повторно відкриваються, мають незалежні профілі й конфігурацію. Не підміняйте справжню built-БД для тестів.
- [ ] Сім розділів, breadcrumbs, герб, бузково-фіолетовий дизайн, Tab/Enter/видимий фокус, вузьке вікно й масштаби Windows збережені.
- [ ] Дві теки: системний picker/cancel, зміна/збереження/перезапуск, шляхи/доступність. Однакові/вкладені/data-теки відхиляються; один том дає попередження.
- [ ] Після налаштування створено auto-копії в обох теках. Від'єднання одного тестового носія дає часткову помилку без блокування; пізніше повторюється лише невдала тека в межах ліміту.
- [ ] Ручне резервування: виконання/блокування повторного кліку, результати окремо для обох тек, auto-день не змінено. Ручні копії не ротуються.
- [ ] Відновлення перевіряти тільки в ізольованому тестовому Windows-профілі: вибір справної/пошкодженої/новішої копії, попередження, cancel за замовчуванням, явний native confirm, protective snapshot, перезавантаження UI без старих даних.
- [ ] Немає екранів входу, паролів, ролей, шифрування або змін ACL. IPC не має generic invoke/SQL/файлового менеджера.
