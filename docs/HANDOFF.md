## Реалізовано

- Незалежний Electron 44.7.1 / React / TypeScript / Vite / pnpm, сім українських розділів і дизайн-система HromadaAID з власною сиренево-фіолетовою палітрою HR (остаточне уточнення 3.4.2.1; зелений бренд 3.4.1 скасовано). HromadaAID не змінювався. `reference/` — локальні матеріали, не змінювати й не додавати в Git; ресурс герба — `assets/community-coat.png`.
- Main: `contextIsolation=true`, `nodeIntegration=false`, `sandbox=true`, заборона навігації/redirect/webview/сторонніх вікон та дозволів. Обмежений contextBridge, sender/WebContents/mainFrame/URL, Zod для аргументів/відповідей і контрольовані коди помилок.
- SQLite better-sqlite3 13.0.3 (Node-API prebuild), Zod 4.6.7; на 2.4.1 додано лише koffi 3.3.6 для фіксованих Win32-викликів (Node-API optional prebuild; build script вимкнено). Windows x64 native load та online backup перевірено в справжньому Electron Main. ARM64/пакування не перевірялися.
- БД built: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`; dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`. Корінь — системний LOCALAPPDATA, режим — чинний `!app.isPackaged && --dev`, без NODE_ENV. Незалежні Electron-профілі залишаються в `%APPDATA%`. `start:built` використовує продукційну БД, тому не є командою руйнівних тестів.
- WAL, foreign_keys=ON, busy_timeout=5000, synchronous=FULL. Readonly integrity_check/FK/ledger до змін, перевірка після міграцій. Пошкоджена/невідома/недоступна БД не замінюється порожньою.
- Міграція 1/schema_migrations не змінена. Нова міграція 2 додає тільки backup_config і backup_state. Конфігурація/результати атомарні, namespace UUID відділяє копії цієї БД від інших профілів. Немає local_account або app_settings; кадрові таблиці додано окремою міграцією 3.
- У налаштуваннях: дві теки через Main/system dialog, показ шляхів/доступності/результатів, ручна копія та двоетапне відновлення. Канонічні Windows-шляхи з junction/case/trailing separators: однакові/вкладені або перетин із data-каталогом заборонені; перевіряється запис. Один том — попередження, не блокування. Довільні каталоги за шляхом із renderer не створюються.
- Автоматичний цикл після обох тек: при запуску/збереженні та кожні 15 хвилин тільки у відкритому застосунку. Успіх фіксується окремо для кожної теки за локальну добу. До чотирьох спроб на теку/добу, повтор не раніше ніж через 15 хвилин; успішна тека не дублюється. Ручна копія не змінює добові маркери/ліміти. Mutex відхиляє паралельні операції; вихід очікує завершення поточної.
- Online snapshot у .partial, нормалізація закритого знімка в standalone DELETE journal mode, integrity/FK/schema/fsync, публікація одним MoveFileExW у тій самій теці, WRITE_THROUGH без REPLACE_EXISTING/COPY_ALLOWED. Hardlinks не використовуються; колізія не перезаписує файл, невдача прибирає власний partial. Перевірено NTFS; фізичного exFAT-носія для приймання немає. У копії вся SQLite, без Electron-профілю, без пароля/шифрування.
- Ротація залишає 14 останніх перевірених auto-копій власного namespace з перевіреним instance_id. Ручні/захисні/чужі/пошкоджені файли не видаляються.
- Restore: перевірка формату/версії/цілісності, власний staged snapshot, одноразовий токен 5 хвилин, окремий IPC і native confirmation із cancel за замовчуванням. Шлях джерела/confirmed-прапорець не приймаються. Перед заміною — перевірений protect-restore у data/protection, checkpoint/close, перевірка відсутності WAL/SHM, журнал перед rename. Reopen/міграції/цілісність, потім commit видаленням журналу. Помилка повертає стару БД, startup повертає її після незавершеного журналу; невдача повернення => RECOVERY_REQUIRED. Джерело й protective snapshot збережені. Після успіху поточні теки/namespace залишаються, історія/auto-маркери очищені, renderer перезавантажується.
- `requiresBackup` інтегровано в асинхронний startup-координатор. Перед критичним SQL — перевірений snapshot у data/protection; його невдача блокує міграцію. SQL-помилка не видаляє копію. На звичайному старті без критичних pending-міграцій зайвих копій немає.

## Етап 3.1 — працівники

- Реалізовано уточнене завдання 3.1: employees (last_name/first_name обов’язкові, middle_name/birth_date/note nullable, employee_type=official|staff), departments, positions, employee_positions. Категорія nullable належить призначенню. Дати YYYY-MM-DD (0001–9999), Zod + SQL CHECK. UUID генерує Main.
- Міграція 3/personnel_foundation має requiresBackup=true: чинний координатор зберігає перевірений pre-v3 snapshot перед SQL. Помилка копії блокує міграцію. Міграції 1–2/назви/SQL/checksum незмінні; тест фіксує оригінальні хеші. Незакомічений попередній варіант 3.1 замінено до публікації; його temp-БД не підтримуються, checksum mismatch автоматично не переписується.
- employee_positions — єдине джерело дати прийняття (перша start_date), поточного призначення (остання start_date) та підрозділу. Немає end_date й дублюючих полів у employees. Поточне призначення — останній запис, включно з майбутньою датою; не відбір за сьогодні. UNIQUE(employee_id,start_date), FK CASCADE для працівника та RESTRICT для довідників; індекси FK. Немає таблиць наступних модулів.
- Довідники мають технічний name_key UNIQUE: Unicode NFC, згортання пробілів, toUpperCase().toLowerCase(), повторний NFC. Нормалізована назва зберігає регістр. Конфлікти українського регістру, пробілів, складених символів та Straße/STRASSE перевірено; це не транслітерація й не пошук схожих літер.
- Main-only PersonnelService і window.hromadaHR.personnel: дев’ять методів listEmployees/getEmployee/createEmployee/updateEmployee/getHistory, listDepartments/createDepartment, listPositions/createPosition. Створення працівника + першого призначення атомарне. updateEmployee змінює лише персональні відомості. ПІБ до 200, примітка до 4000; nullable поля явно null. createEmployee додатково приймає positionId, departmentId, category, startDate. Картка повертає обчислені hireDate/currentAssignment із довідниками.
- Strict Zod аргументів/відповідей, sender/frame/URL, IpcResult та контрольовані NOT_FOUND/CONFLICT/STORAGE_UNAVAILABLE/BUSY. Довільного SQL/FS API немає. Сервіс бере актуальне з’єднання після restore й блокується під час backup/restore.
- На 3.1 видалення працівника, наступні призначення та виправлення історії ще не були відкриті; їх додано на 3.3 (нижче). Редагування/видалення довідників також не додано. Каскад і можливість додати історію перевірено тільки прямим SQL тестових fixture.
- Нові файли: shared/personnel.ts; electron/personnel/{schemas,service}.ts; electron/storage/personnel-migration.ts; tests/personnel.test.mjs. Розширено чинні Main/preload/IPC та цільові тести. src/env.d.ts успадковує HromadaHRApi без змін. Залежності, storage/backup/recovery runtime й React не змінено.
- Перевірки: pnpm typecheck; цільові personnel+IPC тести 26/26; pnpm test 76/76 + справжній Electron Main smoke; pnpm build; git diff --check. Лише ізольовані mkdtemp-бази/профілі. Продукційні дані не відкривалися; GUI-приймання не виконувалося.
- На 3.2 ці дев’ять методів підключено до UI (див. нижче). Схема, сервіси й IPC залишилися без змін; дії 3.3 не додано.

### Ручне приймання 3.2 — ще не виконано

Використовуйте лише тестові дані в ізольованому профілі; start:built відкриває продукційну БД.

- [ ] Порожній реєстр → створення працівника з мінімальними та повними відомостями → картка; перевірити обидва типи, nullable поля та повідомлення про успіх.

- [ ] Додати посаду й підрозділ із форми, перевірити автоматичний вибір і збереження всіх полів. Повторити назву зі зміненим регістром/пробілами → CONFLICT. Скасувати працівника: нові довідники залишилися.

- [ ] Змінити форму й натиснути «Скасувати», breadcrumbs, інший розділ або закриття вікна: перевірити підтвердження/відмову. Пройти Tab/Shift+Tab/Enter, стрілки/Home/End вкладок; перевірити focus, вузьке вікно й масштаби Windows 125–200%.

## Етап 3.3 — кадрові зміни та видалення

- Додано чотири явні PersonnelService/IPC/preload методи: createAssignment(employeeId,input), updateAssignment(assignmentId,input), deleteAssignment(assignmentId), deleteEmployee(employeeId). Разом 13 кадрових методів. AssignmentInput: departmentId, positionId, category nullable, startDate. Перші три повертають актуальну EmployeeCard; повне видалення — null. Strict Zod аргументів/відповідей, sender/mainFrame/URL та IpcResult збережено.
- Усі мутації — IMMEDIATE-транзакції під чинним guard backup/restore. Перевіряються існування працівника/довідників, реальні дати, унікальність початку, народження <= початок, відсутність майбутніх дат і однакових сусідніх станів (positionId/departmentId/category). Категорія порівнюється точно після чинного trim; нормативної класифікації/зміни регістру не додано.
- Після INSERT/UPDATE/DELETE перевіряється вся хронологія; помилка відкочує операцію. Вставлення заднім числом перевіряє обох сусідів. Виправлення першої дати та перенесення запису в іншу позицію хронології дозволені. Видалення проміжного запису, яке залишає дубльованих сусідів, відхиляється. Єдиний запис історії видалити не можна; видалення найновішого при наявності інших дозволене.
