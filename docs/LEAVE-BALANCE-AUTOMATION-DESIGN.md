# Проєкт автоматизації обліку залишків відпусток

**Статус:** технічний проєкт для погодження; функціональні зміни не розпочаті.
**Стан коду для аналізу:** HromadaHR SQLite v24, гілка етапу 9.12.4.5.
**Межа:** документ не є юридичним висновком і не затверджує застосовність конкретної норми до працівника.

## 1. Поточний стан

### Типи та дані

`shared/leave.ts` поділяє шість видів на три періодні (`annual_main`, `oms_service_additional`, `children_social_additional`) і три подієві (`study_leave`, `veteran_special_leave`, `chernobyl_special_leave`).

SQLite v24 зберігає:

- `employee_leave_rights`: по одному поточному `has_right`/`no_right` на вид та timestamp перевірки. Запис не містить категорії пільги, документа-підстави, періоду її чинності чи історії змін. Відсутність рядка в API представляється UI як `unknown`.
- `leave_period_balances`: підтверджені періоди трьох періодних видів, `confirmed_days`, `used_days` через активні списання, `available_days` як різниця та `accounting_basis`. Унікальність — працівник/вид/початок періоду. Старі `initial_balance` обмежені датою до 2027 року; `confirmed_entitlement` — датою від 2027 року. `reference_entitlement_days` дозволене лише для початкового балансу, тому не є полем належної тривалості підтверджених нових періодів.
- `leave_records` та `leave_allocations`: реєстрації всіх шести типів; записи мають `active`/`cancelled`, календарні дати, `used_days`, revision і підставу. Періодні списання прив'язані до `leave_period_balances`; подієві записи списань періодів не мають.

### Поточний потік

`proposePeriods` повертає незбережені пропозиції. Для основної щорічної відпустки `shared/leave-periods.ts` формує робочі роки від дати прийняття; для додаткової за стаж ОМС — інтервали від окремо збереженої дати набуття права. Пропозиції не створюють підтверджених днів. У `BalanceEditor` кадровик вносить/підтверджує тривалість; рекомендація ОМС є окремою явною дією, що повторно перевіряє projection перед підстановкою.

`proposeAllocation` рахує доступні дні з підтверджених балансів, для яких період почався не пізніше початку відпустки, і застосовує FIFO за найстарішим періодом. Main повторно перевіряє кожне списання в транзакції. SQL-тригери забороняють перевищити підтверджені дні, зменшити використаний період або видалити період із прив'язаним списанням.

Скасування змінює статус запису, але зберігає його та алокації для історії. `getBalances` підсумовує алокації лише активних записів, тому скасування повертає доступні дні рівно один раз. Редагування перевіряє revision, у транзакції замінює алокації та повторно валідує весь запис. Для спеціальних подієвих відпусток чинні `specialLeaveLimit`/SQLite обмежують суму, а часткове значення потребує пояснення; частковий унікальний індекс дозволяє не більш як одну активну реєстрацію кожного виду за роком її `start_date`.

`annualUsage` також відносить подієве використання до року початку запису. Це чинна технічна конвенція, а не підтверджене правило розподілу запису, що перетинає 31 грудня. Реєстрація подієвої відпустки не використовує балансний FIFO і просить текстову підставу. `LeaveRights` зберігає загальний статус, але не доводить конкретну категорію УБД/ЧАЕС чи сімейну підставу. `saveRights` не переписує періоди або реєстрації.

IPC типізований і проходить через preload/Main із Zod; окремих API для категоріальної підстави, пропозиції річного спеціального балансу або розподілу подієвої реєстрації за entitlement-year поки немає.

### UI

`LeaveBalances` працює з трьома періодними типами та чинним редактором періодів. `LeaveRights` редагує шість загальних статусів. `LeaveRegistrationForm` викликає серверну пропозицію FIFO для періодних типів; для подієвих перевіряє дні через `specialLeaveLimit`, показує записи за роком початку й відкидає скасовані під час підрахунку. У цих екранах немає окремого підтвердження законодавчої категорії УБД/ЧАЕС або автоматичного річного grant.

Цільово звірено попередньо перевірений read-only HromadaAID snapshot SHA `33eca10733caaf73b1a99e75a24ff35e706a0afb` (`src/RecipientRegistry.tsx`, `src/App.tsx`, `src/styles.css` та задокументований пошук leave-workbench). Аналога кадрового річного entitlement/FIFO для відпусток у перевірених джерелах не виявлено. Код і дані AID не переносилися; основа проєкту — чинні транзакції, періоди, allocation-тригери та UI HromadaHR.

## 2. Цільові правила за видом

Усі числа в цьому документі є **параметрами, запропонованими замовником для перевірки**, а не автоматично чинними нормами. Перед розробкою потрібно затвердити таблицю «вид/категорія працівника/місце роботи/період/підстава/дні/перенесення/поділ/фінансування/дата дії» з кадровим фахівцем або юристом. Зберігати версію правил і дату перевірки; зміна закону не повинна непомітно перераховувати збережені підтвердження.

### УБД та інші законодавчі категорії

- Цільова гіпотеза етапу — 14 календарних днів на календарний рік після явного підтвердження відповідної законодавчої категорії.
- Не створювати entitlement з `employee_leave_rights.has_right` самого по собі. Потрібні окремий типізований код підтвердженої категорії, дата/рік застосовності та мінімальне посилання на документ-підставу; копії посвідчень і зайві персональні відомості в HR-схему не переносити.
- Після категоріального підтвердження Main може показати пропозицію на поточний календарний рік. Кадровик явно підтверджує річну кількість. За відсутності права/доказу нові дні не пропонуються як доступні.
- Для автоматичного залишку використовувати окремий bucket поточного календарного року. Минулі роки не додаються. Використання обчислюється лише з активних реєстрацій, явно зіставлених із bucket цього року.
- Не встановлювати без перевірки можливість поділу на кілька реєстрацій, часткове надання, перенесення, компенсацію чи місце роботи. Поточний унікальний індекс «один активний запис за роком start_date» не вважати достатньою юридичною моделлю.

### ЧАЕС

- Цільова гіпотеза — 16 календарних днів за відповідного підтвердженого статусу/категорії; загальне `has_right` не достатнє.
- Офіційні роз'яснення Пенсійного фонду називають, зокрема, категорії 1 і 2 та окрему сімейну підставу, пов'язану з інвалідністю дитини внаслідок ЧАЕС. Вони також описують фінансування та обмеження на перенесення/поділ. Точний перелік і процедура мають бути повторно звірені з чинною редакцією закону та застосовністю до конкретного роботодавця до реалізації.
- Кадровик вибирає підтверджений тип підстави й реквізит посвідчення/документа, а система не виводить категорію з інших полів працівника.
- Річний bucket не переносить невикористані дні минулих років. Кількість використання — лише активні записи, пов'язані з підтвердженим entitlement року.
- Не дозволяти автоматично розщепити одну реєстрацію між роками. За переходу через 31 грудня потрібне окремо затверджене правило або контрольований ручний розгляд; це особливо важливо, якщо відпустка має надаватися неподільно.
- Окремо вирішити, чи належить HR-системі тільки облік наказу/днів, чи також вести процес заяви-розрахунку/відшкодування з держбюджету. Цей етап такого фінансового процесу не додає.

### Додаткова відпустка на дітей

- Модель року вже є: `children_social_additional` пропонується як 01.01–31.12, а фактична тривалість підтверджується в `BalanceEditor`.
- Запропонований робочий сценарій: кадровик для конкретного календарного року підтверджує підставу та обирає перевірену тривалість 10 або 17 календарних днів. Автоматично перевіряти сімейні обставини, родинні зв'язки, вік/інвалідність дітей чи кількість підстав не потрібно.
- `confirmedDays` лишається єдиним підтвердженим джерелом днів; підказане/розрахункове значення відокремлюється від нього до явного збереження. Нестандартний розмір вимагає ручного підтвердження та короткої причини/посилання на документ.
- Невикористаний залишок зберігати у своєму річному періоді. Не підсумовувати/не списувати його без перевірки строку використання й актуальних перехідних правил. Після правового затвердження можливий FIFO за найстарішим доступним роком: чинний `leave_allocations` уже зберігає точний розподіл, а не тільки загальну суму.
- Підстава/кількість підстав має бути мінімальною структурованою кадровою міткою для пояснення 10/17; не записувати подробиці про дітей у довільний текст, якщо цього не вимагає затверджений процес.

### Щорічна основна та додаткова за стаж ОМС

- Періоди пропонує чинний `proposePeriods`: для основної відпустки — календарні робочі роки від прийняття; для ОМС — інтервали від вручну підтвердженої дати набуття права та чинної projection.
- Зберегти модель «пропозиція → явне підтвердження кадровиком». Жодні дні не стають доступними лише від появи року, дати або розрахункового прогнозу.
- Окремо показувати пропозицію, підтверджену тривалість, списане й доступне; не підміняти підтвердження автоматичною нормативною тривалістю. Для ОМС явна підстановка рекомендації лишається редагованою чернеткою.
- Підсвічувати пропущені/непідтверджені періоди як нагадування у робочій області й у картці працівника. Початковий варіант — детермінований список із наявних `proposePeriods`, без OS notifications, фонових таймерів або нової системи нагадувань.
- Дозволяти кадровику підтвердити винятковий розмір, явно позначивши його як ручне рішення з поясненням. Не зараховувати прогнозні/непідтверджені дні до FIFO.

## 3. Запропонована модель даних та API

Це варіант для окремого погодження, не зміна v24 у цьому коміті.

### Періодні види

Зберегти `leave_period_balances` як авторитетне підтвердження для основної, ОМС і дитячої відпусток. Додати окреме поле `suggested_days` або read-only пропозицію в DTO, якщо значення потрібно показувати до підтвердження; не записувати його в `confirmed_days`. Для дитячої моделі окремо узгодити мінімальний `basis_code`/`manual_reason` у річному підтвердженні. Не використовувати `reference_entitlement_days` для нових підтверджених періодів: чинний CHECK саме це забороняє.

### Річні спеціальні види

Додати additive v25 таблиці після погодження:

1. `leave_eligibility_confirmations`: employee, leave type, затверджений `basis_code`, період чинності, тип/номер/дата документа як мінімальні реквізити, статус і revision. Для кожного типу — allowlist кодів після юридичної перевірки. Загальний `employee_leave_rights` лишається коротким поточним статусом, не замінюючи доказ категорії.
2. `leave_annual_entitlements`: employee, type, calendar year, посилання на eligibility confirmation, rule version, запропоновані дні, підтверджені дні (nullable до підтвердження), статус `review_required/proposed/confirmed/not_applicable`, revision і timestamps; унікальність employee/type/year. Не створювати confirmed row за автоматичною підстановкою.
3. `leave_annual_allocations`: зв'язок реєстрації з entitlement-year і кількістю днів; унікальність зв'язку, обмеження суми активних allocations на підтверджений bucket тригером/транзакційною перевіркою. Скасовані записи/зв'язки зберігати для аудиту, але вони не витрачають дні.

Не перебудовувати `leave_allocations` на поліморфну таблицю без окремого обґрунтування. Періодні FIFO й річні спеціальні bucket мають різні правила eligibility та перенесення; спільною лишається транзакційна гарантія «не списати більше підтвердженого».

### Main/IPC

Можливі типізовані операції:

- `listLeaveEligibility` / `saveLeaveEligibility` — лише явне внесення/коригування кадрової підстави з expected revision.
- `proposeAnnualEntitlement(employeeId, type, year)` — read-only пропозиція з перевіреною rule version, категоріальною підставою й вже зареєстрованим використанням.
- `confirmAnnualEntitlement(input, expectedRevision)` — окрема транзакція підтвердження/ручного винятку.
- `proposeAnnualAllocation(...)` — показ доступного bucket; Main повторно перевіряє дату, рік і залишок під час register/update.

Усі нові контракти мають Zod input/output schemas, sender validation та preload methods. Жодне renderer-значення `suggestedDays` не вважається підтвердженим без Main перевірки. Повторення requestId не створює подвійного списання.

## 4. Розрахунок і цілісність

### Річне entitlement

Для УБД/ЧАЕС розрахунок отримує лише кадрово підтверджені коди категорії і перевірену за рік версію правила. Без них результат — `review_required`, без кількості доступних днів. Після підтвердження кадровиком `available = confirmedDays − sum(active allocations)` тільки для того entitlement-year, без додавання попередніх років.

Для дитячої/основної/ОМС логіка періодів зберігається у `leave_period_balances`; `availableDays = confirmedDays − sum(active allocations)` як зараз. Пропозиції без підтвердження не включаються у доступні FIFO-періоди.

### Реєстрація, межі років та списання

- Для period leave зберегти явний allocation за періодами й поточне обмеження списання лише з bucket, придатних на дату початку, поки окремо не погоджено інше.
- Для подієвих річних entitlement не відносити всі дні мовчки до року `start_date`. До затвердження юридичного правила: запит, що перетинає 31 грудня, блокується з повідомленням або передається на ручну перевірку.
- Якщо правова норма дозволяє розподіл між роками, UI вимагає явний per-year allocation; сума allocation має дорівнювати `usedDays`. Якщо норма вимагає неподільну відпустку — один entitlement year покриває весь запис, а дата/межа валідується відповідно до затвердженого правила.
- На `cancelLeave` status стає cancelled, allocations лишаються для аудиту й перестають рахуватися активними. Повторне скасування ідемпотентне. Canceled leave не відновлюється; нове надання — новий запис після перевірки річного права.
- `updateLeave` в одній транзакції змінює записи й алокації з revision guard, повторно валідуючи новий тип, рік та суму. Будь-яка помилка rollback-ить і запис, і розподіл.
- Перед реєстрацією/редагуванням Main перевіряє entitlement/status, річний залишок, дати, overlap, потрібну підставу та revision. Не покладатися на disabled-кнопку у Renderer.

### Права, виключення та сповіщення

- `no_right` або відсутній загальний статус блокує автоматичну пропозицію нових днів. Збережені підтвердження й записи не видаляються й автоматично не анулюються при зміні статусу.
- `has_right` є необхідним сигналом для загального UI, але для УБД/ЧАЕС додатково потрібне окреме категоріальне підтвердження. При суперечності UI просить перевірку, а не робить висновок.
- Зміна підстави не перераховує вже підтверджене та не видаляє використання. Кадровик явно позначає майбутній entitlement для перегляду; правове рішення щодо попередніх років залишається ручним.
- Ручними лишаються нестандартна тривалість, категорія без однозначного коду, перетин року, кілька/змінені сімейні підстави, історичні записи без доказу, розбіжні довідки й фінансове відшкодування ЧАЕС.
- Нагадування на першій ітерації — похідне повідомлення про конкретну непідтверджену пропозицію. Воно не змінює право/дні і не надсилає зовнішніх сповіщень.

## 5. Міграція без втрати та подвійного обліку

1. До v25 створити перевірену резервну копію; старі міграції не редагувати. Нова міграція лише additive, `requiresBackup`, із `foreign_key_check` та rollback-тестом.
2. Поточні підтверджені періоди й `leave_allocations` лишити незмінними. Дитячі календарні періоди зберегти як є, включно з нулями та початковими балансами. Не дублювати їх у новій таблиці спеціальних entitlement.
3. `employee_leave_rights.has_right` не backfill-ити у категоріальну eligibility. Вона потребує явного кадрового перегляду.
4. Усі старі `leave_records`, включно зі скасованими, ідентифікатори, revisions, document links та алокації залишити незмінними. Нові sidecar-таблиці спочатку не створюють entitlement із цих записів.
5. Для старих активних подієвих записів підготувати список reconciliation. Рік `start_date` показати лише як запропоноване зіставлення, не підтверджувати автоматично. Поки кадровик не призначив використані дні до entitlement-year або явно не позначив невідповідність, доступний річний залишок не показувати як повний і не дозволяти повторне автоматичне нарахування.
6. Для записів через 31 грудня чи з `usedDays`, що не дорівнює календарній довжині, не обчислювати розподіл евристично. Потрібне ручне зіставлення з reason та документом.
7. Після reconciliation перевірити: кількість/суми старих записів до/після, суми allocations, canceled історію, документальні зв'язки, відсутність entitlement-дублів і SQLite foreign keys. До успішної перевірки лишати legacy reader доступним і мати recovery через резервну копію.

## 6. Поетапна реалізація та критерії приймання

| Фаза | Зміст | Критерій приймання |
|---|---|---|
| 0. Правове затвердження | Матриця категорій/днів/календарного року/перенесення/поділу/фінансування/підстав та дати дії для чотирьох моделей | Підписані кадровиком правила; невизначені винятки лишаються ручними; жодної норми не виводять із загального `has_right`. |
| 1. Модель і міграція | Additive v25 для категоріальної підстави, річного спеціального entitlement і його allocations | v24 backup/migration round-trip без втрат; старі дані не backfill-яться як підтверджені без доказу; constraints забороняють дубль і overdraw. |
| 2. Main/IPC | Read-only proposal, explicit confirm, entitlement-year allocation, transaction/revision/idempotency | Renderer не може підтвердити довільне число; одночасні/повторні submit, cancel/edit/rollback залишають цілісні суми. |
| 3. UI | Стани «підстава не внесена», «перевірити», «пропозиція», «підтверджено», «використано», «залишок» у Rights/Balances/Registration | Немає вигаданого нуля; загальний статус відрізняється від категорії; ручний виняток має пояснення; navigation/dirty/focus збережені. |
| 4. Звірка й rollout | Reconciliation старих спеціальних реєстрацій та контроль операційних річних звітів | Підсумки збігаються до/після; за відсутності доказу — тільки review; GUI/кадрове приймання пройдене окремо. |

Цільові тести: eligibility відсутня/підтверджена/закрита; `has_right` без категорії; 14/16/10/17 лише як погоджені параметри; current-year only для УБД/ЧАЕС; збереження child carry-over за затвердженим строком; непідтверджений period не потрапляє у FIFO; відпустка через межу року; split sum; одночасні/повторні save; edit, cancel і rollback; заборона списати понад bucket; migration v24 data preservation, FK/trigger і restore. Нормативні параметри мають власні тест-кейси за версією правила.

## 7. Юридичні перевірки до реалізації

Первинні джерела для обов'язкового повторного перегляду в день затвердження: [Закон «Про відпустки» №504/96-ВР](https://zakon.rada.gov.ua/go/504/96-%D0%B2%D1%80), [Закон №3551-XII про статус ветеранів війни](https://zakon.rada.gov.ua/go/3551-12), [Закон №796-XII про статус постраждалих від ЧАЕС](https://zakon.rada.gov.ua/go/796-12), [Закон №2493-III про службу в органах місцевого самоврядування](https://zakon.rada.gov.ua/go/2493-14), [Закон №3077-IX](https://zakon.rada.gov.ua/go/3077-20) та [постанова КМУ №229](https://zakon.rada.gov.ua/go/229-2016-%D0%BF). Перевіряти редакцію, дату набрання чинності й перехідні положення; Закон №3077-IX має відкладений початок дії, а стан актуальності змінюється.

Для виявлення обмежень ЧАЕС під час цього проєктування переглянуті офіційні матеріали [Пенсійного фонду про право/категорії](https://www.pfu.gov.ua/cv/420284-chornobylska-vidpustka-i-hto-maye-na-neyi-pravo/) та [порядок надання і фінансування](https://www.pfu.gov.ua/mk/169286-sotsialni-vyplaty-ta-dodatkova-vidpustka-osobam-postrazhdalym-vnaslidok-chornobylskoyi-katastrofy-poryadok-pryznachennya-ta-finansuvannya/). Це вказує, що модель 16 днів може мати окремі категоріальні, процедурні й фінансові умови; вона не дорівнює загальному статусу `has_right`. Матеріали не замінюють юридичного затвердження всієї матриці.

Перед реалізацією ще потрібно погодити: точний перелік статусів УБД та інших осіб для 14 днів; категорії та процедури ЧАЕС; допустимість поділу/межі року; зв'язок між загальним `LeaveRights` та спеціальною доказовою підставою; нормативний алгоритм 10/17 і строки перенесення дитячого залишку; правила ручних винятків; чи входить фінансування ЧАЕС до системи; формат і строк нагадувань. До цього рішення параметри не можна перетворювати на автоматичні юридичні висновки.
