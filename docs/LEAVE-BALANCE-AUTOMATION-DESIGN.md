# Специфікація автоматичного обліку залишків відпусток

**Статус:** напрям B уточнено до специфікації проєктування; це не дозвіл на SQLite v25, API або функціональну реалізацію.
**Зріз коду:** SQLite v24, контрольний стан codex/9.12.5-leave-automation-architecture (b19154e26da2e6d846b5b9f5412b6312dd912e78).
**Перевірка офіційних джерел:** 25.11.2026. Нормативні висновки попередні та не замінюють юридичного погодження застосовності до установи.
**Вихідна умова:** цільова робоча база порожня. Звірка старих спеціальних реєстрацій, UI-міграція тестових записів і підтримка legacy тестових даних не потрібні. Для розвитку схеми використовувати штатну послідовність версійних міграцій із резервним копіюванням.

> Це єдина актуальна специфікація напрямку B. Початковий варіант із трьома новими таблицями відхилено, він не лишається конкурентним планом. Невирішені юридичні питання нижче є передумовою реалізації.

## 1. Принципи та фактична база

HromadaHR — локальна кадрова система невеликої установи. Модель має прибрати повторні пошуки й введення, але не перетворювати пропозицію на підтверджене право. Право/підстава, рекомендовані дні, підтверджені дні, використання та доступність — різні стани.

У shared/leave.ts шість видів поділено на три періодні (annual_main, oms_service_additional, children_social_additional) і три подієві (study_leave, veteran_special_leave, chernobyl_special_leave). SQLite v24 уже містить:

- employee_leave_rights: загальний поточний has_right/no_right для виду, без коду категорії, документа-підстави, строку дії чи історії річних перевірок.
- leave_period_balances: підтверджені періоди та confirmed_days; використання пов'язане через leave_allocations; залишок є похідним. Є обмеження унікальності та перекриття періодів.
- leave_records: активні/скасовані реєстрації шести видів, реквізити документа, revision і підстава. Періодні записи мають allocations; подієві — ні.
- Подієве використання групується за роком start_date; часткове подієве значення допускається з поясненням, індекс обмежує один активний запис працівника/типу/року початку.

proposePeriods уже створює незбережені пропозиції робочих періодів: основна — від дати прийняття, ОМС — від підтвердженої дати набуття права з повторним використанням service projection. LeaveService транзакційно перевіряє періодні allocations; FIFO та SQL-тригери є чинним захистом балансу. Скасування зберігає історичний запис, але неактивні allocations більше не списують доступні дні.

У v24 немає річних категоріальних підтверджень УБД/ЧАЕС. Цільова база порожня, тому немає потреби переносити тестові special records у нову модель.

## 2. Мінімальна модель даних — напрям B

### 2.1 Не створювати окремі таблиці періодів або allocations

Чинні leave_period_balances і leave_allocations залишаються джерелом підтверджених днів та їх використання для основної, ОМС і дитячої відпусток. Таблиця leave_annual_entitlements дублювала б period row, який уже містить вид, інтервал і confirmed_days. Для річних special rights не потрібні leave_annual_allocations: річна доступність споживається однією подією, а факт використання вже міститься у leave_records.

### 2.2 Одна таблиця річної перевірки спеціального права

Запропонована leave_special_year_rights зберігає підтвердження на працівника, вид і календарний рік; вона не зберігає 14/16 як редагований баланс.

Мінімальні поля:

| Поле | Призначення й обмеження |
|---|---|
| employee_id | FK на працівника |
| leave_type | CHECK allowlist лише veteran_special_leave або chernobyl_special_leave |
| calendar_year | INTEGER у затвердженому діапазоні років |
| basis_code | Не-null allowlist категорій після юридичного затвердження |
| eligibility_status | CHECK eligible / not_eligible; відсутність рядка означає «ще не перевірено» |
| basis_document_id | Необов'язковий FK на наявний документ працівника, якщо його зв'язок відповідає вимогам доказу |
| other_employer_use | unknown / yes / no лише для типів, де підтверджено обмеження одним роботодавцем; для інших — NULL |
| checked_at | Час кадрового підтвердження |
| revision | Позитивна версія для захисту від застарілого оновлення |

Первинний/унікальний ключ: employee_id + leave_type + calendar_year. Додатково індекс employee_id + calendar_year для огляду року. CHECK-обмеження узгоджують типи, enum і рік; FK використовує чинні правила цілісності. basis_code перевіряється серверним allowlist. Не зберігати копії посвідчень або надлишкові персональні подробиці.

Якщо право не підтверджено, рядок необов'язковий: відсутність означає unknown; негативний результат записується лише після кадрової перевірки. На наступний рік basis_code і документ можна запропонувати як чернетку, але підтвердження має бути новим.

### 2.3 Мінімальні відомості для дитячої відпустки

Використати наявний календарний період children_social_additional, confirmed_days та allocations. До period row пропонується додати тільки структурований маркер перевірених підстав (single_basis / multiple_bases / manual_exception) і дату річної перевірки; за потреби — посилання на чинний кадровий документ. Не зберігати дані дітей або подробиці сімейних обставин.

confirmed_days лишається єдиною підтвердженою кількістю. Стандартна пропозиція — 10 днів для однієї підстави та до 17 за кількох підтверджених підстав; виняток потребує ручного коригування й обґрунтування. Конкретні коди підстав та правило переходу 10→17 затверджуються до розробки.

### 2.4 Основна відпустка — єдиний інституційний стандарт

Не створювати таблицю нормативних налаштувань. Для кожного нового робочого періоду система автоматично пропонує 30 календарних днів усім працівникам установи відповідно до затвердженої умови проєкту. Це єдиний інституційний default, не автоматична класифікація посади й не твердження, що закон установлює 30 днів кожному працівникові.

Для посадових осіб ОМС 30 днів передбачені спеціальним законом. Для решти персоналу 30 днів — стандарт роботодавця, який має бути закріплений належним локальним актом/умовами праці. Індивідуальна більша тривалість та винятки лишаються ручними. Пропозиція не створює period row і не збільшує підтверджений залишок.

## 3. Правила обчислення для шести видів

### 3.1 Щорічна основна

1. Чинний proposePeriods визначає робочий рік від дати прийняття і повертає відсутні періоди.
2. Для нового періоду suggestedDays = 30. Немає вибору 24/30 за посадою чи окремої конфігураційної таблиці.
3. Кадровик перевіряє інтервал, застосовність локальної умови, можливий індивідуальний виняток і підтверджує або змінює число.
4. Тільки явне збереження створює confirmed_days. Майбутній рік або зміна графіка не переписують попередній період.

### 3.2 Додаткова за стаж ОМС

1. Періоди й рекомендацію обчислювати тільки чинними генератором періодів та ServiceProjection; алгоритм стажу не дублювати.
2. Зміна projection, дата початку права або відсутність наступного інтервалу створює пропозицію, а не підтверджені дні.
3. Відсутні/нові інтервали знаходити автоматично під час запуску готового застосунку, відкриття профілю та оновлення відомостей працівника. Нагадування — похідний список proposals; не додавати daemon, фоновий таймер чи нову конфігурацію.
4. Підстановка рекомендації лишається явною дією та повторно перевіряє projection перед збереженням.

### 3.3 Додаткова на дітей

1. Щороку формується пропозиція календарного періоду. Попередній рік може заповнити чернетку типом підстави й реквізитами документа, але не підтверджує нове право.
2. Кадровик щороку підтверджує актуальність підстави, визначає кількість підстав та перевіряє залежні від року умови, зокрема використання іншим із батьків, якщо застосовно.
3. Програма пропонує 10 або 17 згідно з погодженою матрицею; кадровик зберігає або коригує. Сімейні обставини автоматично не аналізуються.
4. Попередні періоди й allocations зберігаються. Зміна поточного права не видаляє підтверджені дні. Чинний FIFO застосовується лише до періодів, підтверджених як доступні до використання; правила строку/умов використання старих періодів треба затвердити.
5. Щороку повторно підтверджуються фактичні умови права, кількість підстав, умовний критерій щодо іншого з батьків та актуальність доказу. З попереднього року пропонуються лише код підстави й документ, не їх актуальність як факт.

### 3.4 УБД та інші ветеранські категорії

1. Річна доступність виникає лише після eligible для затвердженого basis_code; employee_leave_rights.has_right недостатньо.
2. Після підтвердження показувати 14 к.дн. як доступну спеціальну подію; активна допустима реєстрація позначає її використаною. Не трактувати як накопичуваний баланс чи 14 мінус довільна частина.
3. Скасування/редагування перевіряються транзакційно. Скасування повертає доступність того самого року лише якщо право ще можна реалізувати за погодженим правилом; історичний запис і документ зберігаються.
4. Наступний рік потребує нової перевірки; завершена минулорічна подія не зменшує новорічну доступність.
5. Держпраці підтверджує 14 днів для названих законом категорій та право незалежно від основного місця/сумісництва. Отже не вводити блокування за іншим роботодавцем без окремого юридичного висновку. Невирішено: чи річна одиниця права — особа, трудові відносини або кожне місце роботи.
6. Чинний індекс за роком start_date сам не доводить допустимість часткової, повторної чи перехідної події. Повна тривалість та межі запису вимагають погодження; до нього не автоматизувати такі випадки.

### 3.5 Чорнобильська

1. Показувати річну доступність лише після підтвердження конкретної категорії/підстави та річної перевірки.
2. ПФУ вказує 16 календарних днів для категорій і умов із закону, основне місце роботи, одну реалізацію за рік, без поділу/перенесення/накопичення; перехідна відпустка належить року початку. За цією офіційною позицією UI показує двійкову доступність однієї події, а не баланс 16 мінус довільно використані дні.
3. Кадровик щороку перевіряє категорію, доказ, основне місце й факт відсутності використання в іншого роботодавця; попередні реквізити можна повторно запропонувати.
4. Активна подія відноситься до року дати початку. Вона споживає це річне право цілком і не створює списання з наступного року. Наступного року потрібна нова перевірка.
5. Якщо подію скасовано, доступність повертається тільки після перевірки, що право ще може бути реалізоване в тому році та ПФУ-процедурі; повторне надання не має відбуватися мовчки.
6. Фінансування/компенсація витрат ПФУ — поза автоматизованим балансом; обов'язки кадровика/бухгалтерії треба погодити.

### 3.6 Навчальна

Залишається подієвою. Тривалість і підстава підтверджуються для кожної реєстрації. Немає річного накопичення чи залишку; у зведенні — лише активне фактичне використання. Скасовані записи не рахуються.

## 4. Підтвердження нового календарного року

Для УБД/ЧАЕС програма формує review task/чернетку і попередньо підставляє минулорічні basis_code, документ і сталі реквізити. Новий рядок не вважається підтвердженим автоматично. Кадровик перевіряє чинність статусу, новий рік і відповідні умови (для ЧАЕС — основне місце та використання в іншого роботодавця; для УБД — тільки умови, визначені юридичним висновком). Після перевірки створюється/оновлюється один запис працівник/вид/рік.

Для дитячої відпустки можна повторно запропонувати тип підстави та документ; щорічно підтвердити конкретні умови, кількість підстав і за потреби стан іншого з батьків. Для annual main автоматично з'являються нові робочі періоди з 30-денною пропозицією; для ОМС періоди — з чинного projection. Жодне нагадування не записує дні чи право.

## 5. Активні реєстрації та межі року

Цільова база порожня, тому інтерфейс звірки старих реєстрацій не створюється. Стандартна версійна міграція не переписує чинні ID, документи, статуси або аудит.

- Активний special record відповідного entitlement-year споживає річну подію і блокує дубль навіть за відсутності підтвердження; відсутність підтвердження не стирає запис.
- Завершений минулорічний запис не зменшує нового права; 14/16 не переносяться.
- Cross-year Chornobyl record повністю відноситься до року початку за офіційним роз'ясненням ПФУ.
- Cross-year UBD не отримує автоматичного правила за аналогією. До правового висновку такий випадок переводиться на кадрову перевірку і не дає права на другий запис/списання наступного року.
- Дитячі періоди зберігаються окремо за роками, allocations прив'язані до періоду. Якщо не можна однозначно підтвердити законність використання старого залишку, система не показує його як безумовно доступний і не списує автоматично.

## 6. API та транзакційні гарантії (пропозиція, не контракт)

Поточні period/record APIs залишаються. Нові методи можливі лише після окремого погодження v25:

- listSpecialYearRights(employeeId, year) — підтвердження та стан використання з активних leave records.
- proposeSpecialYearRight(employeeId, type, year) — read-only чернетка з пропозицією попередньої підстави/документа.
- saveSpecialYearRight(input, expectedRevision) — явне кадрове підтвердження з перевіркою allowlist, типу/року/документа й revision.
- Чинні register/update/cancel серверно перевіряють річний статус, тривалість і відсутність активної події; Renderer не визначає доступність.

Main перевіряє транзакційно (BEGIN IMMEDIATE), повторно читає право і запис, перевіряє request idempotency/revision та обмеження річної події. Унікальний ключ права (employee_id, leave_type, calendar_year) захищає від дубльованого підтвердження. Active-record unique index лишається лише для тих типів, де юридично підтверджено одну подію. Збереження права, реєстрація, зміна та cancel не можуть утворити конкурентне подвійне використання. Повторний cancel/stale update відхиляється; cancel лишає аудит.

Для періодних видів лишаються Main allocation proposals, FIFO та SQL-тригери. 30-денна пропозиція, service projection і дитячі 10/17 ніколи не змінюють confirmed_days без явного збереження.

## 7. Точні стани «Зведення»

| Вид | «Облік днів» | «Залишок» |
|---|---|---|
| Щорічна основна | Підтверджені / використані за робочими періодами. До підтвердження: «30 днів запропоновано» або «Період не підтверджено» | Підтверджені доступні дні; proposal не є залишком |
| Додаткова за стаж ОМС | Підтверджені / використані; service recommendation окремо як пропозиція | Лише з підтверджених періодів; невідоме не є нулем |
| Додаткова на дітей | Підтверджені / використані за роками; 10/17 чітко маркується пропозицією до підтвердження | Тільки підтверджені доступні allocations; неперевірене перенесення не включати як безумовне |
| УБД | Річний стан та одна подія: 14 к.дн. доступно / використано | Не баланс накопичення; binary цього року, без підтвердження — «Право не перевірено» |
| ЧАЕС | Річний стан та одна подія: 16 к.дн. доступно / використано | Binary цього року, start-year, без carry; неперевірене право не показує число |
| Навчальна | Фактично використано за активними реєстраціями | «—» — показник незастосовний |

Для всіх видів «Потрібна перевірка» відрізняється від нуля та від «Права немає». Підтверджене історичне використання лишається видимим після зміни права; cancelled записи не рахуються.

## 10. Невирішені питання

1. Локальний акт про 30 днів для всіх: форма, затвердження, дата чинності; застосування до працівників, не охоплених спеціальним статусом; індивідуальні умови та воєнні обмеження.
2. Чинність і перехід від Закону №2493-III до №3077-IX на дату реалізації та для конкретних посад.
3. УБД: точні категорії; чи обмежена щорічна гарантія особою, місцем роботи чи трудовими відносинами; сумісництво; перехід року; часткове надання; можливість повернення доступності після скасування.
4. ЧАЕС: повний перелік статусів і доказів; вимоги основного місця роботи; звітність/фінансування ПФУ; наслідки скасування після подання документів.
5. Дитяча: перелік підстав, 10/17 і доказування, річні умови, перенесення невикористаних періодів та зміна роботодавця.
6. ОМС: дата права/період за перехідного законодавства й випадки, коли ServiceProjection не достатній.
7. Для тимчасового невирішеного випадку система не створює доступність, не перетворює unknown на 0 і переводить операцію на кадрову перевірку.

## 11. Фактична реалізація етапу 9.12.6

- Для нових канонічних періодів `annual_main` із `confirmed_entitlement` read-only `proposePeriods` додає `suggestedDays: 30`. Періоди `initial_balance`, зокрема ті, що перетинають межу 01.01.2027, не отримують цю пропозицію.
- `BalanceEditor` показує 30 у редагованій чернетці та позначає значення як непідтверджене. Для ОМС редактор автоматично підставляє лише достовірну рекомендацію чинного `ServiceProjection` у порожні придатні рядки. Значення редагується; окремого кроку підтвердження рекомендації немає.
- Порожні або незмінені рекомендації не створюють запису. Тільки явне «Зберегти» викликає чинний `savePeriods`. Підтверджені періоди й початкові залишки не переписуються.
- DTO пропозиції містить опційний `suggestedDays`; SQLite, версія схеми, API збереження, FIFO, allocations та річні права не змінені.
- Для дітей, УБД і ЧАЕС на цьому етапі не додано пропозицій, таблиць, API чи UI. Їхні майбутні рішення та юридичні питання в цьому документі залишаються проєктними.

## Фактичне уточнення після етапу 9.12.8

Дитячий періодний облік реалізовано без запланованих у початковому проєкті child metadata: програма не зберігає категорії підстав, реквізити посвідчень чи відомості про дітей. `leave_period_balances.confirmed_days` лишається єдиним підтвердженим числом. Для нового календарного періоду з `confirmed_entitlement` кадровик явно вибирає 10 або 17 днів у Select цього року; Main повторно перевіряє `has_right` і допустимість 10/17 під час транзакції збереження. Зміна права не поширюється на минулі роки. `initial_balance` не отримує такої пропозиції та приймає тільки ручний фактичний залишок. Уже підтверджені нетипові значення не замінюються і можуть коригуватися за чинними обмеженнями використання.

Поточний `getPeriodAttention` включає дитячу відпустку лише для календарного року дати запиту: за `unknown` просить перевірити право, за `has_right` просить обрати 10/17 для нового entitlement або вручну внести початковий залишок до межі електронного обліку, за `no_right` не створює нове завдання. Тривалість не обирається автоматично; жодні дні не записуються до явного збереження. Це фактичне спрощене рішення етапу 9.12.8 замінює ранішу проєктну пропозицію з child metadata для майбутньої реалізації. УБД/ЧАЕС і правові межі застосовності стандартів цим етапом не змінюються.
