# Фактична архітектура HromadaHR

Документ описує версію 0.1.0 після етапу 2.2 (SQLite та міграції). Погоджені майбутні механізми наведено окремо в [DECISIONS.md](DECISIONS.md).

## Стек та структура

Цільова платформа — Windows 10/11, локальний настільний застосунок без окремого сервера. Середовище розробки: Node.js 24.22.1, pnpm 11.25.0. Використано Electron 44.7.1, React/React DOM 19.2.9, TypeScript 5.9.3, Vite 8.3.4, @vitejs/plugin-react 6.1.2 та lucide-react 0.577.0. Фактичні версії залежностей зафіксовано в `package.json` і `pnpm-lock.yaml`.

Це один пакет, без серверного workspace. `pnpm-workspace.yaml` дозволяє build-скрипти Electron та явно вимикає компіляцію better-sqlite3 13: пакет містить готові Node-API бінарники. Кореневий `postinstall` викликає штатний `install-electron`, щоб підготувати бінарний Electron під час встановлення залежностей. Runtime-залежність SQLite — better-sqlite3 13.0.3, типи — @types/better-sqlite3 9.6.0; ORM немає. Вибір і вимоги пакування — у DECISIONS.

## Electron та межа безпеки

Ідентичність: package `hromada-hr`, product HromadaHR, версія 0.1.0. Main задає назву HromadaHR та Windows AppUserModelId `local.hromadahr`. Створюється звичайне вікно 1000 × 700 без власного меню.

BrowserWindow використовує `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; стандартна web security не вимикається. Main блокує навігацію та перенаправлення через `will-navigate`/`will-redirect`, приєднання webview і створення сторонніх вікон. Запити дозволів відхиляються.

Ланцюжок виклику: React Renderer → явний метод `window.hromadaHR` → preload/contextBridge → IPC → Main. Дозволено лише `system.getInfo()` (`system:getInfo`) і `storage.getStatus()` (`storage:getStatus`). Публічний API не містить SQL, універсальних CRUD/invoke/send/on, ipcRenderer, файлових операцій чи привілейованих об'єктів Electron. Renderer не має прямого доступу до Node.js, Electron чи файлової системи.

`shared/ipc.ts` містить allowlist та контракти; Zod 4.6.7 використовується лише в Main. Реєстратор викликається один раз на життєвий цикл застосунку, а актуальне вікно визначається для кожного запиту. Перевіряються наявність і стан вікна/WebContents, тотожність `event.sender` його WebContents, тотожність `event.senderFrame` актуальному `mainFrame`, точний URL дозволеного dev або built документа. Самого URL недостатньо. Після цього Zod tuple відхиляє будь-які аргументи, включно з явним undefined; strict object перевіряє відповідь.

Успіх має форму `{ ok: true, data }`, помилка IPC — `{ ok: false, error: { code } }`. Main повертає FORBIDDEN, INVALID_ARGUMENTS або INTERNAL_ERROR без тексту винятку; preload перетворює відмову транспорту на UNAVAILABLE. Невідомі канали не мають обробників і відхиляються транспортом Electron. Кожний публічний метод викликає лише свій канал без аргументів. SystemInfo містить тільки name/version/mode з Electron app. StorageStatus містить state, для ready — created/schemaVersion, для error — контрольований code. Шляхи, користувацькі дані та секрети не повертаються.

Місце для майбутньої перевірки доступу — в Main після перевірки відправника/аргументів і перед виконанням захищеної операції. Зараз існує лише публічна діагностика; немає сеансів, авторизації або заглушки, що автоматично дозволяє доступ. Майбутні операції з даними також мають перевіряти готовність сховища в Main.

Vite збирає `.cts` разом зі спільними константами в один CommonJS `dist-electron/preload.cjs`, залишаючи зовнішнім лише Electron. Це потрібно через [обмеження require у sandboxed preload](https://www.electronjs.org/docs/latest/tutorial/sandbox). Окремий TS-конфіг перевіряє preload без emit; NodeNext компілює Main і shared зі збереженням структури каталогів.

Production CSP у `index.html` задає `default-src 'none'`, власні scripts/styles/images/fonts, `connect-src 'none'`, заборону base/form/object. Лише Vite serve-плагін дозволяє inline React refresh/styles і локальний HMR WebSocket. Це не послаблює built-CSP.

## Dev, built та профілі

Dev обирається лише коли застосунок не запакований і передано `--dev`; сама відсутність пакування не вмикає Vite. `pnpm dev` спочатку компілює Main/preload, далі запускає Vite та Electron через concurrently/wait-on. Адреса — `http://127.0.0.1:5176/`, `strictPort: true`. Немає логіки примусового звільнення порту. Після змін Main/preload потрібен перезапуск dev; renderer використовує HMR.

`package.json.main` веде до `dist-electron/electron/main.js`; preload — `dist-electron/preload.cjs`. Built завантажує `../../dist/index.html` від каталогу Main через `loadFile`. Vite має `base: './'`, тому JS/CSS і зображення завантажуються з локальної збірки без Vite та інтернету. `start:built` не виконує збірку й потребує встановленого Electron.

Main обирає userData до single-instance lock:

- dev: `%APPDATA%\HromadaHR-dev`;
- built і майбутній packaged-режим: `%APPDATA%\HromadaHR`.

Профілі незалежні від HromadaAID. Повторний запуск одного режиму фокусує його наявне вікно; dev і built можуть працювати паралельно. На Windows закриття останнього вікна завершує застосунок. Дані SQLite розміщено окремо від цих Electron-профілів.

## SQLite, життєвий цикл та помилки

Main визначає системний корінь через `process.env.LOCALAPPDATA`, перевіряє його наявність та абсолютність і використовує той самий isDev (`!app.isPackaged && --dev`), що й для Electron-профілю. NODE_ENV не використовується. Шляхи:

- built/packaged: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`;
- dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`.

Якщо системний корінь відсутній або недоступний, ініціалізація завершується FILESYSTEM; fallback у вихідний код, dist/resources, roaming-профіль або каталог executable відсутній. `start:built` використовує продукційні дані, тому не є командою руйнівного тестування.

Після single-instance lock та `app.whenReady`, перед створенням вікна, Main один раз ініціалізує Storage. Власник утримує одне робоче з'єднання; повторна ініціалізація ігнорується, а guard шляхів відхиляє паралельне відкриття тієї самої бази в процесі. Readonly preflight-з'єднання закривається до відкриття робочого. `will-quit` закриває з'єднання; close ідемпотентний. При помилці відкриття/міграції з'єднання також закривається. Це не розподілений lock від сторонніх SQL-редакторів: SQLite забезпечує власні блокування.

Відсутній файл створюється ексклюзивно (`wx`), без перезапису конкурентно створеного файла. Наявний файл має бути звичайним файлом із повним SQLite-заголовком; існуючий порожній або обрізаний файл вважається пошкодженим. До змін схеми readonly preflight виконує повний `integrity_check`, окремий `foreign_key_check` та перевірку версії/ledger. Після міграцій цілісність перевіряється знову. Пошкоджена, невідома чи недоступна база ніколи автоматично не видаляється, не замінюється і не ремонтується.

На кожному робочому з'єднанні: `foreign_keys=ON`, `journal_mode=WAL` (його успішне ввімкнення обов'язкове), `busy_timeout=5000`, `synchronous=FULL`. FULL обрано з пріоритетом збереження даних при збоях живлення, з урахуванням гарантій накопичувача/ОС. WAL може створювати штатні файли `-wal`/`-shm`; їх не можна вручну видаляти під час роботи. Підстава політики — [SQLite PRAGMA](https://www.sqlite.org/pragma.html).

StorageStatus розрізняє initializing, ready, error, closed. Ready.created відділяє перше створення від повторного відкриття. Помилки: CORRUPT, UNSUPPORTED_SCHEMA, FILESYSTEM, BUSY, MIGRATION_FAILED, INITIALIZATION_FAILED, BACKUP_REQUIRED. Вони не містять шляхів чи текстів технічних винятків. Renderer показує помилку на будь-якому розділі та не повідомляє про готовність сховища; у налаштуваннях справний стан показано окремо. Після помилки потрібні усунення причини та перезапуск; автоматичного retry/reset немає.

## Версійні міграції

Єдина поточна таблиця — `schema_migrations` (STRICT): version, name, SHA-256 checksum SQL/назви та applied_at UTC. Міграція 1 створює сам ledger. `app_settings` не додано через відсутність поточних налаштувань; `local_account` і предметних таблиць немає.

Manifest — послідовний список статичних SQL-міграцій у Main, версії починаються з 1 без пропусків. Застосовані записи мають утворювати точний префікс manifest та збігатися за назвою/checksum. `PRAGMA user_version` дублює поточну версію і має відповідати ledger. Новіша версія, невідомі ID, пропуски чи змінений checksum відхиляються. База з невідомими таблицями без нашого ledger не приймається автоматично; додаткові таблиці у впізнаній базі не видаляються.

Кожна міграція виконується в окремій `BEGIN IMMEDIATE` транзакції: зміна схеми, INSERT у ledger та user_version комітяться разом. Перед SQL версія повторно перевіряється під write lock. Виняток відкочує всі зміни поточної міграції, а вже успішні попередні міграції зберігаються. Повторний запуск не виконує застосований SQL. Автоматичного downgrade, видалення чи перебудови невідомих таблиць немає.

Поле `requiresBackup` відмічає майбутні критичні міграції. Поки немає перевіреного механізму захисної копії, така міграція блокується BACKUP_REQUIRED перед SQL. На 2.4 координатор зможе створити/перевірити копію через online backup драйвера перед транзакцією; зараз копії та обхід цього бар'єра не реалізовано.

Синхронні SQLite-операції, integrity_check і очікування busy timeout блокують цикл Main. Для нинішньої малої службової схеми це прийнятно; перед великими міграціями/запитами потрібне вимірювання й окреме рішення про worker. Це не система авторизації, резервування, відновлення чи захисту даних від читання іншими програмами Windows.

## Renderer та стилі

`App.tsx` використовує один `useState<SectionId>`, без React Router, глобального сховища або збереження вибраного розділу. Розділи: Головна, Огляд, Працівники, Відпустки, Стаж і ранги, Документи, Налаштування. Заголовок, breadcrumbs та активний пункт походять з одного опису розділів. Налаштування розміщено внизу sidebar.

Головна містить ідентичність пілотної установи й стан розробки без KPI та кнопок удаваних операцій. Решта розділів використовує `DataState kind="planned"` з тематичним поясненням. Цей стан відрізняється від `empty`; підтримка loading/empty/search у компоненті не означає наявності запитів чи реєстрів. Alert показує локальні інформаційні повідомлення.

У налаштуваннях footer через IPC показує реальну версію застосунку, стан завантаження або повідомлення про недоступність. StorageNotice отримує стан сховища один раз після монтування; поточних записів/фонових операцій із даними немає. Сім розділів та дизайн-система збережені.

`src/styles.css` імпортує:

- `tokens.css`: семантичні кольори, відступи, радіуси, висоти й тривалість переходів;
- `base.css`: Segoe UI, базові правила, видимий focus, skip-link і reduced motion;
- `components.css`: кнопки, Alert, DataState;
- `shell.css`: sidebar, topbar, breadcrumbs, головний блок і адаптивність.

Використано відібрані універсальні правила HromadaAID на [коміті 16582ce](https://github.com/Anatol1ch/HromadaAID/tree/16582ce252086bb39d2276ac3c1de90e4895f21f), без залежності від його коду або історії. Власна палітра HromadaHR: акцент `#6F5AA5`, темний `#594681`, світлий `#EFEAF7`, фон `#F7F6FA`, межі `#E4DFEC`, текст `#252738`, допоміжний текст `#687084`, картки `#FFFFFF`. Кольори success/error/warning відокремлені від акценту.

Збережено sidebar 258 px (244 px до 1280 px; піктограми 68 px до 1100 px), topbar 68 px, контент до 1500 px, стандартний контроль 44 px і шкалу 4/8/12/16/20/24/32 px. За ширини до 760 px topbar має 58 px, до 600 px головний блок стає одноколонковим, topbar — автоматичної висоти з мінімумом 68 px. Окремої мобільної версії немає.

Розрахунки палітри на етапі 1.2.1: білий текст кнопки 5,70:1 (hover 8,02:1), основний текст на фоні 13,69:1, допоміжний на білому 4,95:1 і на робочому фоні 4,60:1, темний акцент на світлому 6,79:1. Це не замінює ручного приймання всього інтерфейсу.

## Герб і діагностика старого вікна

`App.tsx` імпортує `../assets/community-coat.png`. PNG 1488 × 1996, SHA256 `ca93bd8920cffa188ef2dbce9ecc276c553c4c80bf0b5716b4fdae2662e1456f`. Vite копіює його з хешованою назвою до `dist/assets`; URL формується відносно JS-бандла і працює з `file://`. Розмір області зображення — 128 × 168 із `max-width: 100%` та `object-fit: contain`, без обрізання або спотворення пропорцій.

Герб ліворуч і назва Вишнівської селищної територіальної громади праворуч — пілотна ідентичність установи. Основний бренд HromadaHR у sidebar зберігає UsersRound. Завантаження або зміни герба через налаштування немає.

На етапі 1.3 старе відкрите dev-вікно ще показувало UsersRound у блоці установи; нове built-вікно коректно показало герб. Змін PNG, CSS, CSP чи шляхів для виправлення не знадобилося. Якщо видно старий екран, закрийте відповідний екземпляр, зупиніть старий dev-сеанс Ctrl+C у його терміналі та виконайте `pnpm build`, потім `pnpm start:built`. Повторний запуск без закриття може лише сфокусувати старе вікно.

## Команди

| Команда | Результат |
| --- | --- |
| `pnpm install --frozen-lockfile` | Встановлення за lockfile та підготовка Electron; для першого встановлення потрібен інтернет |
| `pnpm dev` | Компіляція Main/preload, Vite й Electron у dev-профілі |
| `pnpm typecheck` | Перевірка renderer, Vite-конфігурації та Electron без emit |
| `pnpm test` | Збірка Main/preload, 26 тестів IPC/SQLite та smoke у реальному Electron Main |
| `pnpm build:electron` | Emit Main/shared і один CommonJS preload-бандл |
| `pnpm build` | Typecheck, emit Main/preload, production renderer і ресурси |
| `pnpm start:built` | Відкриття вже зібраного застосунку через локальний Electron |

TS-конфігурація спільно задає strict-перевірки. Renderer має DOM/react-jsx, Bundler resolution і noEmit; Vite-конфігурації — окрему node-перевірку; Electron — NodeNext і rootDir `.` для Main/shared; preload — окрему Bundler-перевірку. Встановлені залежності не містять серверного runtime або пакувальника.

IPC-тести запускають реальний скомпільований реєстратор із doubles Electron-об'єктів і preload-бандл у Node VM із контрольованим transport/contextBridge. SQLite-тести використовують реальний драйвер і лише `mkdtemp` під системним temp: створення/повторне відкриття, послідовність/неповторність/rollback, новіша схема, пошкодження без перезапису, FK, незалежні шляхи, закриття, ledger/checksum, критичний бар'єр та помилки файлової системи.

Smoke окремо запускає Electron 44.7.1 як справжній Main без BrowserWindow й без ELECTRON_RUN_AS_NODE: better-sqlite3 створює/мігрує/закриває/повторно відкриває тимчасову базу. Профілі Electron, logs і crashDumps також спрямовано в temp; батьківський процес видаляє їх після завершення Electron. Перевірено Windows x64, Node у Electron 24.21.0; ARM64 та майбутнє пакування не перевірялися. У sandbox облікового запису Codex можливий блок ACL виконуваного Electron; контрольний запуск поза ним пройшов без зміни налаштувань безпеки застосунку. GUI-приймання залишається ручним.

## Ще не реалізовано

Локальна авторизація, майстер першого запуску, кадрові IPC, реєстри й операції, відпустки, стаж, ранги, документообіг, резервування, відновлення, оновлення та інсталятор відсутні. Сховище й міграції готові як основа етапу 2.3, який не розпочато. Не слід трактувати службову БД, навігаційні кнопки або інформаційні стани як реалізацію предметних механізмів.
