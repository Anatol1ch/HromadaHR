# Фактична архітектура HromadaHR

Документ описує версію 0.1.0 у робочій гілці після 3.4.1 (UI-основа HromadaAID; main поки 3.3). Етап 2.3 остаточно скасовано. Погоджені рішення наведено окремо в [DECISIONS.md](DECISIONS.md).

## Стек та структура

Цільова платформа — Windows 10/11, локальний настільний застосунок без окремого сервера. Середовище розробки: Node.js 24.22.1, pnpm 11.25.0. Використано Electron 44.7.1, React/React DOM 19.2.9, TypeScript 5.9.3, Vite 8.3.4, @vitejs/plugin-react 6.1.2 та lucide-react 0.577.0. ## Electron та межа безпеки

Ідентичність: package `hromada-hr`, product HromadaHR, версія 0.1.0. Main задає назву HromadaHR та Windows AppUserModelId `local.hromadahr`. Створюється звичайне вікно 1000 × 700 без власного меню.

BrowserWindow використовує `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; стандартна web security не вимикається. Main блокує навігацію та перенаправлення через `will-navigate`/`will-redirect`, приєднання webview і створення сторонніх вікон. Запити дозволів відхиляються.

Ланцюжок виклику: React Renderer → явний метод `window.hromadaHR` → preload/contextBridge → IPC → Main. Окрім system.getInfo/system.quit/storage.getStatus/storage.retry дозволено backup.getStatus, chooseFolder, saveConfig, runManual, chooseRestore, confirmRestore та явні методи personnel, описані нижче. GetStatus містить конфігурацію і результати, тому окремий дублюючий config-getter не потрібний. Публічний API не містить SQL, універсальних CRUD/invoke/send/on, ipcRenderer або привілейованих об'єктів Electron. Renderer не має прямого доступу до Node.js, Electron чи файлової системи.

`shared/ipc.ts` містить allowlist та контракти; Zod 4.6.7 використовується лише в Main. Реєстратор викликається один раз на життєвий цикл застосунку, а актуальне вікно визначається для кожного запиту. Перевіряються наявність і стан вікна/WebContents, тотожність `event.sender` його WebContents, тотожність `event.senderFrame` актуальному `mainFrame`, точний URL дозволеного dev або built документа. Самого URL недостатньо. Після цього Zod tuple відхиляє будь-які аргументи, включно з явним undefined; strict object перевіряє відповідь.

Успіх має форму `{ ok: true, data }`, помилка IPC — `{ ok: false, error: { code } }`. Main повертає контрольовані коди без тексту винятку; preload перетворює відмову транспорту на UNAVAILABLE. Асинхронні операції очікуються перед Zod-перевіркою результату. Невідомі канали не реєструються. Кожний публічний метод викликає лише свій канал із визначеними аргументами. SystemInfo/StorageStatus не містять шляхів. BackupStatus навмисно повертає тільки вибрані користувачем теки для відображення в налаштуваннях, результати й назви копій; активний шлях SQLite, технічні винятки та SQL не повертаються.

Усі функції доступні без входу. Авторизація, реєстрація, акаунти, сеанси, паролі, ролі/RBAC, обмеження функцій та відновлення паролів остаточно виключені з архітектури. Спеціальні NTFS ACL не налаштовуються, стандартні дозволи Windows не змінюються; SQLite і копії не шифруються. Технічні перевірки IPC залишаються; готовність SQLite та зайнятість операцією перевіряються в Main.

Vite збирає `.cts` разом зі спільними константами в один CommonJS `dist-electron/preload.cjs`, залишаючи зовнішнім лише Electron. Це потрібно через [обмеження require у sandboxed preload](https://www.electronjs.org/docs/latest/tutorial/sandbox). Окремий TS-конфіг перевіряє preload без emit; NodeNext компілює Main і shared зі збереженням структури каталогів.

Production CSP у `index.html` задає `default-src 'none'`, власні scripts/styles/images/fonts, `connect-src 'none'`, заборону base/form/object. Лише Vite serve-плагін дозволяє inline React refresh/styles і локальний HMR WebSocket. Це не послаблює built-CSP.

## Dev, built та профілі

Dev обирається лише коли застосунок не запакований і передано `--dev`; сама відсутність пакування не вмикає Vite. `pnpm dev` спочатку компілює Main/preload, далі запускає Vite та Electron через concurrently/wait-on. Адреса — `http://127.0.0.1:5176/`, `strictPort: true`. Немає логіки примусового звільнення порту. Після змін Main/preload потрібен перезапуск dev; renderer використовує HMR.

`package.json.main` веде до `dist-electron/electron/main.js`; preload — `dist-electron/preload.cjs`. Built завантажує `../../dist/index.html` від каталогу Main через `loadFile`. Vite має `base: './'`, тому JS/CSS і зображення завантажуються з локальної збірки без Vite та інтернету. `start:built` не виконує збірку й потребує встановленого Electron.

Main обирає userData до single-instance lock:

- dev: `%APPDATA%\HromadaHR-dev`;
- built і майбутній packaged-режим: `%APPDATA%\HromadaHR`.

Профілі незалежні від HromadaAID. Повторний запуск одного режиму фокусує його наявне вікно; dev і built можуть працювати паралельно. На Windows закриття останнього вікна завершує застосунок. Дані SQLite розміщено окремо від цих Electron-профілів.

## SQLite, життєвий цикл та помилки

Main визначає системний корінь через `process.env.LOCALAPPDATA`, перевіряє його наявність та абсолютність і використовує той самий isDev (`!app.isPackaged && --dev`), що й для Electron-профілю. NODE_ENV не використовується. Шляхи:

- built/packaged: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`;
- dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`.

Якщо системний корінь відсутній або недоступний, ініціалізація завершується FILESYSTEM; fallback у вихідний код, dist/resources, roaming-профіль або каталог executable відсутній. `start:built` використовує продукційні дані, тому не є командою руйнівного тестування.

Після single-instance lock та app.whenReady, перед створенням вікна, Main очікує initializeSafely: повернення з незавершеного restore-журналу, readonly preflight, відкриття й міграції із захисними копіями для requiresBackup. Власник утримує одне робоче з'єднання; guard шляхів відхиляє паралельне відкриття тієї самої БД в процесі. Readonly preflight закривається до робочого з'єднання. Під час відновлення власник контрольовано закривається й повторно відкривається. Before-quit очікує завершення активної backup/restore-операції; will-quit зупиняє таймер, скасовує невикористаний вибір та закриває SQLite. Це не розподілений lock від сторонніх SQL-редакторів: SQLite забезпечує власні блокування.

На першому запуску відсутній файл створюється ексклюзивно (`wx`). Після успішного відкриття Main записує маркер `storage-{hash шляху}.initialized` у корені HromadaHR[-dev], окремо від data/. Відомий відсутній файл дає MISSING_DATABASE; повторна перевірка ніколи не створює базу. Наявні sidecars також забороняють перше створення. Маркер не змінює шлях SQLite чи міграції. До першого запуску 2.4.1 старі інсталяції ще не мають маркера; одночасна відсутність бази й маркера не відрізняється від нової інсталяції.

Наявний файл має бути звичайним файлом із повним SQLite-заголовком; доступ на читання встановлюється до діагностики короткого файла. До змін схеми readonly preflight виконує `integrity_check`, `foreign_key_check` та перевірку версії/ledger; після міграцій цілісність перевіряється знову. CORRUPT відрізняється від UNSUPPORTED_SCHEMA, BUSY і FILESYSTEM (доступ/носій/місце/I/O). Пошкоджена, невідома чи недоступна база автоматично не видаляється, не замінюється і не ремонтується.

На кожному робочому з'єднанні: `foreign_keys=ON`, `journal_mode=WAL` (його успішне ввімкнення обов'язкове), `busy_timeout=5000`, `synchronous=FULL`. FULL обрано з пріоритетом збереження даних при збоях живлення, з урахуванням гарантій накопичувача/ОС. WAL може створювати штатні файли `-wal`/`-shm`; їх не можна вручну видаляти під час роботи. Підстава політики — [SQLite PRAGMA](https://www.sqlite.org/pragma.html).

StorageStatus розрізняє initializing, ready, error, closed. Ready.created відділяє перше створення від повторного відкриття. RECOVERY_REQUIRED означає неможливість безпечного повернення після заміни; коди не містять шляхів чи текстів винятків. App опитує стан раз на секунду й до ready показує окремий екран замість семи розділів. CORRUPT/UNSUPPORTED_SCHEMA/MISSING_DATABASE дозволяють явне аварійне відновлення; інші помилки — лише повторну перевірку й закриття. Обидві дії мають явні IPC storage.retry/system.quit без аргументів із чинними sender/mainFrame/URL і Zod-перевірками. Автоматичних циклів повторного відкриття немає.

## Версійні міграції

Міграція 1 створює schema_migrations (STRICT): version, name, SHA-256 checksum SQL/назви та applied_at UTC. Її SQL/checksum не змінено. Міграція 2 додає лише службові backup_config (один instance_id і дві теки) та backup_state (по рядку на теку: добовий успіх, остання спроба/успіх/помилка/файл, день і кількість спроб, retry_after). Усі часові мітки — ISO UTC, добовий ключ — локальна календарна дата. Загального конфігураційного фреймворку й local_account немає. Міграція 3 додає кадрові таблиці, описані нижче; SQL, назви та checksum міграцій 1–2 не змінено.

Manifest — послідовний список статичних SQL-міграцій у Main, версії починаються з 1 без пропусків. Застосовані записи мають утворювати точний префікс manifest та збігатися за назвою/checksum. `PRAGMA user_version` дублює поточну версію і має відповідати ledger. Новіша версія, невідомі ID, пропуски чи змінений checksum відхиляються. База з невідомими таблицями без нашого ledger не приймається автоматично; додаткові таблиці у впізнаній базі не видаляються.

Кожна міграція виконується в окремій `BEGIN IMMEDIATE` транзакції: зміна схеми, INSERT у ledger та user_version комітяться разом. Перед SQL версія повторно перевіряється під write lock. Виняток відкочує всі зміни поточної міграції, а вже успішні попередні міграції зберігаються. Повторний запуск не виконує застосований SQL. Автоматичного downgrade, видалення чи перебудови невідомих таблиць немає.

Поле requiresBackup інтегроване в applyMigrationsSafely: до транзакції виконується перевірений online snapshot у data/protection з версією міграції в назві. Помилка копії блокує SQL; помилка SQL не видаляє захисну копію. Міграція 2 некритична. Міграція 3 має requiresBackup=true; перед її SQL обов’язково створюється перевірений знімок версії 2. Повторний запуск після застосування не створює зайвих копій. Синхронний низькорівневий applyMigrations залишено fail-closed: без координатора він відхиляє requiresBackup через BACKUP_REQUIRED.

Синхронні SQLite-операції, integrity_check і очікування busy timeout блокують цикл Main; online backup асинхронний. Перед великими міграціями/запитами потрібне вимірювання й окреме рішення про worker. Файли доступні іншим програмам згідно зі стандартними дозволами Windows.

## Предметна основа працівників (3.1)

Міграція 3/personnel_foundation має requiresBackup=true і додає чотири STRICT-таблиці: employees, departments, positions, employee_positions. SQL — electron/storage/personnel-migration.ts. Перед SQL чинний startup-координатор створює перевірену захисну копію в data/protection; невдача блокує міграцію. Міграції 1–2, їхні назви, SQL та checksum незмінні. Попередній незакомічений варіант 3.1 у цьому чаті замінено уточненою моделлю до публікації; його тимчасові тестові БД не є підтримуваною версією схеми. Невідомий checksum, як і раніше, відхиляється без автоматичного переписування.

employees містить id (UUID із Main), last_name, first_name, nullable middle_name/birth_date/note та employee_type зі значеннями official або staff. Прізвище та ім’я обов’язкові; по батькові необов’язкове. Текстові поля до 200 символів, примітка до 4000. Nullable поля в контракті передаються явно як null; порожні рядки відхиляються. Zod обрізає зовнішні пробіли. Дати — реальні календарні YYYY-MM-DD, роки 0001–9999, без часу: перевіряються в Main та додатковими SQL CHECK. Народження не пізніше першого призначення перевіряється сервісом.

Довідники departments і positions мають id/name та технічний name_key UNIQUE NOT NULL. Назва нормалізується Unicode NFC, зовнішні пробіли видаляються, послідовності Unicode-пробілів згортаються до одного. Ключ утворюється з нормалізованої назви Unicode-перетворенням toUpperCase().toLowerCase() та повторним NFC; це усуває залежність від ASCII-only SQLite NOCASE і враховує, зокрема, український регістр, складені символи та Straße/STRASSE. Ключ обчислюється лише Main; UNIQUE захищає від конкурентного дублювання. Довільний SQL у renderer відсутній. Ця нормалізація не є пошуком схожих символів або транслітерацією. Майбутнє редагування назв має використовувати той самий ключ.

employee_positions містить id, employee_id, department_id, position_id, nullable category і start_date. Категорія належить конкретному призначенню, у positions її немає. UNIQUE(employee_id,start_date) та його індекс забезпечують однозначну хронологію; додано індекси зовнішніх посилань на довідники. employee_id має ON DELETE CASCADE, довідники — ON DELETE RESTRICT. Немає end_date, окремої дати прийняття чи поточної посади в employees. Дата прийняття в відповіді — перша start_date; поточне призначення — остання start_date незалежно від сьогоднішньої дати. Історія повертається за зростанням start_date. Картка містить обчислену hireDate та currentAssignment із назвами посади/підрозділу. Створення через сервіс завжди додає перше призначення; неконсистентна картка без історії повертає CONFLICT.

Main-only PersonnelService отримує поточне з’єднання від Storage на кожній операції, включно з повторним відкриттям після restore. Створення працівника та першого призначення виконується однією IMMEDIATE-транзакцією; помилка будь-якої частини відкочує все. updateEmployee змінює лише персональні відомості, не дату прийняття/призначення. Списки, картка й історія читаються узгоджено в транзакціях. Сервіс відхиляє операції під час backup/restore через BUSY, недоступну SQLite — STORAGE_UNAVAILABLE, відсутній ID — NOT_FOUND, конфлікти — CONFLICT. SQL-винятки обробляє IPC без витоків деталей.

На 3.1 window.hromadaHR.personnel отримав дев’ять явних методів: listEmployees/getEmployee/createEmployee/updateEmployee/getHistory, listDepartments/createDepartment та listPositions/createPosition. Контракти — shared/personnel.ts і shared/ipc.ts; Zod аргументів і відповідей — electron/personnel/schemas.ts та чинний IPC-реєстратор. Збережено allowlist, sender/mainFrame/URL та IpcResult. src/env.d.ts уже посилається на HromadaHRApi, додаткової декларації не потребує. На 3.3 додано кадрові зміни та видалення (див. нижче). Редагування/видалення довідників через IPC не відкриті. Схему змінювати не знадобилося.

Цільові tests/personnel.test.mjs перевіряють checksum 1–2, нову БД/оновлення v2, фактичну захисну копію й блокування при її невдачі, валідацію, FK/UNIQUE/STRICT, атомарність, обчислення хронології, Unicode-конфлікти довідників та готовність каскаду. tests/ipc.test.mjs перевіряє всі кадрові канали й bundled preload → IPC → ізольовану SQLite, на 3.2 — включно з відсутністю тоді ще не реалізованих методів 3.3/SQL. На 3.3 тести розширено на нові явні методи; SQL API як і раніше відсутній. Синхронні базові storage-тести використовують явно обмежений manifest v2; повна v3 тестується тільки через захищений асинхронний координатор. Наявні backup/recovery-тести збережено, враховано обов’язкову pre-v3 копію та додано відновлення працівника/історії. Усі БД/профілі тимчасові; GUI не змінено й вручну не перевірено. На 3.2 реєстр і картку підключено до цих контрактів без зміни backend; GUI-приймання описано нижче.

## Резервування і відновлення

BackupService об'єднує mutex для конфігурації, вибору, ручного/автоматичного резервування та restore. System dialogs знаходяться лише в BackupController/Main. ChooseFolder повертає path для показу й непрогнозований токен вибору на 10 хвилин. SaveConfig приймає два токени/null (null залишає збережену теку), повторно перевіряє існування, запис та канонічні шляхи через realpath, включно з junction/case/trailing separators Windows. Однакові/вкладені теки й перетин із активним data-каталогом заборонені. Довільних тек застосунок не створює; власні staging/protection під data створюються для службової процедури. Stat.dev дає попередження щодо одного тому без блокування.

Автоматичний цикл запускається після налаштування обох тек, при старті та кожні 15 хвилин тільки в запущеному застосунку. За локальну добу кожній теці потрібний власний успішний результат; успіх першої не позначає успіх другої. Невдачі й retry_after атомарно записуються у SQLite; не більше чотирьох автоматичних спроб на теку/добу з інтервалом щонайменше 15 хвилин. Наступного дня ліміт починається знову. Ручна копія працює в обидві теки, показує окремі результати й не змінює auto_day/ліміти; одночасні операції відхиляються BUSY.

Snapshot викликає better-sqlite3 backup у випадковий .partial у цільовій теці. Закритий результат переводиться в standalone DELETE journal mode, перевіряється integrity_check/foreign_key_check/ledger/schema та fsync. Публікація — одна операція MoveFileExW із MOVEFILE_WRITE_THROUGH, без REPLACE_EXISTING/COPY_ALLOWED, у тій самій теці. Це перейменування імені без перезапису та без fallback копіювання у готове ім'я. Hardlinks не використовуються; перевірка exists перед rename не підміняє гарантію no-replace. Невдача прибирає власний .partial, попередні копії залишаються. Назви: hromadahr-{instance UUID}-{auto/manual}-{UTC timestamp}-{random UUID}.db. Копія містить всю SQLite, без Electron-профілю. Реально перевірено NTFS; exFAT не потребує hardlinks, але фізичний носій ще потребує ручної перевірки. Файлові системи, що відхиляють цю операцію, дають контрольовану помилку; гарантій проти фізичної відмови чи збою ФС немає.

Для цих фіксованих викликів Win32 додано koffi 3.3.6 (Node-API prebuild), бо Node fs.rename допускає заміну існуючого файла. Немає generic FFI/файлового API в IPC. Build-script вимкнено, runtime optional-пакет відповідної Windows-архітектури має бути включений майбутнім пакувальником поза ASAR. Перевірено Node та справжній Electron Windows x64; ARM64 і пакування не перевірялися.

Ротація виконується після публікації нової auto-копії: відбирає лише точний namespace/type/name, звичайні файли, перевірену SQLite та відповідний instance_id усередині копії. Залишає 14 останніх справних auto-копій за назвою UTC-часу. Ручні, захисні, чужі, невідомі й пошкоджені файли не видаляються. Проблема очищення відображається як помилка, нова справна копія зберігається.

Restore складається з окремих chooseRestore і confirmRestore. Спочатку системний picker, перевірки формату/цілісності/версії, відхилення активного файла та його hardlink-аліаса; далі створюється власний immutable staged snapshot. Renderer отримує тільки basename, schemaVersion й одноразовий токен на 5 хвилин, без шляху джерела. Перед заміною Main ще раз перевіряє staged файл і вимагає системне підтвердження з default/cancel «Скасувати». Прапорець confirmed не приймається. Навігація/закриття вікна скасовують невикористані вибори.

Після підтвердження створюється перевірена protect-restore копія у data/protection. Під mutex виконується checkpoint TRUNCATE, закриття з'єднання та перевірка відсутності WAL/SHM; при сторонньому активному з'єднанні заміна припиняється. Синхронізований restore-journal містить лише UUID для похідних власних імен. Він записується до переміщення активної БД у .previous-{UUID} та встановлення incoming знімка. Потім reopen(false), міграції й повторна перевірка цілісності. Лише після успіху журнал видаляється, попередній файл прибирається; protective snapshot залишається.

При винятку після закриття координатор закриває кандидата, повертає .previous і відкриває його заново. При аварійному завершенні startup бачить журнал і повертає попередню БД до звичайного відкриття. Відхилений кандидат і sidecars зберігаються під .rejected-{UUID}; якщо повернення не вдається, стан RECOVERY_REQUIRED без продовження роботи. Джерело не змінюється. Штатне відновлення справної БД зберігає поточні теки/instance_id, очищує результати/добові маркери й перезавантажує renderer.

Аварійний сценарій використовує ті самі picker, перевірки, staging, одноразовий токен, native confirmation і mutex. Після підтвердження ще раз перевіряється окремий incoming; вихідний файл не мігрується. Замість online-захисту пошкодженої SQLite Main відкриває всі наявні DB/-wal/-shm/-journal через CreateFileW(OPEN_EXISTING, GENERIC_READ|DELETE, share=0). Несумісний handle іншого процесу блокує процедуру. Усі handles утримуються до завершення копіювання й перейменування; ReadFile зберігає байти у data/protection/raw-{UUID}, manifest містить розмір/SHA-256 кожного файла. Це діагностичний набір, а не справна SQLite-копія. Неуспіх збереження забороняє заміну. Відсутній початковий файл явно фіксується відсутністю запису.

Чинний restore-journal розширено версією 2/raw; старий формат читається без змін. Після fsync перевіреного набору й журналу SetFileInformationByHandle(FileRenameInfo, ReplaceIfExists=false) переміщує оригінали в .previous через ті самі ексклюзивні handles. Incoming встановлюється no-replace. Reopen(false) виконує цілісність/міграції; лише успіх видаляє журнал. Raw/.previous зберігаються поза ротацією, налаштування резервування беруться з відновленої копії (недостовірна стара БД не читається). UI перезавантажується, таймер знову може працювати з ready-сховищем.

При помилці або наступному startup журнал v2 спочатку перевіряє всі raw-хеші. Із них створюються синхронізовані приватні rollback-файли, поточний набір ексклюзивно відкривається й перейменовується у rejected, оригінали повертаються через handles. Незмінний raw дозволяє повторити повернення після ще одного переривання. Пошкоджена/відсутня початкова БД після rollback лишається на екрані відновлення; невдача безпечного повернення дає RECOVERY_REQUIRED зі збереженим журналом. Початкові діагностичні файли автоматично не видаляються.

Обмеження: таймер не працює після виходу; ручні, raw та захисні копії не мають автоматичного ліміту. Після примусового завершення можуть залишитися приватні staging/partial/rollback/previous/rejected файли для технічного прибирання, але не неповний файл під готовою назвою. При аварії між публікацією і фіксацією успіху можлива додаткова копія при повторі. Синхронна перевірка raw-хешів читає файли в пам'ять, великі бази потребуватимуть вимірювання. Журнал перевірений для процесних збоїв, не гарантує відновлення після відмови носія або довільного збою живлення/ФС. Автоматичного ремонту, шифрування, спеціальних ACL і фонової служби немає. Модель залишається локальною.

### Реєстр і картки (3.2)

Чотири компоненти src/components/employees/ винесено з App: EmployeesWorkspace (локальний view registry/create/card/edit, query/filter/sort і повідомлення), EmployeeRegistry (listEmployees і клієнтська таблиця), EmployeeForm (створення/персональне редагування та швидкі довідники), EmployeeCard (загальна інформація, історія та вкладки). src/employees/model.ts містить чисті функції пошуку, українського сортування, клієнтської валідації й мапування payload, дат та презентації історії; у renderer немає імпорту Electron/Node/Main Zod.

Реєстр перечитується при вході/поверненні та явному retry; фільтри зберігаються лише в пам’яті відкритого розділу. Пошук NFC/case-insensitive по токенах ПІБ (незалежно від порядку), сортування Intl.Collator('uk'), фільтр поточного підрозділу з listEmployees. Немає пагінації, localStorage, фіктивних записів або додаткових залежностей. Стан помилки не видається за порожній результат. Успішні create/update застосовують авторитетну картку з IPC та відкривають її; після повернення список знову завантажується.

Форма перевіряє обов’язкові текстові поля, межі 200/4000, enum, реальні календарні дати й народження не пізніше прийняття. Порожні необов’язкові поля перетворюються на null. updateEmployee отримує лише lastName/firstName/middleName/birthDate/employeeType/note; кадрові поля показуються окремим readonly-блоком. Посади/підрозділи завантажуються паралельно. Швидке додавання — компактний блок усередині тієї самої форми; успіх оновлює перелік/вибір, CONFLICT перечитує довідник і пропонує вибрати наявний запис. Перед створенням явно пояснено негайне збереження довідника навіть при подальшому скасуванні працівника.

Картка паралельно викликає getEmployee/getHistory/listDepartments/listPositions, зіставляє назви історії за ID та показує останні записи першими. Кінцева дата попереднього призначення — день перед наступним початком, обчислений UTC-календарною арифметикою лише для UI; жодних записів у SQLite. Поточне призначення — останнє за контрактом 3.1, незалежно від сьогоднішньої дати. Інші вкладки не виконують розрахунків. На 3.3 UI розширено кадровими операціями, описаними нижче.

Усі read-effects мають cleanup для пізніх відповідей, повторні mutation-запити блокуються синхронним ref та disabled controls; пізні результати після unmount ігноруються. Помилки не очищують форму. При непідтвердженому transport-result повідомлення радить перевірити реєстр перед повтором створення. Форма встановлює guard для cancel/breadcrumbs/sidebar та beforeunload: підтвердження втрати змін, під час mutation вихід блокується. Фокус переводиться на заголовок нового представлення або перше помилкове поле; доступні labels/aria-invalid, таблиця з aria-sort, вкладки з roving tabindex/стрілками/Home/End, адаптивні сітки та прокручування широкої таблиці. Нативне закриття, фокус і Windows scaling ще потребують ручного приймання.

Main/IPC/сервіси/міграції 1–3 та backup/restore не змінено.

### Кадрові операції (3.3)

Нові явні канали personnel:createAssignment/updateAssignment/deleteAssignment/deleteEmployee проходять той самий register, sender/mainFrame/URL та Zod. AssignmentInput містить лише startDate/departmentId/positionId/category; власника на update/delete визначає Main за assignmentId, передати інший employeeId у payload не можна. Створення/виправлення/видалення рядка повертає EmployeeCard, видалення працівника — null. Сумарно 13 кадрових методів. Контрольовані додаткові коди: FUTURE_ASSIGNMENT, DUPLICATE_ASSIGNMENT_DATE, NO_ASSIGNMENT_CHANGE, ASSIGNMENT_BEFORE_BIRTH, LAST_ASSIGNMENT.

PersonnelService проводить кожну мутацію в IMMEDIATE-транзакції. Після перевірки існування ID/довідників і дубля дати виконується SQL та перевірка всієї результуючої хронології під тим самим write lock. Відхиляються порожня історія, дата до відомого народження або після локальної календарної дати Windows, однакові сусідні трійки positionId/departmentId/category. Категорія — точне порівняння після чинного trim, без нормативного довідника/регістрового згортання. Перевірка охоплює обох сусідів вставки заднім числом і сусідів, які з’єдналися після delete. Першу дату можна виправити або перемістити в іншому порядку; hireDate/currentAssignment далі обчислюються з першого/останнього рядка. Виняток відкочує SQL; єдиний рядок захищено навіть при прямому IPC. Найновіший рядок можна видалити, якщо лишається коректна непорожня історія.

Сумісність майбутніх дат оцінено окремо: createEmployee/schema/форма 3.2 досі допускають майбутнє початкове прийняття, цей контракт не змінено. Такі картки продовжують показувати останній рядок як поточний, а не стан на сьогодні. Нові кадрові мутації вимагають відсутності майбутніх дат у всій результуючій історії. Форма виправлення зберігає стару майбутню дату й показує warning; збереження вимагає її явного виправлення. Явне видалення майбутнього рядка дозволене за наявності коректної історії, що лишається. Планування, автопідміни дат і нової моделі поточної посади немає. Clock injection використовується лише в тестах; runtime бере календарну дату Windows.

У EmployeesWorkspace додано view assignment; AssignmentForm і EmployeeForm використовують спільний DirectoryFields (завантаження/вибір/швидке створення та CONFLICT) й useUnsavedChanges. Запити захищено ref/disabled та alive cleanup. У картці є додавання/виправлення, підтверджене видалення історії та окрема секція повного видалення. DeleteConfirmation — нативний HTML dialog showModal із alertdialog, описом, cancel focus/Escape/відновленням фокусу. Видалення працівника показує ПІБ, кількість історії й незворотність; не вимагає пароля/введення ПІБ. Помилка не закриває діалог, pending блокує повторне надсилання/вихід. Успіх повертає до реєстру з повідомленням. Кадрові зміни перечитують картку/історію/довідники, оновлюють кеш і шапку; реєстр також перечитується при поверненні зі збереженими query/filter/sort. Кінці історії лише обчислюються для показу; helper перевіряє min-date та порядок, тому не віднімає день від 0001-01-01 і не формує зворотних діапазонів.

Повне видалення — DELETE employees в IMMEDIATE-транзакції з чинним ON DELETE CASCADE employee_positions. Довідники й інші працівники не видаляються; можливий SQL-збій відкочує і працівника, і каскад. Soft-delete/кошика/архіву/журналу аудиту немає. Перед додаванням модулів відпусток, стажу, рангів, документів політику повного видалення потрібно поширити на їхні фактичні employee_id FK/залежні записи та перевірити атомарність; зараз таких таблиць/умовних каскадів немає. SQLite owner, backup/restore, міграції 1–3/checksum та залежності незмінні.

tests/personnel-history.test.mjs перевіряє додавання/вставку заднім числом/виправлення першого й проміжного рядка/перестановку, дублі дат і станів з обох боків, birth/today/future межі, видалення поточного/першого/єдиного рядка, міст A → B → A, каскад і відкат employee-delete через ін’єкцію SQL-збою. Після кожної відмови порівнюються всі кадрові таблиці та виконуються integrity_check/foreign_key_check. Checksum 3 зафіксовано поряд із наявними 1–2. IPC-тести охоплюють нові сигнатури/відправників/невалідні відповіді та bundled preload → handler → SQLite → видалення. Electron Main smoke виконує всі чотири операції й перевіряє повернення історії через чинний backup/recovery. Повний pnpm test — 96/96 + smoke, typecheck/build/diff-check успішні. Лише mkdtemp; продукційна БД не відкривалася. GUI-кліки не автоматизувалися, ручний чекліст у HANDOFF ще не виконаний. Етап 04 не розпочато.

## Герб і діагностика старого вікна

`App.tsx` імпортує `../assets/community-coat.png`. PNG 1488 × 1996, SHA256 `ca93bd8920cffa188ef2dbce9ecc276c553c4c80bf0b5716b4fdae2662e1456f`. Vite копіює його з хешованою назвою до `dist/assets`; URL формується відносно JS-бандла і працює з `file://`. Розмір області зображення — 128 × 168 із `max-width: 100%` та `object-fit: contain`, без обрізання або спотворення пропорцій.

Герб ліворуч і назва Вишнівської селищної територіальної громади праворуч — пілотна ідентичність установи. Основний бренд HromadaHR у sidebar зберігає UsersRound. Завантаження або зміни герба через налаштування немає.

На етапі 1.3 старе відкрите dev-вікно ще показувало UsersRound у блоці установи; нове built-вікно коректно показало герб. Змін PNG, CSS, CSP чи шляхів для виправлення не знадобилося. Якщо видно старий екран, закрийте відповідний екземпляр, зупиніть старий dev-сеанс Ctrl+C у його терміналі та виконайте `pnpm build`, потім `pnpm start:built`. Повторний запуск без закриття може лише сфокусувати старе вікно.

## Команди

| Команда | Результат |
| --- | --- |
| `pnpm install --frozen-lockfile` | Встановлення за lockfile та підготовка Electron; для першого встановлення потрібен інтернет |
| `pnpm dev` | Компіляція Main/preload, Vite й Electron у dev-профілі |
| `pnpm typecheck` | Перевірка renderer, Vite-конфігурації та Electron без emit |
| `pnpm test` | Збірка Main/preload, 63 тести IPC/SQLite/backup/restore та smoke online backup/аварійного restore у реальному Electron Main |
| `pnpm build:electron` | Emit Main/shared і один CommonJS preload-бандл |
| `pnpm build` | Typecheck, emit Main/preload, production renderer і ресурси |
| `pnpm start:built` | Відкриття вже зібраного застосунку через локальний Electron |

TS-конфігурація спільно задає strict-перевірки. Renderer має DOM/react-jsx, Bundler resolution і noEmit; Vite-конфігурації — окрему node-перевірку; Electron — NodeNext і rootDir `.` для Main/shared; preload — окрему Bundler-перевірку. Встановлені залежності не містять серверного runtime або пакувальника.

IPC-тести запускають реальний скомпільований реєстратор із doubles Electron-об'єктів і preload-бандл у Node VM із контрольованим transport/contextBridge. SQLite-тести використовують реальний драйвер і лише `mkdtemp` під системним temp: створення/повторне відкриття, послідовність/неповторність/rollback, новіша схема, пошкодження без перезапису, FK, незалежні шляхи, закриття, ledger/checksum, критичний бар'єр та помилки файлової системи.

Smoke окремо запускає Electron 44.7.1 як справжній Main без BrowserWindow й без ELECTRON_RUN_AS_NODE: better-sqlite3 створює/мігрує тимчасову базу, виконує online snapshot, закриває й повторно відкриває її, а також перевіряє Koffi/Win32 публікацію та аварійне відновлення з побайтовим збереженням пошкодженого оригіналу. Профілі Electron, logs і crashDumps також спрямовано в temp; батьківський процес видаляє їх після завершення Electron. Перевірено Windows x64, Node у Electron 24.21.0; ARM64 та майбутнє пакування не перевірялися. У sandbox облікового запису Codex можливий блок ACL виконуваного Electron; контрольний запуск поза ним пройшов без зміни налаштувань безпеки застосунку. GUI-приймання залишається ручним.
