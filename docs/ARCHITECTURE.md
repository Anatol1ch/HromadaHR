# Фактична архітектура HromadaHR

Документ описує HromadaHR 0.1.0 після підетапу 4.9.6.4. Чинна схема **SQLite v12**. Вона зберігає поточні кадрові записи, довідники з ручною черговістю, права, підтверджені періоди, реєстрації відпусток та розподіли. [Поточний стан і приймання](HANDOFF.md).

## Чинна модель

- **Працівники.** Дата прийняття зберігається окремо від актуальних посади й підрозділу. Реєстр групує за порядком підрозділів, потім за глобальним порядком посад і ПІБ. Особова картка читає актуальні дані й передає до модуля відпусток лише типізований навігаційний намір.
- **Довідники.** SQLite v12 зберігає порядок і ревізії. Main перевіряє повноту набору ID та актуальність ревізії при зміні порядку. Перейменування зберігає ID, а видалення перевіряє посилання. Історія назв не ведеться.
- **Відпустки.** Поточне право вводиться окремо від облікових днів. Три види мають підтверджені періоди й залишки. Три подієві види показують надання за роком початку. Реєстрація, редагування за ревізією, розподіли й скасування є транзакційними. Скасування повертає дні й залишає історію. Чернетка при контекстному переході залишається в пам’яті Renderer до завершення роботи з формою.
- **Сховище.** SQLite відкриває лише Main. IPC перевіряє виклики з дозволеного preload. Версійний ledger перевіряє назву й SHA-256 кожної міграції. Захищені міграції виконуються після перевіреного знімка. Резервування публікує один знімок у двох налаштованих місцях. Відновлення перевіряє джерело, захищає попередній стан і мігрує активну БД, зберігаючи вихідний файл.

Нумеровані секції нижче зберігають технічну історію. Старі версії схем і конфігурації інтерфейсу належать відповідним етапам. [Погоджені рішення](DECISIONS.md).

## Electron та межа безпеки

Ідентичність: package `hromada-hr`, product HromadaHR, версія 0.1.0. Main задає назву HromadaHR та Windows AppUserModelId `local.hromadahr`. Створюється звичайне вікно з restore-розміром 1000 × 700 без меню; перед першим показом воно максимізується штатним BrowserWindow.maximize(), без fullscreen/kiosk. Ctrl +/−/0 і NumPad змінюють WebContents zoom; значення 80/90/100/110/125/150% зберігається в interface-settings.json незалежних Electron-профілів. Видимого zoom-selector немає.

BrowserWindow використовує `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; стандартна web security не вимикається. Main блокує навігацію та перенаправлення через `will-navigate`/`will-redirect`, приєднання webview і створення сторонніх вікон. Запити дозволів відхиляються.

Ланцюжок виклику: React Renderer → явний метод `window.hromadaHR` → preload/contextBridge → IPC → Main. Явно дозволено system.getInfo/getZoom/setZoom/openContact/quit, storage.getStatus/retry, backup.getStatus/getHistory/listCopies/selectCopy/openBackupFolder/chooseFolder/saveConfig/runManual/chooseRestore/confirmRestore та дев’ять методів personnel, описаних нижче. GetStatus містить конфігурацію і результати, тому окремий дублюючий config-getter не потрібний. Публічний API не містить SQL, універсальних CRUD/invoke/send/on, ipcRenderer або привілейованих об'єктів Electron. Renderer не має прямого доступу до Node.js, Electron чи файлової системи.

`shared/ipc.ts` містить allowlist та контракти; Zod 4.6.7 перевіряє аргументи й результати IPC у Main. Реєстратор викликається один раз на життєвий цикл застосунку, а актуальне вікно визначається для кожного запиту. Перевіряються наявність і стан вікна/WebContents, тотожність `event.sender` його WebContents, тотожність `event.senderFrame` актуальному `mainFrame`, точний URL дозволеного dev або built документа. Самого URL недостатньо. Після цього Zod tuple відхиляє будь-які аргументи, включно з явним undefined; strict object перевіряє відповідь.

Успіх має форму `{ ok: true, data }`, помилка IPC — `{ ok: false, error: { code } }`. Main повертає контрольовані коди без тексту винятку; preload перетворює відмову транспорту на UNAVAILABLE. Асинхронні операції очікуються перед Zod-перевіркою результату. Невідомі канали не реєструються. Кожний публічний метод викликає лише свій канал із визначеними аргументами. SystemInfo/StorageStatus не містять шляхів. BackupStatus навмисно повертає тільки вибрані користувачем теки для відображення в налаштуваннях, результати й назви копій; активний шлях SQLite, технічні винятки та SQL не повертаються.

Усі функції доступні без входу. Авторизація, реєстрація, акаунти, сеанси, паролі, ролі/RBAC, обмеження функцій та відновлення паролів остаточно виключені з архітектури. Спеціальні NTFS ACL не налаштовуються, стандартні дозволи Windows не змінюються; SQLite і копії не шифруються. Технічні перевірки IPC залишаються; готовність SQLite та зайнятість операцією перевіряються в Main.

Vite збирає `.cts` разом зі спільними константами в один CommonJS `dist-electron/preload.cjs`, залишаючи зовнішнім лише Electron. Це потрібно через [обмеження require у sandboxed preload](https://www.electronjs.org/docs/latest/tutorial/sandbox). Окремий TS-конфіг перевіряє preload без emit; NodeNext компілює Main і shared зі збереженням структури каталогів.

Production CSP у `index.html` задає `default-src 'none'`, власні scripts/styles/images/fonts, `connect-src 'none'`, заборону base/form/object. Лише Vite serve-плагін дозволяє inline React refresh/styles і локальний HMR WebSocket. Це не послаблює built-CSP.

## Dev, built та профілі

Dev обирається лише коли застосунок не запакований і передано `--dev`; сама відсутність пакування не вмикає Vite. `pnpm dev` спочатку компілює Main/preload, далі запускає Vite та Electron через concurrently/wait-on. Адреса — `http://127.0.0.1:5176/`, `strictPort: true`. Немає логіки примусового звільнення порту. Після змін Main/preload потрібен перезапуск dev; renderer використовує HMR.

`package.json.main` веде до `dist-electron/electron/main.js`; preload — `dist-electron/preload.cjs`. Built завантажує `../../dist/index.html` від каталогу Main через `loadFile`. Vite має `base: './'`, тому JS/CSS і зображення завантажуються з локальної збірки без Vite та інтернету. `start:built` не виконує збірку й потребує встановленого Electron.

Main обирає userData до single-instance lock:

- dev: `%APPDATA%\HromadaHR-dev`;
- built і майбутній packaged-режим: `%APPDATA%\HromadaHR`.

Профілі незалежні від HromadaAID. Повторний запуск одного режиму фокусує його наявне вікно; dev і built можуть працювати паралельно. На Windows закриття останнього вікна завершує застосунок. Дані SQLite розміщено окремо від цих Electron-профілів.

## SQLite, життєвий цикл та помилки

Main визначає системний корінь через `process.env.LOCALAPPDATA`, перевіряє його наявність та абсолютність і використовує той самий isDev (`!app.isPackaged && --dev`), що й для Electron-профілю. NODE_ENV не використовується. Шляхи:

- built/packaged: `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db`;
- dev: `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`.

Якщо системний корінь відсутній або недоступний, ініціалізація завершується FILESYSTEM; fallback у вихідний код, dist/resources, roaming-профіль або каталог executable відсутній. `start:built` використовує продукційні дані, тому не є командою руйнівного тестування.

Після single-instance lock та app.whenReady Main через memoized createStartup спочатку відкриває раннє вікно й очікує ready-to-show та довірений storage.getStatus від змонтованого App. Потім один раз виконує initializeSafely: повернення з незавершеного restore-журналу, readonly preflight, відкриття й міграції із захисними копіями для requiresBackup. Власник утримує одне робоче з'єднання; guard шляхів відхиляє паралельне відкриття тієї самої БД в процесі. Readonly preflight закривається до робочого з'єднання. Під час відновлення власник контрольовано закривається й повторно відкривається. Before-quit очікує завершення незавершеної ініціалізації та активної backup/restore-операції; will-quit зупиняє таймер, скасовує невикористаний вибір та закриває SQLite. Це не розподілений lock від сторонніх SQL-редакторів: SQLite забезпечує власні блокування.

На першому запуску відсутній файл створюється ексклюзивно (`wx`). Після успішного відкриття Main записує маркер `storage-{hash шляху}.initialized` у корені HromadaHR[-dev], окремо від data/. Відомий відсутній файл дає MISSING_DATABASE; повторна перевірка ніколи не створює базу. Наявні sidecars також забороняють перше створення. Маркер не змінює шлях SQLite чи міграції. До першого запуску 2.4.1 старі інсталяції ще не мають маркера; одночасна відсутність бази й маркера не відрізняється від нової інсталяції.

Наявний файл має бути звичайним файлом із повним SQLite-заголовком; доступ на читання встановлюється до діагностики короткого файла. До змін схеми readonly preflight виконує `integrity_check`, `foreign_key_check` та перевірку версії/ledger; після міграцій цілісність перевіряється знову. CORRUPT відрізняється від UNSUPPORTED_SCHEMA, BUSY і FILESYSTEM (доступ/носій/місце/I/O). Пошкоджена, невідома чи недоступна база автоматично не видаляється, не замінюється і не ремонтується.

На кожному робочому з'єднанні: `foreign_keys=ON`, `journal_mode=WAL` (його успішне ввімкнення обов'язкове), `busy_timeout=5000`, `synchronous=FULL`. FULL обрано з пріоритетом збереження даних при збоях живлення, з урахуванням гарантій накопичувача/ОС. WAL може створювати штатні файли `-wal`/`-shm`; їх не можна вручну видаляти під час роботи. Підстава політики — [SQLite PRAGMA](https://www.sqlite.org/pragma.html).

StorageStatus розрізняє initializing, ready, error, closed. Ready.created відділяє перше створення від повторного відкриття. RECOVERY_REQUIRED означає неможливість безпечного повернення після заміни; коди не містять шляхів чи текстів винятків. App опитує стан і до ready показує заставку замість робочого простору; критична помилка одразу відкриває RecoveryScreen, без очікування таймера. Auto-backup стартує лише після ready. CORRUPT/UNSUPPORTED_SCHEMA/MISSING_DATABASE дозволяють явне аварійне відновлення; інші помилки — лише повторну перевірку й закриття. Обидві дії мають явні IPC storage.retry/system.quit без аргументів із чинними sender/mainFrame/URL і Zod-перевірками. Автоматичних циклів повторного відкриття немає.

## Версійні міграції

Міграція 1 створює schema_migrations (STRICT): version, name, SHA-256 checksum SQL/назви та applied_at UTC. Її SQL/checksum не змінено. Міграція 2 додає лише службові backup_config (один instance_id і дві теки) та backup_state (по рядку на теку: добовий успіх, остання спроба/успіх/помилка/файл, день і кількість спроб, retry_after). Усі часові мітки — ISO UTC, добовий ключ — локальна календарна дата. Загального конфігураційного фреймворку й local_account немає. Міграція 3 додає чотири кадрові таблиці. Міграція 4/remove_employee_note видаляє тільки employees.note; SQL, назви та checksum 1–3 не змінено. Міграція 5 перебудовує employees та вилучає employee_positions. Міграція 6 додає leave_period_balances із каскадом працівника та захистом від перетинів. Міграція 7 додає реєстрації та розподіли днів. Міграція 8 додає ревізію й відомості скасування та UPDATE-тригери. Актуальна версія схеми — 8.

Manifest — послідовний список статичних SQL-міграцій у Main, версії починаються з 1 без пропусків. Застосовані записи мають утворювати точний префікс manifest та збігатися за назвою/checksum. `PRAGMA user_version` дублює поточну версію і має відповідати ledger. Новіша версія, невідомі ID, пропуски чи змінений checksum відхиляються. База з невідомими таблицями без нашого ledger не приймається автоматично; додаткові таблиці у впізнаній базі не видаляються.

Кожна міграція виконується в окремій `BEGIN IMMEDIATE` транзакції: зміна схеми, INSERT у ledger та user_version комітяться разом. Перед SQL версія повторно перевіряється під write lock. Виняток відкочує всі зміни поточної міграції, а вже успішні попередні міграції зберігаються. Повторний запуск не виконує застосований SQL. Автоматичного downgrade, видалення чи перебудови невідомих таблиць немає.

Поле requiresBackup інтегроване в applyMigrationsSafely: до транзакції виконується перевірений online snapshot у data/protection з версією міграції в назві. Помилка копії блокує SQL; помилка SQL не видаляє захисну копію. Міграція 2 некритична. Міграції 3–9 мають requiresBackup=true. Перед SQL обов’язковий перевірений знімок попередньої версії. Повторний запуск після застосування не створює зайвих копій. Синхронний низькорівневий applyMigrations залишено fail-closed: без координатора він відхиляє requiresBackup через BACKUP_REQUIRED.

Синхронні SQLite-операції, integrity_check і очікування busy timeout блокують цикл Main; online backup асинхронний. Перед великими міграціями/запитами потрібне вимірювання й окреме рішення про worker. Файли доступні іншим програмам згідно зі стандартними дозволами Windows.

## Кадрова модель v5

Таблиця employees зберігає UUID, прізвище, ім’я, необов’язкові по батькові та дату народження, тип official або staff, дату прийняття та обов’язкові FK на positions і departments. Обидва FK індексовані й обмежують видалення використовуваних довідникових записів. STRICT і CHECK забезпечують допустимі типи, поля та календарні ISO-дати. Дата народження, якщо задана, не пізніша за дату прийняття. Довідники зберігають id, name і унікальний Unicode-нормалізований name_key.

Міграція v5 із requiresBackup=true після перевіреної копії видаляє employee_positions та перебудовує employees порожньою в чинній IMMEDIATE-транзакції разом із ledger і user_version. Міграції 1–4 і їхні checksum збережені. Довідники й службові таблиці залишаються на місці. Це разовий дозвіл для тестових записів. Старі копії не переписуються. Відновлення v4 або старішого знімка також проходить v5 і очищує його старі кадрові записи.

PersonnelService повертає EmployeeCard із поточними даними та назвами довідників. listEmployees і getEmployee читають employees з JOIN. createEmployee та updateEmployee використовують спільний strict контракт EmployeeDetails і пишуть один рядок у транзакції. Посада, підрозділ та дата прийняття змінюються як незалежні поля. Після 4.1 зміна дати прийняття блокується, якщо існують періоди відпустки; видалення працівника каскадно прибирає їх транзакційно, залишаючи довідники. Ще чотири IPC читають і створюють записи довідників. Ізоляція Electron та перевірки sender, mainFrame, URL і Zod застосовуються до дев’яти personnel та дванадцяти leave операцій.

Дві таблиці official/staff використовують актуальні поля для фільтрації та сортування. Єдина модальна форма створює й редагує всі відомості, включно з вибором або швидким створенням підрозділу й посади. Картка показує поточні дані й підтверджені залишки відпусток. Вкладки вислуги та рангів мають стан planned. UI відображає дати ДД.ММ.РРРР і передає ISO.

## Резервування і відновлення

BackupService об'єднує mutex для конфігурації, вибору, ручного/автоматичного резервування та restore. System dialogs знаходяться лише в BackupController/Main. ChooseFolder повертає path для показу й непрогнозований токен вибору на 10 хвилин. SaveConfig приймає два токени/null (null залишає збережену теку), повторно перевіряє існування, запис та канонічні шляхи через realpath, включно з junction/case/trailing separators Windows. Однакові/вкладені теки й перетин із активним data-каталогом заборонені. Довільних тек застосунок не створює; власні staging/protection під data створюються для службової процедури. Stat.dev дає попередження щодо одного тому без блокування.

Автоматичний цикл запускається після налаштування обох тек, при старті та кожні 15 хвилин тільки в запущеному застосунку. За локальну добу кожній теці потрібний власний успішний результат; успіх першої не позначає успіх другої. Невдачі й retry_after атомарно записуються у SQLite; не більше чотирьох автоматичних спроб на теку/добу з інтервалом щонайменше 15 хвилин. Наступного дня ліміт починається знову. Ручна копія працює в обидві теки, показує окремі результати й не змінює auto_day/ліміти; одночасні операції відхиляються BUSY.

Починаючи з 3.4.3.8, один цикл створює SQLite online snapshot у приватному staging; закритий знімок незалежно копіюється у власний .partial кожного місця. Алгоритм images.publishImage та точне повторне дублювання описано нижче в розділі 3.4.3.8. Базовий snapshot використовує better-sqlite3 backup. Закритий результат переводиться в standalone DELETE journal mode, перевіряється integrity_check/foreign_key_check/ledger/schema та fsync. Публікація — одна операція MoveFileExW із MOVEFILE_WRITE_THROUGH, без REPLACE_EXISTING/COPY_ALLOWED, у тій самій теці. Це перейменування імені без перезапису та без fallback копіювання у готове ім'я. Hardlinks не використовуються; перевірка exists перед rename не підміняє гарантію no-replace. Невдача прибирає власний .partial, попередні копії залишаються. Нові назви: hromadahr-{instance UUID}-{auto/manual}-{UTC timestamp}-{SHA256}.db. Старі random-UUID назви підтримуються без перейменування; їх не групують лише за часом. Копія містить всю SQLite, без Electron-профілю. Реально перевірено NTFS; exFAT не потребує hardlinks, але фізичний носій ще потребує ручної перевірки. Файлові системи, що відхиляють цю операцію, дають контрольовану помилку; гарантій проти фізичної відмови чи збою ФС немає.

Для цих фіксованих викликів Win32 додано koffi 3.3.6 (Node-API prebuild), бо Node fs.rename допускає заміну існуючого файла. Немає generic FFI/файлового API в IPC. Build-script вимкнено, runtime optional-пакет відповідної Windows-архітектури має бути включений майбутнім пакувальником поза ASAR. Перевірено Node та справжній Electron Windows x64; ARM64 і пакування не перевірялися.

Ротація виконується після публікації нової auto-копії: відбирає лише точний namespace/type/name, звичайні файли, перевірену SQLite та відповідний instance_id усередині копії. Залишає 14 останніх справних auto-копій за назвою UTC-часу. Ручні, захисні, чужі, невідомі й пошкоджені файли не видаляються. Проблема очищення відображається як помилка, нова справна копія зберігається.

Restore складається з окремих chooseRestore і confirmRestore. Спочатку системний picker, перевірки формату/цілісності/версії, відхилення активного файла та його hardlink-аліаса; далі створюється власний immutable staged snapshot. Renderer отримує тільки basename, schemaVersion й одноразовий токен на 5 хвилин, без шляху джерела. Перед заміною Main ще раз перевіряє staged файл і вимагає системне підтвердження з default/cancel «Скасувати». Прапорець confirmed не приймається. Навігація/закриття вікна скасовують невикористані вибори.

Після підтвердження створюється перевірена protect-restore копія у data/protection. Під mutex виконується checkpoint TRUNCATE, закриття з'єднання та перевірка відсутності WAL/SHM; при сторонньому активному з'єднанні заміна припиняється. Синхронізований restore-journal містить лише UUID для похідних власних імен. Він записується до переміщення активної БД у .previous-{UUID} та встановлення incoming знімка. Потім reopen(false), міграції й повторна перевірка цілісності. Лише після успіху журнал видаляється, попередній файл прибирається; protective snapshot залишається.

При винятку після закриття координатор закриває кандидата, повертає .previous і відкриває його заново. При аварійному завершенні startup бачить журнал і повертає попередню БД до звичайного відкриття. Відхилений кандидат і sidecars зберігаються під .rejected-{UUID}; якщо повернення не вдається, стан RECOVERY_REQUIRED без продовження роботи. Джерело не змінюється. Штатне відновлення справної БД зберігає поточні теки/instance_id, очищує результати/добові маркери й перезавантажує renderer.

Аварійний сценарій використовує ті самі picker, перевірки, staging, одноразовий токен, native confirmation і mutex. Після підтвердження ще раз перевіряється окремий incoming; вихідний файл не мігрується. Замість online-захисту пошкодженої SQLite Main відкриває всі наявні DB/-wal/-shm/-journal через CreateFileW(OPEN_EXISTING, GENERIC_READ|DELETE, share=0). Несумісний handle іншого процесу блокує процедуру. Усі handles утримуються до завершення копіювання й перейменування; ReadFile зберігає байти у data/protection/raw-{UUID}, manifest містить розмір/SHA-256 кожного файла. Це діагностичний набір, а не справна SQLite-копія. Неуспіх збереження забороняє заміну. Відсутній початковий файл явно фіксується відсутністю запису.

Чинний restore-journal розширено версією 2/raw; старий формат читається без змін. Після fsync перевіреного набору й журналу SetFileInformationByHandle(FileRenameInfo, ReplaceIfExists=false) переміщує оригінали в .previous через ті самі ексклюзивні handles. Incoming встановлюється no-replace. Reopen(false) виконує цілісність/міграції; лише успіх видаляє журнал. Raw/.previous зберігаються поза ротацією, налаштування резервування беруться з відновленої копії (недостовірна стара БД не читається). UI перезавантажується, таймер знову може працювати з ready-сховищем.

При помилці або наступному startup журнал v2 спочатку перевіряє всі raw-хеші. Із них створюються синхронізовані приватні rollback-файли, поточний набір ексклюзивно відкривається й перейменовується у rejected, оригінали повертаються через handles. Незмінний raw дозволяє повторити повернення після ще одного переривання. Пошкоджена/відсутня початкова БД після rollback лишається на екрані відновлення; невдача безпечного повернення дає RECOVERY_REQUIRED зі збереженим журналом. Початкові діагностичні файли автоматично не видаляються.

Обмеження: таймер не працює після виходу; ручні, raw та захисні копії не мають автоматичного ліміту. Після примусового завершення можуть залишитися приватні staging/partial/rollback/previous/rejected файли для технічного прибирання, але не неповний файл під готовою назвою. При аварії між публікацією і фіксацією успіху можлива додаткова копія при повторі. Синхронна перевірка raw-хешів читає файли в пам'ять, великі бази потребуватимуть вимірювання. Журнал перевірений для процесних збоїв, не гарантує відновлення після відмови носія або довільного збою живлення/ФС. Автоматичного ремонту, шифрування, спеціальних ACL і фонової служби немає. Модель залишається локальною.

### Реєстр і картки (3.2)

Чотири компоненти src/components/employees/ винесено з App: EmployeesWorkspace (локальний view registry/create/card/edit, query/filter/sort і повідомлення), EmployeeRegistry (listEmployees і клієнтська таблиця), EmployeeForm (створення/персональне редагування та швидкі довідники), EmployeeCard (загальна інформація, історія та вкладки). src/employees/model.ts містить чисті функції пошуку, українського сортування, клієнтської валідації й мапування payload, дат та презентації історії; у renderer немає імпорту Electron/Node/Main Zod.

Реєстр перечитується при вході/поверненні та явному retry; фільтри зберігаються лише в пам’яті відкритого розділу. Пошук NFC/case-insensitive по токенах ПІБ (незалежно від порядку), сортування Intl.Collator('uk'), фільтр поточного підрозділу з listEmployees. Немає пагінації, localStorage, фіктивних записів або додаткових залежностей. Стан помилки не видається за порожній результат. Успішні create/update застосовують авторитетну картку з IPC та відкривають її; після повернення список знову завантажується.

Форма перевіряє обов’язкові текстові поля, межі 200/4000, enum, реальні календарні дати й народження не пізніше прийняття. Порожні необов’язкові поля перетворюються на null. updateEmployee отримує лише lastName/firstName/middleName/birthDate/employeeType/note; кадрові поля показуються окремим readonly-блоком. Посади/підрозділи завантажуються паралельно. Швидке додавання — компактний блок усередині тієї самої форми; успіх оновлює перелік/вибір, CONFLICT перечитує довідник і пропонує вибрати наявний запис. Перед створенням явно пояснено негайне збереження довідника навіть при подальшому скасуванні працівника.

Картка паралельно викликає getEmployee/getHistory/listDepartments/listPositions, зіставляє назви історії за ID та показує останні записи першими. Кінцева дата попереднього призначення — день перед наступним початком, обчислений UTC-календарною арифметикою лише для UI; жодних записів у SQLite. Поточне призначення — останнє за контрактом 3.1, незалежно від сьогоднішньої дати. Інші вкладки не виконують розрахунків. На 3.3 UI розширено кадровими операціями, описаними нижче.

### Кадрові операції (3.3)

Нові явні канали personnel:createAssignment/updateAssignment/deleteAssignment/deleteEmployee проходять той самий register, sender/mainFrame/URL та Zod. AssignmentInput містить лише startDate/departmentId/positionId/category; власника на update/delete визначає Main за assignmentId, передати інший employeeId у payload не можна. Створення/виправлення/видалення рядка повертає EmployeeCard, видалення працівника — null. Сумарно 13 кадрових методів. Контрольовані додаткові коди: FUTURE_ASSIGNMENT, DUPLICATE_ASSIGNMENT_DATE, NO_ASSIGNMENT_CHANGE, ASSIGNMENT_BEFORE_BIRTH, LAST_ASSIGNMENT.

PersonnelService проводить кожну мутацію в IMMEDIATE-транзакції. Після перевірки існування ID/довідників і дубля дати виконується SQL та перевірка всієї результуючої хронології під тим самим write lock. Відхиляються порожня історія, дата до відомого народження або після локальної календарної дати Windows, однакові сусідні трійки positionId/departmentId/category. Категорія — точне порівняння після чинного trim, без нормативного довідника/регістрового згортання. Перевірка охоплює обох сусідів вставки заднім числом і сусідів, які з’єдналися після delete. Першу дату можна виправити або перемістити в іншому порядку; hireDate/currentAssignment далі обчислюються з першого/останнього рядка. Виняток відкочує SQL; єдиний рядок захищено навіть при прямому IPC. Найновіший рядок можна видалити, якщо лишається коректна непорожня історія.

Сумісність майбутніх дат оцінено окремо: createEmployee/schema/форма 3.2 досі допускають майбутнє початкове прийняття, цей контракт не змінено. Такі картки продовжують показувати останній рядок як поточний, а не стан на сьогодні. Нові кадрові мутації вимагають відсутності майбутніх дат у всій результуючій історії. Форма виправлення зберігає стару майбутню дату й показує warning; збереження вимагає її явного виправлення. Явне видалення майбутнього рядка дозволене за наявності коректної історії, що лишається. Планування, автопідміни дат і нової моделі поточної посади немає. Clock injection використовується лише в тестах; runtime бере календарну дату Windows.

У EmployeesWorkspace додано view assignment; AssignmentForm і EmployeeForm використовують спільний DirectoryFields (завантаження/вибір/швидке створення та CONFLICT) й useUnsavedChanges. Запити захищено ref/disabled та alive cleanup. У картці є додавання/виправлення, підтверджене видалення історії та окрема секція повного видалення. DeleteConfirmation — нативний HTML dialog showModal із alertdialog, описом, cancel focus/Escape/відновленням фокусу. Видалення працівника показує ПІБ, кількість історії й незворотність; не вимагає пароля/введення ПІБ. Помилка не закриває діалог, pending блокує повторне надсилання/вихід. Успіх повертає до реєстру з повідомленням. Кадрові зміни перечитують картку/історію/довідники, оновлюють кеш і шапку; реєстр також перечитується при поверненні зі збереженими query/filter/sort. Кінці історії лише обчислюються для показу; helper перевіряє min-date та порядок, тому не віднімає день від 0001-01-01 і не формує зворотних діапазонів.

Повне видалення — DELETE employees в IMMEDIATE-транзакції з чинним ON DELETE CASCADE employee_positions. Довідники й інші працівники не видаляються; можливий SQL-збій відкочує і працівника, і каскад. Soft-delete/кошика/архіву/журналу аудиту немає. Перед додаванням модулів відпусток, стажу, рангів, документів політику повного видалення потрібно поширити на їхні фактичні employee_id FK/залежні записи та перевірити атомарність; зараз таких таблиць/умовних каскадів немає. SQLite owner, backup/restore, міграції 1–3/checksum та залежності незмінні.

tests/personnel-history.test.mjs перевіряє додавання/вставку заднім числом/виправлення першого й проміжного рядка/перестановку, дублі дат і станів з обох боків, birth/today/future межі, видалення поточного/першого/єдиного рядка, міст A → B → A, каскад і відкат employee-delete через ін’єкцію SQL-збою. Після кожної відмови порівнюються всі кадрові таблиці та виконуються integrity_check/foreign_key_check. Checksum 3 зафіксовано поряд із наявними 1–2. IPC-тести охоплюють нові сигнатури/відправників/невалідні відповіді та bundled preload → handler → SQLite → видалення. Electron Main smoke виконує всі чотири операції й перевіряє повернення історії через чинний backup/recovery. Повний pnpm test — 96/96 + smoke, typecheck/build/diff-check успішні. Лише mkdtemp; продукційна БД не відкривалася. GUI-кліки не автоматизувалися, ручний чекліст у HANDOFF ще не виконаний. Етап 04 не розпочато.

## HromadaAID як глобальна референсна реалізація

HromadaHR — незалежний локальний продукт майбутнього сімейства Hromada. AID є основним референсом готових компонентів, сценаріїв і технічних рішень на всіх наступних етапах. Оцінювання проводиться цільово перед реалізацією; джерело та SHA фіксуються в [HROMADAAID_REUSE.md](HROMADAAID_REUSE.md). Деталі вже перенесених UI-модулів — UI-TRANSFER.md.

Повторне використання не утворює runtime-залежності від AID, сервера чи його сховища. Межі: read-only незалежне джерело, сумісність з локальною SQLite, чинними міграціями, кадровою моделлю, типізованим IPC та sandbox. Надійні критичні механізми HR не переписуються без технічного обґрунтування. Авторизація, ролі й шифрування не повертаються. Перелік знайдених аналогів — реєстр рішень, а не дозвіл переходити до наступних модулів.

У продовженні 3.4.1 SettingsPage/HelpDialog адаптовано з AID SettingsPage.tsx/App.tsx (SHA 33eca10733caaf73b1a99e75a24ff35e706a0afb). Компонування налаштувань використовує чинний BackupSettings, about — system.getInfo; HelpDialog використовує спільний Modal. Account/server/update механізми не копіювалися. Контакти підтримки — текст для копіювання без нового IPC. BackupSettings зберігає mount при перемиканні секцій налаштувань; backup runtime не змінений.

### 3.4.3.8 — один знімок у двох місцях

BackupService під чинним exclusive створює один online snapshot у приватному staging/backup-cycle-*, після чого images.publishImage незалежно копіює закритий файл у кожне місце. Scratch прибирається у finally; при аварійному завершенні приватні залишки можливі, як і раніше.

names.ts приймає старий hromadahr-INSTANCE-KIND-TIMESTAMP-UUID.db та новий hromadahr-INSTANCE-KIND-TIMESTAMP-SHA256.db: спільний digest є ID точного образу; дата/namespace збережені, джерело з іншої lineage відхиляється. ## Облікові періоди й підтверджені залишки v6

Міграція 6 додає тільки `leave_period_balances`: працівник, один із трьох стабільних типів (`annual_main`, `oms_service_additional`, `children_social_additional`), межі ISO-періоду, основа (`initial_balance` або `confirmed_entitlement`), підтверджені цілі невід’ємні дні та необов’язкові довідкові дні належної тривалості для початкового залишку. STRICT/CHECK/FK/UNIQUE, індекс і SQLite-тригери забороняють некоректні календарні дати, від’ємні числа, дубль початку та перекриття одного типу в одного працівника. Видалення працівника каскадно видаляє періоди в межах однієї транзакції; довідники не зачіпаються.

`LeaveService` у Main обчислює лише пропозиції: робочі роки від дати прийняття послідовним додаванням календарного року зі затисканням дня до останнього дня місяця (для 29.02 у невисокосному році — 28.02), календарні роки для соціальної відпустки. Один запит обмежено 200 роками. Періоди за стаж ОМС автоматично не пропонуються. Пропозиції не записуються й не містять днів; у БД потрапляють лише явно підтверджені записи. Початок до 01.01.2027 вимагає основу `initial_balance`, від цієї дати — `confirmed_entitlement`. Пропорційного нарахування й юридичних норм немає.

Типізовані `leave:listPeriods`, `leave:proposePeriods`, `leave:savePeriods`, `leave:deletePeriod` проходять чинні preload/IPC межі та Main busy guard. Масове збереження виконується одним IMMEDIATE-транзакційним блоком; повторне збереження тієї самої ідентичності оновлює підтверджене значення. ## 4.2 — Інтерфейс залишків

LeaveBalances використовується у вкладці картки та в розділі «Відпустки» для вибраного працівника. Панель об’єднує записи й пропозиції Main за початком періоду в межах виду. Запит обмежено вибраним працівником і датою max(сьогодні, 01.01.2027). Один модальний редактор надсилає лише нові або змінені значення одним savePeriods. Після мутації панель перечитує Main. Довідкова тривалість збережених періодів зберігається при виправленні днів.

Після вилучення період за стаж ОМС залишається пропозицією в поточній панелі до її закриття. Для виправлення його меж вилучіть підтвердження й додайте ручний період із правильними межами. Схема v6 та контракти Main збережені.

## 4.3 — Реєстрації та списання (SQLite v7)

Міграція 7 після requiresBackup/перевіреного захисного знімка додає leave_records і leave_allocations. Реєстрація містить employee_id, вид, календарний інтервал, явну used_days, nullable реквізити розпорядження/пояснення, active/cancelled, created_at і request_id/request_json. Розподіл містить лише record_id, period_id і days. Періоди залишаються єдиним джерелом підтверджених величин. Доступно = confirmed_days − SUM(allocations.days для active реєстрацій). Окреме поле залишку відсутнє.

registerLeave виконує перевірку UUID/даних повтору, працівника, дат, перетинів, достатності та суми розподілу разом із INSERT реєстрації й усіх списань у межах однієї IMMEDIATE-транзакції. Нормалізований payload містить відсортовані за periodId розподіли. Повтор requestId із тими самими даними повертає існуючий запис, із відмінними — CONFLICT. Форма зберігає UUID для повтору незмінених даних після невизначеної відповіді.

Нові явні методи leave.registerLeave, listRecords(employeeId|null), getBalances, proposeAllocation проходять чинні sender/mainFrame/URL і strict Zod. FIFO сортує підтверджені періоди за periodStart/id та послідовно використовує доступні дні. Ручний розподіл має ту саму перевірку в транзакції. Права кадровик підтверджує самостійно.

Тривалість за замовчуванням — кількість календарних днів включно з обома датами. Зменшення потребує пояснення. used_days зберігається явно. Звичайна реєстрація починається від 01.01.2027 і не раніше hire_date. Перехідні відпустки з початком у 2026 році повертають TRANSITION_LEAVE.

savePeriods не дозволяє зменшення нижче використаного або зміну ідентичності використаного періоду. deletePeriod блокується за наявності будь-яких розподілів. FK розподілу на період — RESTRICT. BEFORE DELETE працівника спочатку видаляє реєстрації з каскадом розподілів, потім штатний каскад видаляє періоди. Виняток відкочує всі частини видалення.

Для 4.4 потрібні явні транзакційні операції корекції/скасування з повторною перевіркою перетинів, сум і доступності, захистом від застарілого редагування та узгодженою семантикою повтору requestId після корекції. Статус cancelled уже виключено з витрат і перевірки перетинів. У 4.3 операції зміни статусу через IPC відсутні.

## 4.4 — Атомарні виправлення й скасування

v8 додає revision INTEGER DEFAULT 1, cancelled_at/cancel_reason nullable та три мінімальні UPDATE-guards: відсутність перетину з іншими active записами, незмінність ідентичності/заборона реактивації cancelled та заборона прямого UPDATE розподілу (він замінюється DELETE/INSERT у транзакції). Старі записи й підтверджені величини міграція не змінює.

updateLeave({id,expectedRevision,...поля без employeeId/requestId}) виконує одну IMMEDIATE-транзакцію. Актуальний active запис і ревізія перевіряються перед розрахунком. Доступність тимчасово обчислюється без власних попередніх списань. Після перевірки суми, типу/працівника, меж дат і достатності старі розподіли замінюються новими, поля оновлюються та revision збільшується. Виняток відкочує поля, розподіли й ревізію. created_at, id, request_id/request_json є незмінною ідентичністю первинного створення. Повтор початкового registerLeave повертає актуальний стан того самого запису.

cancelLeave(id,expectedRevision,reason) переводить active у cancelled, записує UTC-час і причину та збільшує revision в IMMEDIATE. Повтор для cancelled повертає поточний запис. Розподіли зберігаються. Формула залишку продовжує враховувати лише active. FK RESTRICT та deletePeriod захищають навіть періоди, на які посилається cancelled. Їхні підтверджені дні можна коригувати з урахуванням витрат інших active реєстрацій.

proposeEditAllocation виключає власний record_id тільки після перевірки існування, active і expectedRevision. Жодних SQL-записів при пропозиції немає. В обох сценаріях FIFO враховує period_start<=startDate. Повернені допустимі ручні кандидати мають period_start<=endDate. Та сама межа endDate перевіряється в registerLeave/updateLeave. Для збережених раніше неправильних зв’язків allocationWarning обчислюється при читанні, не змінюючи історичні дані.

getRecord додає вузьке читання актуального запису. UI завантажує його перед редагуванням. Після UNAVAILABLE/невизначеної відповіді update/cancel перечитує запис. Корекція визнається успішною лише за expectedRevision+1 і тотожними полями/розподілом. Скасування перевіряється за фактичним статусом. Недоступність перевірки блокує наступну мутацію, зберігаючи чернетку. Після закриття діалогу дані також перечитуються. Зовнішній refreshRevision оновлює панель працівника після дій у загальному журналі.

## 4.5 — Подієвий режим і міграція v9

shared/leave.ts розділяє PeriodLeaveType (три види з періодами) й загальний LeaveType (шість реєстрацій). periodInput/proposedPeriod та proposeAllocation/proposeEditAllocation/proposePeriods приймають лише periodLeaveType. Спільна strict registration підтримує порожні allocations, але Main вимагає повну суму для періодного виду, порожній розподіл і непорожню grantBasis для подієвого. getBalances обчислює лише витрати фактичних періодних розподілів. Нових IPC-каналів немає; чинні операції та guards збережені.

В одному IMMEDIATE-блоці create/update перевіряють дати, hire/transition, тривалість, перетини й відповідний режим. Подієві не проходять перевірку достатності періодних днів. Для річних спеціальних видів перевіряється employee/type/рік start_date серед active без власного ID при редагуванні. shared specialLeaveLimits — єдине джерело runtime-числових меж для Main і UI; статичні CHECK v9 захищають ті самі межі в SQLite. cancelLeave зберігає історію й виключає запис із partial UNIQUE активного року.

v9 не вимикає foreign_keys і не покладається на перейменування старої батьківської таблиці: спочатку прибирає два зовнішні тригери, створює leave_records_v9 та leave_allocations_v9 з FK на нову батьківську, копіює всі дані до встановлення INSERT-guards, видаляє старі allocations, потім records. Перейменування нової records переприв’язує FK нової allocations; її кінцевий target перевірено тестом pragma foreign_key_list. Після перейменування allocations відтворюються сім старих тригерів реєстрацій/розподілів та додається guard несумісного виду на UPDATE. Відтворено індекси employee_dates/allocations_period і додано special_year. Два overlap-тригери й індекси періодів збережені. foreign_key_check у транзакції та integrity_check відкриття залишаються чинними. Помилки DDL/даних відкочують увесь rebuild; before-v9 snapshot містить вихідну v8.

Нове nullable grant_basis не змінює старі request_json. При canonical serialization null пропускається; непорожній текст включається. Тести відтворюють старі запити після міграції v7/v8 і після редагування. Заміна режиму звільняє старі allocations і зберігає новий запис/розподіл одним updateLeave без зміни ID, created_at, request_id/request_json. UI readback невизначеного update враховує grantBasis поряд з іншими полями. Перемикання на подієвий вид скасовує актуальність попередньої FIFO-відповіді й передає allocations: [].

EmployeeCard імпортує LeaveOverview замість LeaveBalances. Огляд виконує лише getBalances/listRecords/proposePeriods, використовує спільний balanceSummary і не монтує мутаційні компоненти. ## 4.6.4 — Поточні ручні права і робочий процес

Міграція v10: employee_leave_rights STRICT/FK/CASCADE/PK(employee_id,leave_type), CHECK шести типів і двох статусів, checked_at Main. Немає запису — немає ручної перевірки. Міграція лише створює таблицю після requiresBackup; 1–9/checksum незмінні. Чинний Main-only LeaveService розширено listRights/saveRights (два явні strict IPC). Збереження IMMEDIATE, максимум шість різних видів, status null видаляє поточну перевірку, час визначається Main; відновлення завжди використовує актуальне з’єднання. Права не беруть участі в register/update/cancel, FIFO, балансах чи річних перевірках.

App зберігає лише навігаційний ID для переходу картка→відпустки через чинні guards. Огляд використовує спільний summary і читає права, записи, підтверджені періоди. LeaveWorkspace володіє єдиним журналом, списком працівників, вибором контексту й refresh; LeaveRights володіє чернеткою поточної перевірки, балансова панель — чинними операціями залишків. registry.ts містить чисті комбіновані фільтри/стабільне сортування та лише календарні чернетки ОМС без SQL/IPC. Реєстрові стилі й контроли повторно використано з кадрового реєстру. Докладна композиція/звірка — HANDOFF 4.6.4; попередні підсекції описують історію UI.

## 4.6.5 — Обмежені майбутні пропозиції

annual_main у чистому proposedPeriods додає один наступний робочий рік після throughDate, не змінюючи isCanonicalPeriod/політику річниць. Пропозиції не містять величин і не пишуть у SQLite. useAccountingDate оновлює дату UI на хвилинному таймері/focus/visibility; BalanceEditor отримує стабільний знімок при відкритті, щоб зміна дня не втратила draft. Чинні суми/FIFO/допустимість списань залишаються Main-операціями. Три локальні секції Workspace розділяють журнал, залишки та права зі спільним ID; нових IPC чи схеми немає. Перегляд реєстрації — умовні інформаційні секції й таблиця, картка — шість окремих підблоків.

## 4.6.6 – Єдиний контекст і річна презентація

LeaveWorkspace зберігає один selected ID для залишків/прав і один records масив журналу. ## 4.7.6 – Дата набуття права за стаж

Захищена міграція v11 додає STRICT-таблицю employee_service_leave_start з однією календарною датою на працівника та каскадним FK. Попередні міграції, кадрові й відпускні записи збережено. ## 4.9.2 – Довідники підрозділів і посад

SQLite v12 додає `sort_order` та `revision` у `departments` і `positions`. Перша позиція дорівнює нулю. Наявні записи отримують щільний порядок за `name_key, id` під захистом verified pre-migration backup та чинної атомарної міграції. `personnel_dictionary_order` має окрему ревізію складу й порядку для кожного виду. Створення додає запис у кінець і збільшує цю ревізію. Видалення зсуває наступні позиції. Перейменування за тим самим ID змінює тільки назву, ключ і ревізію запису. Посади мають один глобальний порядок.

`PersonnelService` читає довідник і ревізію в одному знімку, а мутації виконує в IMMEDIATE-транзакціях. Reorder звіряє ревізію і повний набір унікальних ID. Видалення перевіряє поточні кадрові посилання під тим самим блокуванням, зовнішні ключі зберігають RESTRICT. Чотири нові IPC використовують чинну типізацію, strict Zod, перевірки відправника й блокування резервування. Наявні кадрові Select отримують упорядковані списки з Main.

## 5.1 – Backend стажу, надбавок і рангів

Реалізовано SQLite v13 (`seniority_ranks`), Main-only `SeniorityRanksService` і шість явних методів `window.hromadaHR.seniorityRanks`: `getAllowance`, `saveAllowance`, `clearAllowance`, `getRank`, `saveRank`, `clearRank`. Аргументи й відповіді перевіряються Zod; чинний sender/main-frame/URL guard збережено. Сервіс отримує актуальне з’єднання Storage для кожної операції, враховує BUSY, мутації транзакційні.

`employee_seniority_allowances`: PK/FK employee_id (ON DELETE CASCADE), status, percentage, effective_on, document_type, document_number, document_date, review_on, confirmed_at. Статус confirmed вимагає відсотка 0/10/15/20/25/30/40 та дати; not_applicable вимагає NULL для обох. Відсутній рядок, підтверджений 0% і not_applicable різні. Надбавка дозволена для обох типів працівників лише за явним рішенням кадровика.

`employee_current_ranks`: PK/FK employee_id (ON DELETE CASCADE), rank (ціле 1–15), assigned_on, nullable effective_on, ті самі реквізити документа, review_on, confirmed_at. Окрема effective_on зберігається NULL за відсутності; майбутній UI показуватиме assigned_on як початок дії. Ранг дозволений лише official (Main + SQLite trigger). PersonnelService повертає EMPLOYEE_HAS_CURRENT_RANK при спробі official → staff до явного очищення рангу; SQLite також блокує суперечність. Перехід staff → official не створює запису.

Дати реальні календарні ISO. assigned_on/effective_on не пізніше локального сьогодні (Main та SQLite triggers); вони можуть передувати hire_date. review_on довільна календарна дата й нічого автоматично не змінює. confirmed_at задає Main при кожному збереженні. Документ необов’язковий; кожен реквізит може бути NULL. Очищення ідемпотентне для наявного працівника; невідомий працівник дає NOT_FOUND. Зберігається тільки актуальний стан без історії.
