# Етап 2.5: результати дослідження, реалізацію зупинено

Дата: 02.11.2026. База дослідження — main, `a2dde3042b0e7d012a08a146807d7a43df336a11`, початкове робоче дерево чисте. Замовник підтвердив, що тестового SMB-стенда зараз немає.

**Етап 2.5 не завершений.** Код застосунку, IPC, налаштування, шлях робочої БД, WAL та міграції 1–2 не змінені. Додано лише відтворюваний Windows-прототип і його локальні тести. Це не механізм блокування HromadaHR, не дозвіл відкривати активну БД через SMB і не підтвердження її мережевої надійності.

## Чому зупинено

У завданні прямо заборонено імітувати ексклюзивність і дозволено зупинити відповідну частину, якщо її надійність у цільовому середовищі забезпечити неможливо. Тут немає конкретного SMB-сервера/діалекту/налаштувань та двох тестових клієнтів; замовник підтвердив відсутність стенда. Тому немає доказу виконання вимоги щодо втрати й повернення мережі та одночасного відновлення доступу двома ПК. Це брак підтвердження для цільового середовища, а не твердження, що Windows/SMB взагалі не підтримує блокувань.

Зміну шляху, підключення, перенесення, екран очікування й мережеве відновлення не ввімкнено частково: всі вони залежать від єдиного надійного сеансового блокування до **будь-якого** відкриття SQLite або recovery-журналу. Наявні `openPaths` та single-instance lock Electron цього між комп'ютерами не забезпечують. Тестовий guard не підключений до production-коду.

## Перевірені джерела та кандидати

| Механізм | Що забезпечує | Межа застосування |
| --- | --- | --- |
| `CreateFileW`, `dwShareMode=0`, утримуваний HANDLE | ОС відхиляє несумісне повторне відкриття того самого файла; це не перевірка існування lock-файла | Кандидат для окремого сеансового guard; треба довести узгодження його lifetime з усіма SQLite/recovery-дескрипторами на цільовому SMB |
| `LockFileEx`, EXCLUSIVE та FAIL_IMMEDIATELY | ОС-блокування діапазону байтів, підтримка SMB заявлена Microsoft | Не з'єднує автоматично lifetime окремого guard із незалежними файлами БД/журналів |
| `PRAGMA locking_mode=EXCLUSIVE` | SQLite утримує власні файлові блокування довше | Потребує вже відкритого SQLite-з'єднання, отже саме по собі не виконує вимогу «другий процес не відкриває SQLite до блокування»; також не закриває протокол заміни файла під час restore |
| Named mutex / JS Set / Electron single-instance | Координація на одному хості або в одному процесі | Не міжкомп'ютерний механізм |
| Існування lock-файла, PID, timestamp, heartbeat | Можуть бути лише діагностикою | Не доказ ексклюзивності; примусове «прострочення» не використовується |

Microsoft описує [sharing semantics CreateFile](https://learn.microsoft.com/en-us/windows/win32/fileio/creating-and-opening-files) та [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex). Пряме відкриття самої БД з shareMode=0 також заборонить її повторне відкриття власним звичайним SQLite-дескриптором; це не готова обгортка для better-sqlite3.

За [специфікацією SMB](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/ae543f57-d993-4905-bce0-3cfc446c1fbb) реакція на disconnect залежить від durable/resilient/persistent open. Окремо визначено [reconnect durable open](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/3309c3d1-3daf-4448-9faa-81d2d6aa3315). **Інженерний висновок:** сам факт успішного відкриття sidecar-guard до `new Database()` ще не доводить, що старий власник не зможе записати через інший дескриптор після втрати guard. Потрібен доказ втрати можливості запису попереднім власником (fencing) і fail-closed обробка, а не лише опитування раз на 5 секунд. Конкретний split-brain на SMB тут не відтворювався і не оголошується доведеним.

[SQLite попереджає про залежність від надійності locking/fsync мережевої ФС](https://www.sqlite.org/useovernet.html). [WAL потребує одного хоста](https://www.sqlite.org/wal.html). Перехід на DELETE потрібний для цього задуму, але сам по собі не сертифікує SMB. Висновок не базується на припущенні «SMB завжди небезпечний».

## Що фактично протестовано

`tests/helpers/windows-share-handle.ps1` викликає Win32 `CreateFileW` через P/Invoke, з `GENERIC_READ|GENERIC_WRITE`, `dwShareMode=0`, `OPEN_ALWAYS`. Файл не обрізається й не видаляється; право доступу визначається утримуваним ОС-дескриптором. Немає heartbeat/stale timeout. HANDLE закривається нормально або ОС при аварії процесу. Прототип не виконує SQL, не відкриває робочі бази та не запускається застосунком як фоновий helper/service.

`tests/windows-lock-probe.test.mjs` створює лише mkdtemp-каталоги, запускає окремі Windows PowerShell-процеси без профілю, не змінює execution policy чи ACL. Перевірено:

1. Перший процес отримує HANDLE, другий отримує саме `ERROR_SHARING_VIOLATION=32`.
2. Після нормального закриття другий процес отримує HANDLE без видалення guard-файла.
3. Після примусового завершення власника новий процес також отримує HANDLE.
4. Відсутній каталог повертає `ERROR_PATH_NOT_FOUND=3`, а не «зайнято»; каталог не створюється.

На не-Windows ці чотири тести явно пропускаються. Довільний UNC-шлях тести не приймають: немає ризику випадково запустити їх на робочому ресурсі. Це локальний NTFS/ОС-прототип **без інтеграції з SQLite**. Не тестувалися два SQLite-сеанси під цим guard, автопідключення HromadaHR, міграція WAL під міжкомп'ютерним lock, перенесення або restore через SMB. Чинні 46 регресійних тестів етапу 2.4 та Electron smoke залишаються окремими перевірками локальної реалізації.

## Цільова модель за вимогами завдання — ще не реалізована

Один застосунок і одна модель розташування, без local/network прапорця та без окремих редакцій. За замовчуванням — чинний LOCALAPPDATA шлях. Налаштування шляху має бути у локальному `storage-location.json` поряд із dev/built-конфігурацією, поза SQLite; запис атомарний. Підключення наявного файла ніколи не має дозволу створювати новий. Лише явна дія «Створити нову базу» може створювати файл. Вибраний зайнятий/недоступний шлях зберігається; fallback у локальну порожню БД відсутній.

Межа сеансу: отримати ОС-блокування → перевірити/відновити службовий журнал → відкрити SQLite → checkpoint наявного WAL → перевірити DELETE → цілісність/схема/міграції → дозволити роботу й backups. Відпускати lock після закриття всіх пов'язаних з'єднань та файлових операцій. WAL/SHM не видаляти вручну. Native-реалізація має врахувати UNC, mapped drives, алиаси сервера/теки, hardlink/reparse identity, зміну файла під час restore та поведінку при reconnect. PowerShell-прототип не обрано production-backend.

Стан UI визначається перевіреними результатами ОС: busy лише для доведеної конкуренції, unavailable для помилок ресурсу/мережі, invalid/corrupt для формату/схеми. Поки lock не отримано, SQLite та scheduler не запускаються. Waiting-екран, retry близько 5 секунд, ручний retry/інша база/закриття — вимоги до майбутньої інтеграції, зараз не створені. При невизначеному стані мережі потрібно заборонити нові операції, а не продовжити записи після чергового heartbeat.

Перенесення має утримувати блокування джерела й цілі, створювати/перевіряти online snapshot без перезапису цілі, пробно відкривати нову БД під її lock і лише тоді атомарно фіксувати локальний шлях. Після помилки — старе розташування; оригінал автоматично не видаляється. Підключення другого ПК: явний вибір того самого наявного файла, збереження шляху, очікування до звільнення; ніякої локальної робочої репліки. Ці процедури описують ціль, а не доступні кнопки.

### Рішення для конфігурації резервування

Рекомендований простий варіант для продовження: фізичні backup-теки зберігати локально для кожної інсталяції; у спільній SQLite залишити глобальний добовий результат та ідентичність пари цілей поточного циклу. Автоматичні копії робить лише власник сеансового lock. Після повного успіху двох тек наступний ПК того самого дня не дублює цикл. Для незавершеного циклу тієї самої пари повторюється лише невдала тека; якщо інша інсталяція має іншу пару, треба почати повний цикл для нової пари, не змішуючи один успіх з ПК A з іншим успіхом з ПК B. Копії незавершеного циклу зберігаються. Налаштування одного ПК не трактуються як локальні шляхи іншого; відсутність власних тек — явне неналаштоване резервування без fallback. Ручні копії не змінюють глобальний добовий успіх.

Це технічне рішення для майбутнього коду, **не нова реалізована схема**. Потрібна нова міграція/перенесення конфігурації, без зміни SQL/checksum міграцій 1–2. Наявні backup_config/backup_state поки працюють як у 2.4. Чинні hardlink-публікація, protective snapshots та restore-журнал теж не оголошуються перевіреними на SMB.

## Стенд і ручне приймання, необхідні перед активацією

Тільки окремі тестові дані, два фізичні Windows-ПК та конкретна SMB-папка. Зафіксувати версії Windows/сервера/NAS, SMB dialect, файлову систему, durable/CA/offline-files налаштування; жодних автоматичних змін ACL/кешування/служб.

- [ ] Одночасний старт A/B: другий не доходить навіть до readonly SQLite/preflight/recovery; при звільненні автоматично отримує lock.
- [ ] UNC, mapped drive, альтернативне ім'я сервера/шари посилаються на той самий ресурс без двох власників.
- [ ] Нормальне закриття та аварійний kill A до/після відкриття SQLite, під час транзакції, backup, міграції та restore.
- [ ] Фізичний розрив мережі A, спроба B отримати доступ, повернення A: немає перетину власників і відкладених записів старого власника. Не знімати lock власним тайм-аутом.
- [ ] Перезапуск SMB-сервера, короткий/довгий disconnect, durable reconnect та sleep/resume клієнта. Native error відділяє busy від unavailable без удаваної готовності.
- [ ] Втрата ресурсу не створює порожню БД і не змінює вибраний шлях. Недоступний/пошкоджений/новіший файл відхиляється без перезапису.
- [ ] WAL-міграція з залишковими WAL/SHM лише під lock; integrity/FK/checksum після DELETE і після аварійного повернення.
- [ ] Перенесення: повна/нестача місця/недоступна/зайнята ціль, оригінал збережений, локальний path-record не змінений до успіху.
- [ ] Manual/auto/rotation/protective backup/restore/rollback після перенесення; очікуючий ПК не виконує жодної операції; зміна фізичного файла під час restore не обходить lock.
- [ ] Backup-теки різних ПК, повний/частковий добовий цикл, відсутність дублювання завершеного циклу, відсутність локальної робочої репліки.

Позитивний прогін тільки локальних двох процесів або loopback SMB не замінює цей стенд. Навіть стенд має описувати конкретні підтримані умови, а не гарантію для будь-якого NAS.

## Альтернативи

1. Зберегти одну локальну БД і один процес HromadaHR на виділеному Windows-ПК; працювати з ним послідовно через вже організований Remote Desktop. Це не потребує HTTP/SQL-сервера в HromadaHR, локальних реплік або зміни поточної моделі SQLite. Налаштування віддаленого доступу тут не виконується.
2. Якщо саме файл SMB є обов'язковим — надати стенд і окремо завершити native session/fencing-протокол з негативними мережевими тестами. Це може потребувати інтеграції на рівні SQLite VFS/Win32, а не лише JS-lock wrapper.
3. Серверний власник БД міг би усунути мережевий файловий канал, але виходить за чинну заборону сервера. Він не створюється й не приймається як прихована зміна архітектури.
