# HromadaHR

Локальний настільний застосунок кадрового обліку для органів місцевого самоврядування України. Версія **0.1.0**, SQLite **v21**, Electron **44.7.1**. Цільова платформа — Windows 10/11; пілотний обсяг — близько 30 працівників. Функціональні етапи 1–7 завершені; комплексне Windows GUI-приймання ще не виконано.

## Реалізовано

- **Працівники:** реєстр із пошуком/фільтрами/групуванням, створення/редагування/захищене видалення; повноцінна сторінка працівника. Поточне призначення: підрозділ, посада, дата, категорія; історії призначень немає.
- **Стаж, надбавки, ранги:** підтверджена опора й показники, єдині редактори у профілі, read-only прогнози/контрольні дати, спеціальні рангові випадки. Прогнози не оформлюють кадрових рішень автоматично.
- **Відпустки:** шість підтримуваних видів, права, історичні/нові періоди й підтверджені дні, річний облік спеціальних видів, реєстрація/редагування/скасування. Ручний розподіл і FIFO за явною дією, особиста історія та глобальний журнал; контекстні переходи зберігають ту саму чернетку. Нові реєстрації від 01.01.2027.
- **Огляд і дзвіночок:** кадрові нагадування, горизонт 7/14/30/60/90 днів, відкладення/перегляд, перехід до працівника; неповні дані окремо.
- **Документи:** реєстр, пошук/фільтри/картка/create/edit/delete, один працівник у UI, явні структурні зв’язки з відпустками. Серії й річні ручні/атомарні автоматичні номери, claims без повторного використання позицій після delete. LeaveRecord та PersonnelDocument — різні сутності.
- **Довідники:** підрозділи/посади з порядком і revision guards, окремі серії документів.
- **Налаштування/backup:** два місця перевірених копій, каталог/історія й захищений restore; кадровий контроль, масштаб інтерфейсу 80–150%, «Про програму».

Глобальна навігація: **Головна · Огляд · Працівники · Документи · Довідники · Налаштування**. Персональні операції виконуються у профілі, глобальний журнал відпусток — у «Документах». Колишніх глобальних «Відпусток» / «Рангів та вислуги» немає.

## Системні вимоги та збірка для розробки

Windows 10/11, цільове приймання x64; Node.js **24.22.1**, pnpm **11.25.0** за package.json. Для початкового встановлення залежностей та Electron потрібен інтернет; built працює локально без Vite/HTTP-сервера. Сумісність конкретної Windows build, пристрою та масштабів підтверджується ручним протоколом, а не цією декларацією.

```powershell
pnpm install --frozen-lockfile
pnpm dev
```

Dev використовує `http://127.0.0.1:5176/`. Після зміни Main/preload перезапустіть dev-сеанс.

```powershell
pnpm typecheck
pnpm test
pnpm build
```

`pnpm test` включає Electron storage smoke й ізольовані синтетичні SQLite-тести. `pnpm build` створює dist/dist-electron, але не інсталяційний пакет. Після збірки, **лише в безпечному тестовому Windows-профілі для приймальних сценаріїв**:

```powershell
pnpm start:built
```

Це запуск наявної збірки `electron .` без Vite. **Built читає `%LOCALAPPDATA%\HromadaHR\data\hromadahr.db` поточного користувача**, dev — `%LOCALAPPDATA%\HromadaHR-dev\data\hromadahr.db`. Electron userData/інтерфейсні налаштування окремо під appData (зазвичай `%APPDATA%\HromadaHR` або `HromadaHR-dev`). Дані dev і built незалежні, але звичайний built-профіль може містити реальні кадрові відомості.

Для руйнівних тестів потрібні **окремий тестовий локальний Windows-користувач або disposable Windows VM**, підтвердження власника/шляхів і лише синтетичні дані. Не видаляйте `%LOCALAPPDATA%\HromadaHR`, не підміняйте env paths і не відновлюйте тестові копії поверх робочої бази. Починайте з [A01 протоколу](docs/ACCEPTANCE-WINDOWS.md), а не зі start:built у звичайному профілі.

## Архітектура й обмеження

Electron/React/TypeScript/Vite; SQLite через better-sqlite3 лише в Main, WAL/FK/checksum міграцій. Sandbox/contextIsolation, renderer без Node.js/SQLite, strict typed IPC з перевіркою аргументів і sender/frame/URL. Користувацькі дати ДД.ММ.РРРР; ISO збережено в SQLite/IPC.

Windows-інсталятора й автоматичних оновлень через GitHub Releases немає. DOCX, historical snapshot, історичні події рангів/надбавок, майстер первинного введення, XLSX-імпорт і масові кадрові операції не реалізовані. Пароль/ролі/шифрування виключені чинними рішеннями; захист доступу до Windows-профілю та копій потребує операційних заходів. Прогнози не замінюють кадрову перевірку. Міграція v5 очищує погоджені старі тестові кадрові записи, тому restore v4 і нижче не слід вважати способом перенесення реальних працівників.

Vite попереджає про основний JS chunk понад 500 kB; це не помилка build. Успішні автоматичні перевірки не є прийманням до експлуатації. Повний перелік і рішення — [RELEASE-GAPS](docs/RELEASE-GAPS.md).
